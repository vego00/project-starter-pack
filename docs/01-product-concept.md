# 01. 제품 구상

상태: 제안 초안 v0.1 · 2026-11-04

## 목적과 문제 정의

**Source:** 사용자가 겪는 불편을 해결하기 위해, 무엇을 만들고 어떻게 검증할지 판단할 수 있는 출발점을 제공한다.

**문제 정의:** 문제를 설명할 수는 있지만 이를 요구사항·에이전트 역할·도구·검증 기준으로 연결하기 어려운 사용자가, 개발을 시작할 수 있는 일관된 설계를 얻도록 한다.

| 구분 | 내용 |
| --- | --- |
| Goal | 문제 입력에서 개발 가능한 설계 패키지까지 연결한다. 사용자에게 다음 행동과 미확인 조건이 명확해야 한다. |
| Context | 독립된 신규 프로젝트. 기획서 생성보다 넓은 범위를 지향하며, 먼저 Markdown으로 구상한다. |
| Behavior | 문제 구조화, 필요한 질문, 에이전트 필요성 판단, 구성 설계, 검증, 문서 출력과 수정 반영 |

## 근거 수준

| 상태 | 내용 |
| --- | --- |
| 사실 | 프로젝트명과 저장소를 정했고, 구현 전 문서 작업을 요청했다. |
| 해석 | 프로젝트를 시작할 때 반복되는 설계 의사결정을 재사용하려는 방향으로 이해한다. |
| 가정 | 초기 사용자는 AI 기능이나 업무 자동화를 직접 개발하려는 개인 개발자다. 사용자 검증이 필요하다. |
| 제안 | 작은 설계 생성 MVP를 검증한 뒤 실행 기능을 확장한다. |

## 사용자 관점 점검

- **I:** 막연함을 줄이되 질문이 많아 시작을 포기하지 않도록 한다.
- **IT:** 생성 속도뿐 아니라 수정량, 누락, 실제 첫 개발 작업 수행 가능성을 확인한다.
- **WE:** 개발자와 요청자가 목표·책임·완료 조건을 같은 의미로 이해할 수 있어야 한다.
- **ITS:** 접근 가능한 데이터와 도구, 권한, 비용, 운영 담당자를 설계에 포함한다.

## MVP 범위 제안

| 우선순위 | 기능 | 완료 모습 |
| --- | --- | --- |
| Must | 문제 구조화 | 목적, 사용자, 입력, 결과, 제약, 가정이 분리된다. |
| Must | 해결 구조 설계 | 일반 자동화·단일 에이전트·다중 에이전트 중 선택하고 이유를 설명한다. |
| Must | 설계 패키지 생성·검증 | 역할·입출력·도구·흐름·평가·작업 목록이 일관되게 연결된다. |
| Should | 대화 기반 부분 수정 | 변경 요구와 영향받는 문서가 함께 갱신된다. |
| Should | 대표 사례 템플릿 | 동일한 출력 계약을 여러 문제에 적용한다. |
| Nice | 그래프 시각화 UI | 역할과 분기·재시도·승인 지점을 확인한다. |

초기 범위 밖: 임의 코드의 자동 실행, 외부 서비스 쓰기, 자동 배포, 무제한 자율 개선, 모델 파인튜닝.
이 기능들은 후속 검토 대상이며 제품의 최종 확장 범위를 제한하지 않는다.

## 대표 사용 흐름

1. 사용자가 불편과 원하는 결과를 입력한다.
2. 시스템이 목적·요구사항·제약을 정리하고 결론을 바꾸는 정보만 질문한다.
3. 정보가 부족하면 가정을 표시하고 진행하거나, 필수 조건이 없으면 해당 부분을 보류한다.
4. 일반 자동화와 에이전트 방식을 비교하고 필요한 역할만 설계한다.
5. 도구의 실제 연결 여부, 권한, 실패 처리와 검증 계획을 포함한다.
6. 사용자가 설계를 검토하고, 수정 또는 개발 착수를 선택한다.

## 예시: 회의 후 후속 작업 누락

**가상 입력:** “회의가 끝나면 담당자와 할 일을 놓친다. 회의록에서 작업 후보를 정리하고 싶다.”

- 목적: 합의한 일을 빠뜨리지 않고 담당자가 확인하게 한다.
- 확인할 조건: 회의록 형식, 담당자 식별 기준, 연결 대상, 외부 등록 권한.
- 제안 설계: 작업 추출 → 근거 문장 연결 → 담당자·기한 확인 → 검토용 목록 출력.
- 경계: 발언에 없는 담당자나 기한을 사실로 만들지 않는다. 미정으로 표시한다.
- MVP 결과: 위 흐름의 에이전트 명세와 검증 계획. 실제 회의록 처리·작업 등록은 아직 수행하지 않는다.
- 후속 실행 단계: 사용자가 검토한 작업만 외부 도구에 등록하도록 설계한다.

인프라 스타터 생성도 동일한 구조의 활용 사례다. Docker·DB·캐시·클라우드는 요구사항에 따라 선택하며, 모든 프로젝트에 일괄 적용하지 않는다.
