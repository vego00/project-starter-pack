# 03. 검증과 로드맵

상태: 제안 v0.1 · 측정 결과 없음

## 무엇으로 성공을 판단할까

생성 문서 수와 에이전트 수는 성공 지표로 쓰지 않는다.
핵심은 사용자가 결과를 이해하고 첫 개발 작업을 수행할 수 있는가다.

| 지표 | 측정 방법 | 해석 시 주의 |
| --- | --- | --- |
| 요구사항 추적성 | 필수 요구사항과 설계·평가 항목의 연결 확인 | 링크가 있어도 실제 충족 여부를 별도 검토 |
| 설계 일관성 | 역할 입출력, 흐름 의존성, 도구 권한의 모순 기록 | 자동 검사와 사람 검토 병행 |
| 개발 착수 가능성 | 다른 사람이 첫 작업의 입력·출력·완료 조건을 설명하고 수행 | 작성자만 이해하는 문서는 실패 |
| 수정 부담 | 최초 결과 이후 수정 건수와 수정 시간 기록 | 질문을 줄여 수정 부담을 늘리지 않음 |
| 실행 비용·지연 | 호출 횟수, 사용량, 생성 시간 기록 | 저렴하고 빠르더라도 품질 미달이면 실패 |

초기 수치 기준선은 없다. 대표 사례에서 기준선을 수집한 뒤 목표치를 정한다.

## 대표 평가 사례

다음은 실제 사용자 조사 결과가 아닌 검증용 가상 사례다.

| 사례 | 기대 판단 | 주요 실패 조건 |
| --- | --- | --- |
| 회의록 → 작업 후보 | 근거 연결, 미정 담당자·기한 표시 | 없는 담당자·기한을 확정 |
| 사내 자료 질의응답 | 자료 접근권한, 검색·근거·응답 검증 설계 | 접근할 수 없는 자료를 사용 가능으로 처리 |
| 새 API 서비스 시작 | 필요에 맞는 DB·환경·검증 계획 | Redis·Kubernetes 등을 무조건 추가 |
| 정해진 형식의 파일명 변경 | 일반 스크립트 가능성 우선 검토 | 단순 작업에 불필요한 다중 에이전트 구성 |
| 정보 부족·상충 요구 | 질문, 가정 표시, 불가능 조건 설명 | 무제한 질문·보정 또는 모순 은폐 |

동일 사례를 단일 프롬프트 기준선과 구조화 파이프라인에 적용한다. 모델·입력·설정·버전을 기록하고, 검토자가 같은 기준표로 결과를 평가한다.

## 단계별 진행

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 0. 구상 | 목적·범위·논리 구조·평가 기준 작성 | 현재 문서 초안 마련 |
| 1. 사례 구체화 | 대표 입력과 기대 출력, 판정표 작성 | 정상·예외·비에이전트 사례를 설명 가능 |
| 2. 계약 확정 | 상태·에이전트·도구·문서 구조 결정 | 필수 필드와 모순 판정 규칙 명확 |
| 3. 최소 구현 | 입력 → 설계 → 검증 → Markdown 출력 | 대표 사례를 끝까지 처리하고 실패를 드러냄 |
| 4. 수정·관찰 | 버전 관리, 부분 수정, 비용·지연 기록 | 변경 영향과 품질 개선 여부 확인 |
| 5. 제한된 실행 | 한 종류의 안전한 도구부터 연결 | 승인·실패·재시도·결과 검증 확인 |
| 6. 확장·배포 | 코드/인프라 생성, 운영 기능 검토 | 사용자 가치와 운영 부담에 근거해 선택 |

순서는 제안이며 날짜는 미정이다. 초기 담당·범위 결정자는 저장소 소유자로 가정한다.
구상 단계에는 GPU나 배포 환경이 필요하지 않다. 구현 단계의 모델 예산은 별도 결정한다.

| 항목 | 초기 제안 | 결정 시점 |
| --- | --- | --- |
| 첫 사용자 | AI 프로젝트를 시작하는 개인 개발자 | 사례 구체화 전 |
| 첫 대표 문제 | 회의록 기반 후속 작업 설계 | 사례 구체화 시 |
| 최종 지향 범위 | 설계 생성에서 제한된 실행까지 단계 확장 | 최소 구현 검증 후 |
| LLM 공급자·모델 | 교체 가능한 인터페이스, 우선 한 모델 | 최소 구현 전 |
| 개발 인터페이스 | CLI 또는 최소 웹 폼 | 최소 구현 전 |

| 기존 프로젝트 재사용 | 코드보다 역할·상태·검증 경험을 우선 활용 | 실제 코드 검토 후 |
