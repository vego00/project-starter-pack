# 먼저 겪어 본 시행착오

Project Starter Pack을 만들면서 실제로 겪은 일이에요. 같은 실수를 피하는 데 쓰세요.

## 설계

- **형식 검사를 통과했다고 문제가 풀린 것은 아니다.** 구조가 맞는 설계도 사용자 문제를 못 풀 수 있다. 완료 기준에 실제 사용자 결과를 넣는다.
- **역할은 기술 선택이 아니라 요구사항에서 나온다.** 어떤 기술을 고를지 정해도 서비스가 무엇을 해야 하는지는 알 수 없다.
- **지금 설계하는 대상이 어느 시스템인지 구분한다.** 만드는 도구의 규칙과, 그 도구가 만들어 줄 서비스의 규칙이 섞이기 쉽다.
- **내부부터 만든다.** 화면과 선택 카드를 먼저 만들었더니 정작 핵심 기능이 비어 있었다.

## 진행

- **구현이 설계 고민을 앞지르지 않게 한다.** 작업 목록을 순서대로 처리하다 보면 애초에 맞는 목록인지 묻지 않게 된다.
- **이번 단계에서 검증하지 않을 것을 정한다.** 연결 확인과 품질 평가를 나누면 한 번에 다 하려다 멈추는 일을 줄인다.
- **한 번에 끝까지 이어 본다.** 부분을 다듬기 전에 처음부터 끝까지 도는 흐름을 먼저 만든다.

## 문서

- **사실마다 원본을 하나만 둔다.** 설계 문서 21개가 서로 겹치면서 같은 내용이 어긋났다.
- **코드가 원본인 내용은 문서에 옮겨 적지 않는다.** API 표와 폴더 구조는 코드가 바뀌면 바로 틀린다.
- **문서와 코드가 다르면 코드를 확인하고 기록한다.** 문서에는 있던 Fallback이 코드에는 없었다.
- **작업 기록은 상태값이 아니라 본문에 남긴다.** 무엇을 했고 무엇을 확인하지 못했는지가 없으면 나중에 따라갈 수 없다.

## 모델과 검증

- **실패 경로를 먼저 정한다.** 모델 호출은 시간 초과, 한도 초과, 형식 오류가 흔하다. 실패해도 사용자의 결정이 사라지면 안 된다.
- **중간 결과를 저장한다.** 실험 스크립트가 끝에서만 저장해 무료 한도에 걸렸을 때 측정값을 모두 잃었다.
- **연결 확인과 성능 검증을 구분한다.** 한 번 호출에 성공한 것은 품질이 좋다는 뜻이 아니다.
- **반드시 지킬 규칙은 지침이 아니라 코드나 권한으로 강제한다.** 지침은 요청이고 보장이 아니다.
