# 사례 1 · 토스

## 원문

- 선정: [LLM을 이용한 서비스 취약점 분석 자동화 #1](https://toss.tech/article/vulnerability-analysis-automation-1) (토스 기술블로그, 표상영 · Security Researcher, 2025-12-24)
- 보조: [같은 제목 #2](https://toss.tech/article/vulnerability-analysis-automation-2) (2026-03-20)
- 선정 이유: 지시서가 고정한 사례다. 목표, 초기 접근(벡터 검색, 저장소 압축), 관찰한 실패, 후속 시도와 결과가 모두 원문에 있다.
- 원문 확인: 2026-11-18 curl로 HTML을 받아 본문 텍스트를 추출해 읽었다. 단서로 쓴 프로젝트 기록: Notion 사례 C6.

## 기준 시점

대용량 소스코드를 LLM에 넣는 방법을 정하던 때. 벡터 검색과 저장소 압축을 시도하기 전이다.

## 실행 입력

> 보안 연구 담당자입니다. 회사에는 서비스가 수백 개 있고, 대부분 상당한 규모의 소스코드를 가지고 있습니다. LLM이 서비스 소스코드를 직접 분석해서 보안 취약점을 찾아 주는 자동화를 만들고 싶습니다. LLM이 스스로 소스코드를 분석해 취약점을 찾는 외부 연구 결과를 보고 가능성이 있다고 판단했고, 사내의 작은 프로젝트 모임으로 시작했습니다. 새로 공부할 기술은 많고 쓸 수 있는 자원은 한정되어 있습니다.
>
> 제약: 서비스 소스코드가 커서 전체 코드를 한 번에 LLM에 넣기 어렵습니다.
>
> 지금 검토 중인 방법: 코드를 벡터로 임베딩해 필요한 부분만 가져오는 방식, 또는 저장소 전체를 하나로 압축해 모델에 넣는 방식.

넣지 않은 것: 회사명, 원문 제목, URL, 사용 모델, 실행 빈도와 비용 계산, 해결 과정. 권한·예산·기준값은 원문에 없어 만들지 않았다.

## 평가자용 기록

### 관찰한 실패와 발생 조건 (원문 #1 인용)

1. 벡터 검색: “코드를 벡터로 임베딩해서 필요한 부분만 가져오는 방식이었는데, 코드 간 연관관계를 제대로 파악하기 어려웠어요.”
2. 저장소 압축: “Repomix 같은 툴로 전체 소스코드를 압축해서 던져주는 것도 시도해 봤습니다. 하지만 결국 모든 시도가 토큰 문제로 실패” — 실행 입력의 제약과 같은 내용이다.
3. 정보 과다로 인한 환각: “설사 토큰 Context Size 안에 맞춘다고 해도 더 큰 문제가 있었어요. 바로 Hallucination이었습니다. 너무 많은 정보를 한 번에 처리하다 보니 LLM이 실제로는 없는 취약점을 만들어내거나, 코드의 흐름을 잘못 이해하는 경우가 빈번했거든요.”
4. 실행마다 다른 결과(코드 참조 문제를 푼 뒤): “XSS 취약점이 총 10개 있으면, 어떨 때는 8개만 찾고 2개를 빼먹고, 어떨 때는 10개를 다 찾기도 하고, 심지어 9개를 찾았다가 다시 돌리면 7개만 찾기도 하는 등 결과에 일관성이 없었어요.” (모델 Claude-Sonnet-4)

### 후속 시도와 결과

| 순서 | 시도 | 결과 (원문) |
| --- | --- | --- |
| 1 | 모델이 필요할 때 코드를 찾아 읽는 도구를 만들었다(MCP, tree-sitter·ctags·ripgrep로 미리 색인) | “MCP 덕분에 소스코드 참조 문제는 해결됐지만, 이제 정확도 문제가 발목을 잡았어요.” |
| 2 | 정적 분석 도구(Semgrep)로 모든 Source→Sink 경로를 모으고 모델이 전부 분석. CodeQL은 빌드 필요·비용·라이선스 때문에 제외 | “실제로 이 방식을 적용하니 항상 취약점을 놓치지 않고 찾아내는 결과를 얻을 수 있었어요!” |
| 3 | 경로 100개 중 10개만 의미 있어 토큰 낭비 → Supervisor·Discovery·Analysis 세 에이전트로 나눔 | “비용도 줄이고 전체 분석 시간도 단축할 수 있었습니다.” |

| 결과 | — | “최종적으로 정확도 95% 이상의 LLM 취약점 분석 자동화를 구현” (자체 보고, 측정 기준은 원문에 없음) |

### 채점 메모

- ‘실제 문제와 일치’ 2점: 잘라서 가져오는 검색이 코드 사이의 관계(호출·데이터 흐름)를 놓친다는 점, 또는 한꺼번에 많이 넣으면 없는 취약점을 만들거나 흐름을 잘못 읽는다는 점, 또는 같은 코드에서 실행마다 결과가 달라진다는 점을 발생 조건과 함께 짚었다.
- “코드가 커서 한 번에 넣을 수 없다”만 말한 답은 입력의 제약을 되풀이한 것이라 이 항목 0점(작성자 결정, 2026-11-18). 그 답이 구체적인 비교 실험을 제안했다면 판별력은 따로 채점한다.
- 원문이 공개되어 있어 실행 모델이 이 사례를 기억할 수 있다.
