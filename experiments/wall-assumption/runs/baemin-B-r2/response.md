# 초기 설계안과 구현 첫날 계획

## 1. 설계 요약

**기본 구조.** 도구(검색, SQL)를 공통 인터페이스로 분리하고, 그 위에서 질문을 처리하는 방식(고정 워크플로 또는 에이전트 루프)을 교체할 수 있게 둔다. 제안하신 초기 설계(고정 워크플로에 소스 추가)를 출발점으로 삼되, 처리 방식을 바꿔도 나머지가 영향받지 않도록 경계를 둔다.

| 구성 | 내용 |
|---|---|
| 도구 계층 | 기존 SQL 조회, 테이블/메타데이터 검색에 더해 포털, 위키, 이슈 도구, 문서 저장소, 메신저 검색을 같은 형태(입력: 질의와 사용자 ID, 출력: 출처 포함 스니펫)로 래핑 |
| 접근 권한 | 검색 시점에 질문자 권한으로 필터링. 메신저와 문서는 권한이 제각각이라 인덱스 단계에서 ACL 메타데이터를 보존 |
| 대화 맥락 | 세션 단위 히스토리를 저장하고, 후속 질문은 독립 질의로 재작성한 뒤 검색 |
| 답변 형식 | 항상 출처 링크를 붙이고, 근거가 부족하면 모른다고 답하며 담당자 후보를 안내 |
| 개선 루프 | 모든 질문에 트레이스(질의, 호출한 도구, 검색 결과, 최종 답)를 남기고 👍/👎와 사유를 수집. 👎 건은 평가셋 후보로 적재해 회귀 테스트에 사용 |
| 지원 채널 | 처음부터 자동 응대하지 않고 **초안 제안 모드**(담당자에게만 보임, 승인 후 게시)로 시작. FAQ 키워드 매칭은 폴백으로만 쓰고, 채널 이력에서 반복 질문을 군집화해 후보 FAQ를 만들며, 신뢰도가 검증된 군집만 자동 응대로 승격 |

**초기 설계에서 우려되는 점**
- 키워드 기반 FAQ는 기존 도구 검색과 같은 한계(표현이 다르면 못 찾음)를 가진다.
- "서비스 성과 분석"처럼 SQL과 문서를 오가는 질문은 고정 순서로 처리하기 어려울 수 있다.

## 2. 뒤집힐 수 있는 핵심 가정

> **"질문이 어떤 소스를 어떤 순서로 볼지 개발자가 미리 정해둔 소수의 워크플로로 충분히 커버된다."**

- 맞으면: 라우터와 파이프라인 몇 개로 예측 가능하고 저렴하며 디버깅이 쉬운 서비스가 된다.
- 틀리면: 소스를 붙일 때마다 분기가 폭증한다. 도구 선택과 반복 검색을 모델이 하는 에이전트 루프 중심으로 설계를 바꿔야 하고, 비용, 지연, 평가 방식, 안전장치(단계 상한, 권한)도 모두 달라진다.

용어, 주소, 담당자 같은 단일 소스 질문은 고정 워크플로로 충분할 가능성이 높다. 불확실한 쪽은 성과 분석처럼 여러 소스를 조합하는 질문의 비중과 난이도다.

## 3. 가장 작은 실험

- **입력**
  - 최근 실제 질문 로그에서 유형별(용어, 회사 정보, 담당자, 프로젝트 설명, 성과 분석)로 층화 추출한 약 60건. 이전 대화 의존 질문 일부 포함.
  - 각 질문에 대해 해당 분야 담당자가 정답 요지와 정답 근거 소스를 라벨링.
  - 소스는 전부 붙이지 않고, 라벨링된 정답이 있는 상위 3~4개 소스만 연결.
- **비교 대상** (같은 도구, 같은 모델, 같은 프롬프트 예산)
  - A: 라우터 + 고정 워크플로(검색 → 요약 → 필요 시 재검색 → 답변)
  - B: 같은 도구를 주고 모델이 선택하는 에이전트 루프(최대 8단계)
- **사전에 정해두는 실패 기준** (실행 전에 확정)
  - A의 정답률이 B보다 10%p 이상 낮음(전체 또는 다중 소스 층 기준), **또는**
  - 라벨링 단계에서 20% 이상의 질문이 기존 워크플로 어디에도 배정되지 않음.
  - 보조 관찰: B의 평균 비용과 지연이 A의 3배를 넘는지 함께 기록.
- **해석 주의점.** 실패가 오케스트레이션 때문인지 검색 품질 때문인지 구분하려고, 실패 건에는 정답 문서를 직접 넣어 한 번 더 돌린다. 정답 문서를 줘도 A만 실패하면 오케스트레이션 문제로 본다.

60건은 작은 표본이라 방향을 보는 용도이고, 차이가 기준 근처이면 확정하지 않는다.

## 4. 구현 첫날

1. **질문 로그 확보와 분류** (오전). 최근 질문을 뽑아 유형별로 나누고, 현재 서비스가 답하지 못한 비율을 확인한다.
2. **평가셋 라벨링 의뢰** (오전). 유형별 담당자에게 정답 요지와 근거를 요청한다. 가장 오래 걸리므로 먼저 시작한다.
3. **도구 인터페이스 확정** (오후). 기존 SQL/메타데이터 검색과 위키, 포털 중 접근이 가장 쉬운 두 소스를 같은 형태로 래핑한다. 사용자 ID 전달과 트레이스 기록을 처음부터 넣는다.
4. **A/B 실행 하네스 골격** (오후). 같은 질문 파일을 두 방식에 흘려보내고 결과를 한 표로 모으는 스크립트. 채점은 라벨 기준 수동 또는 루브릭 기반으로 한다.
5. **병행 확인.** 메신저 소스의 접근 방식(API 범위, 채널 권한)을 조사해 둔다. 실험 결과와 무관하게 설계에 영향이 크다.

## 5. 실패했을 때의 조치

**직접 시도할 수 있는 것**
- 정답 문서 주입 실험으로 원인 분리(검색 vs 오케스트레이션)
- 라우터 분류 기준과 프롬프트 조정, 워크플로 분기 1~2개 추가 후 재측정
- 표본 확대와 라벨 재검토(라벨 오류 가능성)
- 하이브리드 구성: 단일 소스 질문은 고정 워크플로, 다중 소스 질문만 에이전트 루프로 처리
- B의 비용과 지연 절감(단계 상한, 캐시, 작은 모델로 도구 선택)

**사용자 결정이 필요한 조건**
- 에이전트 방식을 채택하면 비용과 지연이 허용 예산을 넘는 경우(허용 수준 결정)
- 정답률 기준(예: 10%p)이나 "충분히 좋은 답"의 기준 자체를 바꿔야 하는 경우
- 메신저, 비공개 문서를 검색 대상에 넣을 때 권한 모델상 노출 위험이 남는 경우(범위 제한 또는 제외 결정)
- 지원 채널을 초안 모드에서 자동 응대로 승격할 신뢰도 기준과 오답 시 책임 범위
- 라벨링에 담당자 시간을 추가로 써야 하는 경우

실험은 아직 실행하지 않았고, 위 수치(60건, 10%p, 20%, 3배)는 시작용 제안값이라 팀 상황에 맞게 조정하셔도 됩니다. 다만 실행 전에 확정해야 결과를 사후 합리화하지 않게 됩니다.
