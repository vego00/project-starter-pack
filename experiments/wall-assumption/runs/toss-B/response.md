# 초기 설계안과 구현 첫날 계획

현재 검토 중인 두 방법(임베딩 검색, 저장소 압축)은 모두 취약점 탐지에는 맞지 않을 가능성이 큽니다. 아래 설계는 이 판단에서 출발합니다. 실제 코드는 보지 못했고, 말씀하신 내용만 근거로 했습니다.

## 1. 두 방법에 대한 판단

- **임베딩 검색**: "비슷한 코드"를 가져오지만, 취약점에 필요한 것은 "연결된 코드"입니다. 입력 핸들러, 검증 함수, 권한 검사, 위험한 호출(sink)은 서로 유사하지 않은 파일에 흩어져 있습니다. 인덱싱과 청킹 비용도 서비스 수백 개에 곱해집니다.
- **저장소 압축**: 압축해도 컨텍스트에 들어가지 않는 규모이고, 줄이는 순간 취약점 판단에 필요한 세부 정보가 사라집니다. 긴 컨텍스트에서는 정확도도 떨어집니다.
- **대안**: 코드를 미리 가공해 넣는 대신, LLM이 보안 분석가처럼 진입점에서 출발해 필요한 코드를 도구로 직접 따라가게 합니다(grep, 파일 읽기, 정의/참조 조회). 외부 연구의 성공 사례도 대체로 이 에이전트형 구조에 가깝습니다.

## 2. 초기 아키텍처

1. **공격 표면 식별**: HTTP 라우트, RPC 핸들러, 큐 컨슈머 같은 진입점을 tree-sitter나 규칙으로 서비스별로 추출합니다.
2. **후보 좁히기**: Semgrep이나 ripgrep으로 위험한 호출(SQL, exec, 역직렬화, 파일 경로, 외부 요청)과 인증/인가 누락 패턴을 찾아 "진입점 → sink" 후보를 만듭니다. 이 단계는 LLM을 쓰지 않으므로 비용이 거의 들지 않습니다.
3. **에이전트 분석**: 후보 하나마다 LLM이 도구로 코드를 따라가며 취약 여부를 판단합니다. 결과에는 호출 경로와 근거 코드 위치를 반드시 포함시킵니다.
4. **검증**: 별도 호출로 반박을 시도하게 하고(오탐 줄이기), 가능하면 샌드박스에서 재현합니다. 마지막에는 사람이 확인합니다.
5. **평가 하네스**: 이미 알려진 취약점으로 재현율, 정밀도, 건당 비용을 측정합니다. 이것이 전체 설계의 기준이 됩니다.

범위를 줄이기 위해 처음에는 언어 1개, 서비스 2~3개, 취약점 유형 3~4개(인젝션, 인가 누락, SSRF, 경로 조작)로 제한합니다.

## 3. 구현 첫날

1. **정답 데이터 확보**: 과거 모의해킹, 버그바운티, 수정된 사내 취약점 중 10~20건을 모읍니다. 수정 직전 커밋, 취약 위치, 유형을 기록합니다. 서비스는 같은 언어로 2~3개를 고릅니다. 오늘 할 일 중 가장 중요합니다.
2. **최소 에이전트 작성**: 도구는 `grep`, `read_file`, `list_dir` 세 가지면 충분합니다. 벡터 DB나 파서는 아직 만들지 않습니다.
3. **한 건 돌려보기**: 취약점 1건에 대해 에이전트를 실행하고, 대화 기록을 읽으며 어디서 막히는지 확인합니다.
4. 시간이 남으면 아래 실험의 비교군(오라클 컨텍스트)을 준비합니다.

## 4. 뒤집히면 설계가 크게 바뀌는 가정

> **"에이전트가 grep과 파일 읽기만으로 스스로 필요한 코드를 모아 알려진 취약점을 찾을 수 있다. 사전 인덱스나 코드 그래프는 필수가 아니다."**

틀리면 CodeQL이나 호출 그래프 같은 정적 분석 인프라를 먼저 구축하는 방향으로 바뀝니다. 그보다 더 나쁜 경우는 근본적으로 모델의 판단 자체가 부족한 것이고, 이때는 자동 탐지가 아니라 리뷰어 보조 도구로 목표를 바꿔야 합니다.

## 5. 가장 작은 실험

**입력**
- 정답 취약점 10~20건(수정 전 커밋 체크아웃)
- 취약점마다 진입점 파일만 알려주고 "이 진입점에서 도달 가능한 취약점을 찾아라"라고 지시합니다.
- 공개 CVE는 모델이 이미 학습했을 수 있으므로 사내 취약점 위주로 고릅니다. 수정 커밋, 이슈 번호, 힌트가 되는 주석은 제거합니다.

**비교 대상** (같은 모델, 같은 토큰 예산)
- **A**: grep/read 도구를 쓰는 에이전트
- **B**: 임베딩 top-k 검색으로 컨텍스트를 채운 단발 호출 (현재 검토 중인 방식)
- **C**: 수정 diff에 나온 파일만 직접 넣어준 "이상적 컨텍스트" (상한선)

**실패 판단** (임계값은 제안이며 조정 가능합니다)
- **C가 절반 미만(<50%)을 찾음**: 컨텍스트가 아니라 모델의 판단력이 문제입니다. 검색 설계를 논의할 단계가 아닙니다.
- **A가 C의 절반 미만을 찾음**, 또는 **A가 B보다 낫지 않음**: 자율 탐색만으로는 부족하다는 뜻이므로 가정이 틀린 것입니다.
- **진입점당 비용이나 시간**이 전 서비스 확장 시 예산을 넘는 수준임.
- **진짜 취약점 1건당 오탐이 많아** 리뷰 인력이 감당할 수 없음. 예를 들어 20건 이상이면 실패로 봅니다.

실험이 10~20건이라 통계적으로 확정하기는 어렵습니다. 방향을 가르는 용도로만 해석해야 합니다.

## 6. 실패 시 조치

**제가 직접 시도할 수 있는 것**
- 프롬프트와 지시 방식 개선(취약점 유형별 분리, 체크리스트 제공)
- 도구 추가: ctags/tree-sitter 기반 정의·참조 조회, 호출 체인 요약
- 진입점에서 sink까지의 후보 경로를 정적으로 미리 계산해 힌트로 제공
- 여러 번 샘플링 후 합의, 단계 수 상한 조정
- 모델 변경, 컨텍스트 요약 방식 비교
- 실패 사례의 대화 기록을 분류해 원인을 "탐색 실패 / 판단 실패 / 도구 한계"로 정리

**사용자 결정이 필요한 조건**
- **소스코드를 외부 LLM API로 보내도 되는가?** 보안·법무 정책 문제이며, 안 된다면 자체 호스팅 모델로 전제가 바뀝니다. 실험 전에 확인하는 것이 좋습니다.
- 정답 데이터 접근 권한(모의해킹팀, 버그바운티 기록)과 대상 서비스 선정
- CodeQL 같은 상용 도구 라이선스, 추가 예산, 인력 투입
- 오라클(C)조차 실패했을 때 프로젝트 목표를 "자동 탐지"에서 "리뷰어 보조"로 바꿀지 여부
- 합격 기준 자체(재현율, 허용 오탐률, 건당 비용)의 확정

가장 먼저 필요한 답은 두 가지입니다. 정답 취약점 10건 이상을 모을 수 있는지, 그리고 코드를 외부 API에 보낼 수 있는지입니다.
