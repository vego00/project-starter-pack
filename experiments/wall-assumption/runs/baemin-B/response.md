# 초기 설계안 및 첫날 계획

## 1. 설계 방향 요약

주어진 초기 설계(고정 워크플로 + 키워드 FAQ)는 그대로 확장하면 두 가지 문제가 생길 가능성이 큽니다.

- 질문 유형이 열려 있어서(용어, 주소, 담당자, 프로젝트, 성과 분석) 고정 순서로는 분기가 폭증합니다.
- 키워드 FAQ는 각 도구 기본 검색의 한계(표현이 다르면 못 찾음)를 그대로 재현합니다.

그래서 아래 구조를 제안합니다.

**A. 라우터 + 소스별 도구를 가진 에이전트형 구조 (단, 범위를 제한)**
- 1단계: 질문 분류기 (데이터 조회 / 사내 지식 / 담당자·조직 / 분석 / 범위 밖). 기존 text-to-SQL 경로는 **그대로 유지**하고 하나의 도구로 취급합니다.
- 2단계: 사내 지식 질문은 LLM이 도구(소스별 검색, SQL 조회, 담당자 조회)를 골라 호출하는 반복 루프. 호출 횟수·시간 상한을 둡니다.
- 고정 워크플로는 "성과 분석"처럼 순서가 정해진 반복 업무에만 남깁니다.

**B. 지식 계층**
- 소스별 커넥터(포털, 위키, 이슈, 문서 저장소, 메신저)로 수집 → 공통 스키마(본문, 출처 URL, 수정일, 권한, 소스 유형)로 정규화 → 하이브리드 검색(키워드 + 임베딩) + 재순위.
- **권한 상속**: 원본 접근 권한을 검색 시점에 적용합니다. 메신저·비공개 문서 때문에 가장 위험한 부분입니다.
- 모든 답변에 출처 링크와 문서 수정일을 표시하고, 근거가 부족하면 "모르겠다"고 답합니다.

**C. 대화 맥락**
- 세션 단위 대화 기록 + 후속 질문을 독립 질문으로 다시 쓰는 단계. 장기 메모리는 1차에서 제외합니다.

**D. 개선 루프**
- 답변마다 👍/👎 + 사유(틀림/오래됨/출처 없음)를 수집하고, 질문·검색 결과·도구 호출 기록·답변을 함께 저장합니다.
- 👎 건을 평가셋으로 쌓아 변경 때마다 회귀 테스트합니다. 즉시 수정이 필요하면 "정정 답변" 등록(우선 검색되는 큐레이션 항목)을 지원합니다.

**E. 지원 채널 자동응대**
- 키워드 FAQ 대신, 과거 채널 스레드(질문 → 담당자 답변)를 검색해 답을 초안으로 만드는 방식.
- 1차는 **자동 게시가 아니라 제안 모드**(담당자에게만 보이는 초안 또는 "비슷한 과거 답변" 링크)로 시작하고, 채널별 정확도가 기준을 넘으면 자동 응대로 전환합니다.
- 담당자가 승인·수정한 답변은 다시 지식으로 환류합니다.

## 2. 구현 첫날 계획

목표: 설계 전체를 만들지 않고, 아래 가정을 가장 싸게 검증할 수 있는 상태까지 가기.

1. (1~2시간) 실제 질문 로그에서 최근 질문 약 100~200건을 뽑아 유형별로 분류하고, 소스별로 답이 어디 있는지 사람이 표시합니다. 이것이 평가셋 v0입니다.
2. (1시간) 각 소스의 API 접근, 권한 모델, 내보내기 가능 여부를 확인합니다. 메신저 수집 허용 여부는 이 시점에 보안/법무 확인 요청을 보냅니다(대기 시간이 길기 때문).
3. (2~3시간) 가장 쉬운 소스 1~2개(위키 + 문서 저장소)만 수집해 임베딩 + 키워드 하이브리드 검색을 붙이는 스크립트를 만듭니다.
4. (남은 시간) 아래 실험을 실행합니다.

## 3. 뒤집히면 설계가 크게 바뀌는 가정

**가정: "질문의 대다수는 한두 번의 검색(단일 소스 또는 하이브리드 검색 한 번)으로 근거를 찾을 수 있다."**

- 맞다면: 에이전트 루프 없이 "검색 한 번 → 답변"의 단순 RAG + 라우터로 충분하고, 고정 워크플로 확장도 가능합니다.
- 틀리다면(여러 소스를 조합하거나, 검색 결과를 보고 다음 검색을 정해야 하는 질문이 많다면): 반복 호출형 에이전트 구조, 도구 설계, 비용·지연 관리, 평가 방식이 모두 달라집니다. 이 가정이 틀렸을 때 비용이 가장 크기 때문에 이것을 고릅니다.

(참고: "메신저 데이터를 지식원으로 쓸 수 있다"는 가정도 설계를 크게 바꾸지만, 이것은 실험이 아니라 보안/법무 확인 사안이라 2번 항목에서 별도로 처리합니다.)

## 4. 가장 작은 실험

- **입력**: 평가셋 v0에서 뽑은 질문 50건(유형별 균형: 용어, 주소/조직, 담당자, 프로젝트, 성과 분석), 각 질문의 정답 근거 문서를 사람이 미리 표시. 수집된 소스(위키 + 문서 저장소)만 사용하고, 정답 근거가 그 소스에 있는 질문만 포함(없는 질문은 별도 "소스 부재" 표시).
- **비교 대상**:
  - (a) 검색 1회(하이브리드 top-k) → 답변
  - (b) 최대 4회까지 LLM이 검색을 반복·재작성하는 루프 → 답변
  - 기준선: 기존 도구 기본 키워드 검색의 top-5에 정답 문서가 있는 비율
- **측정**: 정답 근거 문서 포함률(retrieval hit@5), 사람이 채점한 답변 정확도, 호출 횟수·지연·비용.
- **실패 판단(= 가정이 틀림)**: (a)가 (b)보다 정확도가 10%p 이상 낮거나, 질문의 30% 이상에서 (a)의 top-5에 정답 근거가 없고 (b)에서는 찾아지는 경우. 즉, 단순 RAG로는 부족하고 반복 검색이 실질적으로 필요하다는 관찰입니다. (임계값은 임시이며 평가셋을 보고 조정합니다.)
- 반대로 (a)와 (b)가 비슷하면 가정이 유지되어 단순 구조로 갑니다. 둘 다 낮으면 가정이 아니라 수집·청킹·소스 커버리지 문제로 봅니다.

## 5. 실패 시 조치

**직접 시도할 조치 (사용자 결정 불필요)**
- 청킹 크기, 메타데이터(제목·경로·수정일) 포함 방식, 임베딩 모델, 재순위 추가, 질의 재작성 프롬프트 조정 후 재측정
- 루프 상한(호출 횟수), 도구 설명 개선, 소스 선택 힌트 추가 등 (b) 쪽 튜닝
- 평가셋 라벨 오류 점검, 채점 기준 보정
- 위키·문서 외 소스를 읽기 전용으로 추가 수집(이미 접근 권한이 확인된 범위 내)

**사용자 결정이 필요한 조건**
- (b)가 필요한 것으로 확인되어 지연·비용이 늘어나는 구조(응답 시간 목표 완화, 질문당 비용 상한)로 가야 할 때
- 정확도 개선에 메신저 등 민감 소스 수집이 필요하고, 보안/법무 승인이나 권한 정책(누구에게 무엇을 보여줄지)이 걸릴 때
- 외부 LLM/임베딩 API로 사내 문서를 보내야 하는 경우
- 평가 기준(허용 오답률, "모르겠다" 허용 비율)을 정해야 할 때
- 기존 워크플로 서비스를 병행 유지할지, 교체할지 일정과 인력을 정해야 할 때
- 지원 채널 자동 게시로 전환하는 정확도 기준과 채널 범위 확정
