# 초기 설계안과 구현 첫날 계획

## 1. 설계 방향: 임베딩 vs 전체 압축 — 둘 다 기본안으로 삼지 않는다

두 방법 모두 취약점 탐지에 약점이 있다.

- **임베딩 검색(RAG)**: 의미가 비슷한 코드를 찾아 주지만, 취약점은 "입력이 들어오는 곳(source) → 중간 처리 → 위험한 호출(sink)"처럼 **호출·데이터 흐름을 따라** 나타난다. 의미 유사도로는 이 흐름이 끊긴다. 인덱싱·갱신 인프라 비용도 크다.
- **저장소 전체 압축**: 압축해도 토큰이 크게 줄지 않거나, 줄이면 정작 필요한 세부가 사라진다. 컨텍스트가 길어질수록 중간 내용을 놓치고 비용이 급증한다. 수백 개 서비스에 반복하면 비용이 감당되지 않는다.

**제안: 에이전트형 탐색 + 정적 분석으로 좁히기.** LLM이 코드를 통째로 읽는 대신, 사람 보안 리뷰어처럼 grep·파일 열기·정의 찾기 도구로 필요한 부분만 따라가게 한다.

```
[서비스 저장소]
   │
   ├─ 1. 공격면 식별 (코드 기반, 저렴)
   │     라우트/핸들러/RPC/큐 소비자 등 외부 입력 진입점 목록화
   │     (정규식/tree-sitter, 또는 Semgrep/CodeQL 규칙)
   │
   ├─ 2. 후보 좁히기
   │     진입점별로 sink(SQL, exec, 파일, 역직렬화, SSRF, 인증 체크 누락 등) 도달 경로를 정적 도구로 추출
   │
   ├─ 3. LLM 에이전트 분석 (진입점/후보 단위로 작은 작업)
   │     도구: 파일 읽기, grep, 심볼 정의/참조 조회
   │     출력: 구조화된 findings (위치, 근거 경로, 공격 시나리오, 신뢰도)
   │
   ├─ 4. 검증
   │     두 번째 LLM 패스(반증 시도) + 가능하면 PoC/테스트 실행
   │
   └─ 5. 사람 리뷰 큐 + 피드백 저장 (오탐/미탐 라벨 → 평가셋으로 축적)
```

핵심 원칙:
1. **분석 단위를 "저장소"가 아니라 "진입점 하나 + 그 호출 체인"으로 쪼갠다.** 컨텍스트 한계 문제가 구조적으로 사라진다.
2. **LLM은 판단에, 결정적 도구는 탐색에.** 코드 검색·호출 그래프는 도구가 하고, LLM은 "이 경로가 실제로 악용 가능한가"를 판단한다.
3. **평가셋을 먼저 만든다.** 방식 비교는 감이 아니라 측정으로 한다. 자원이 한정된 팀에게 가장 중요한 투자다.
4. **서비스 하나로 시작**하고, 수백 개로의 확장(비용, 병렬화, 언어별 차이)은 효과가 확인된 뒤에 한다.

## 2. 구현 첫날 할 일

목표: 오늘 안에 "정답을 아는 문제"와 "가장 단순한 기준선"을 확보한다.

1. **대상 서비스 1~2개 선정** (언어 하나, 중간 규모, 과거 취약점 이력이 있는 것). 보안 티켓·버그바운티·모의해킹 보고서에서 **확인된 취약점 10~20건**을 모아 위치(파일/함수)와 함께 기록한다. 이것이 정답지다. 취약점이 수정되기 *전* 커밋을 체크아웃해 사용한다.
2. **데이터 취급 확인**: 소스코드를 어떤 모델/엔드포인트로 보낼 수 있는지(사내 승인된 API, 데이터 보관 정책)를 확인한다. 막히면 나머지가 전부 막힌다.
3. **기준선 구축(반나절)**: 진입점 하나를 골라, 그 핸들러와 호출하는 함수 몇 개를 직접 붙여 넣어 LLM에 분석시킨다. 에이전트 구조 없이 수동으로 돌려 보며 결과 품질과 토큰 규모를 감 잡는다.
4. **비교 대상 기준선**: 같은 서비스에 Semgrep 등 기존 SAST를 돌려 결과를 저장한다. LLM이 이걸 못 넘으면 가치가 없다.
5. 기록 형식(findings 스키마, 실행 로그)을 정한다.

## 3. 설계를 뒤집을 수 있는 핵심 가정

**가정: "취약점 탐지에 필요한 코드는 진입점에서 출발한 호출 체인을 따라 모으면 대부분 확보된다(즉, 국소적 컨텍스트로 충분하다)."**

이 가정이 틀리면 — 예컨대 실제 취약점이 서비스 간 호출, 전역 설정·미들웨어의 인증 처리, 여러 모듈에 흩어진 비즈니스 로직 상태에 의존한다면 — 진입점 단위 분할이 핵심 문맥을 잘라 버린다. 그러면 설계를 전역 인덱스(코드 그래프)·서비스 간 모델링 중심으로 크게 바꿔야 한다.

## 4. 가장 작은 실험

- **입력**: 첫날 모은 알려진 취약점 중 10~20건. 각 취약점마다 (a) 취약점이 있는 핸들러에서 시작해 (b) 에이전트가 도구로 코드를 따라가도록 한다. 취약점 위치는 알려 주지 않고, 진입점만 준다. 수정 전 커밋 기준.
- **추가 조사(근거 분류)**: 각 취약점에 대해 사람이 "이 취약점을 판단하는 데 필요한 코드가 호출 체인 안에 있는가, 밖(미들웨어, 설정, 다른 서비스)에 있는가"를 먼저 표시해 둔다.
- **비교 대상**:
  - A: 진입점+호출 체인 방식 (제안안)
  - B: 사람이 필요한 파일을 모두 골라 준 "오라클 컨텍스트" (상한선)
  - C: Semgrep 기준선
  - 임베딩 검색은 여력이 있을 때만 D로 추가해, 정말 필요한지 검증한다.
- **실패로 판단할 관찰 결과**:
  - A가 찾은 비율이 B보다 크게 낮고(예: 절반 이하), 놓친 건의 다수가 "체인 밖에 필요한 코드가 있었던" 경우로 분류될 때 → 국소 컨텍스트 가정 실패.
  - 또는 A와 B 모두 Semgrep(C)보다 재현율이 나쁘거나, 같은 수준이면서 오탐이 감당할 수 없이 많을 때 → 접근 자체의 가치 재검토.
  - 기준 숫자는 표본이 작으므로 실험 전에 먼저 합의해 두고, 결과를 본 뒤 바꾸지 않는다.

## 5. 실패했을 때: 직접 시도할 조치 vs 사용자 결정이 필요한 조건

**제가(또는 팀이) 바로 시도할 수 있는 조치**
- 체인 밖 코드가 원인이면: 미들웨어·인증 설정·공통 라이브러리를 항상 컨텍스트에 포함하는 "서비스 공통 요약"을 추가하고 재실험.
- 호출 체인 추출이 부정확하면: 심볼 조회 도구를 개선(tree-sitter, LSP, CodeQL DB)하고 재실험.
- 프롬프트·출력 스키마 조정, 반증 패스 추가, 모델 교체 후 재측정.
- 임베딩 검색을 보조 도구(에이전트가 부를 수 있는 검색 도구)로 추가해 개선되는지 확인.

**사용자(보안 연구 담당자) 결정이 필요한 조건**
- 소스코드를 외부 API로 보낼 수 없어 사내 호스팅 모델로 바꿔야 할 때(성능·비용·인력 영향).
- 서비스 간 취약점이 많아 **전역 코드 그래프 구축**처럼 투자가 큰 방향 전환이 필요할 때.
- 정답지가 부족해 새로 모의해킹·수동 리뷰 비용을 써야 할 때.
- 오탐률이 높아 사람 리뷰 부담이 감당 안 될 때, 허용 오탐 수준·탐지 대상 취약점 유형을 어디까지로 좁힐지.
- 실험 결과 기준선(Semgrep) 대비 이점이 작을 때, 프로젝트를 계속할지·범위를 줄일지(예: 인증/인가 로직 결함처럼 SAST가 약한 유형만).
- 실제 서비스 대상으로 PoC를 실행해야 할 때의 안전·승인 범위.
