# 초기 설계안과 구현 첫날 계획

## 1. 검토 중인 두 방법에 대한 판단

| 방법 | 문제 |
|---|---|
| 임베딩 검색(RAG) | 취약점은 "입력이 들어오는 곳 → 검증/변환 → 위험한 호출"로 이어지는 파일 간 흐름에서 생깁니다. 의미가 비슷한 코드를 찾는 임베딩은 이 흐름을 따라가는 데 약합니다. 단독으로 쓰면 sink만 보이고 source나 sanitizer는 빠지기 쉽습니다. |
| 저장소 전체 압축 | 압축해도 토큰 수가 크게 줄지 않습니다. 줄이면 정보가 손실되고, 줄이지 않으면 컨텍스트에 들어가지 않습니다. 긴 컨텍스트에서는 정밀도도 떨어집니다. 수백 개 서비스를 돌릴 때 비용도 문제입니다. |

두 방법 모두 "어떤 코드를 볼지"를 사전에 정해 두는 방식입니다. 제가 권하는 방향은 에이전트가 도구로 코드를 직접 탐색하게 하고, 임베딩은 보조 도구로만 두는 것입니다.

## 2. 초기 설계안 (파이프라인)

1. **인벤토리**: 서비스별 언어, 프레임워크, 크기(LOC와 토큰), 외부 노출 여부를 수집합니다.
2. **진입점과 위험 지점 추출**: 라우트, 핸들러, 메시지 컨슈머 같은 진입점과 SQL, exec, 역직렬화, 파일 접근, 인증/인가 체크 같은 위험 지점을 Semgrep이나 CodeQL, 단순 grep/AST로 뽑습니다. 이것이 "전체를 넣을 수 없다"는 제약에 대한 1차 답입니다. 서비스 전체가 아니라 후보 단위로 쪼갭니다.
3. **후보별 에이전트 분석**: 후보 하나(예: 핸들러 하나)마다 LLM 에이전트가 grep, 파일 읽기, 정의/참조 조회 도구로 source→sink 경로를 추적합니다. 컨텍스트는 후보당 수십 K 토큰 이내로 제한합니다. 임베딩 검색은 "비슷한 패턴 찾기" 도구로만 추가합니다.
4. **검증 단계**: 별도의 호출이나 모델이 "공격자가 도달 가능한가, 검증이 실제로 없는가"를 반박하는 관점에서 재검토합니다. 가능하면 재현용 요청이나 테스트를 생성하고, 격리 환경에서 실행하는 것은 후순위로 둡니다.
5. **보고와 피드백**: 근거 경로(파일:줄), 심각도, 신뢰도를 구조화해 출력합니다. 담당자의 판정(진짜/오탐/중복)을 저장해 평가 데이터로 재사용합니다.

설계 원칙은 세 가지입니다.
- 정적 분석기를 대체하지 않고 결합합니다.
- 모든 단계의 입출력을 로그로 남깁니다.
- 처음에는 취약점 유형을 3~4개(인젝션, 인증/인가 누락, SSRF, 경로 조작 등)로 좁힙니다.

## 3. 구현 첫날 할 일

1. **파일럿 대상 선정**: 언어와 프레임워크가 다른 서비스 2~3개를 고릅니다. 크기가 중간 정도이고 과거 취약점 이력이 있는 서비스가 좋습니다.
2. **정답 데이터 수집**: 과거 모의해킹, 버그바운티, 취약점 수정 커밋에서 알려진 취약점 15~20개를 모읍니다. 수정 직전 커밋을 체크아웃할 수 있어야 합니다. 안전한 것으로 확인된 유사 코드도 몇 개 함께 모읍니다.
3. **각 취약점의 최소 증거 슬라이스 기록**: source→sink 경로에 있는 파일과 함수를 사람이 표시합니다. 이 작업이 가장 중요하고 시간이 걸립니다.
4. **하네스 구성**: 코드 체크아웃, 모델 호출, 결과 저장, 정답 대조를 하는 최소 스크립트를 만듭니다. 모델 버전과 프롬프트는 고정합니다.
5. **데이터 반출 정책 확인**: 소스코드를 어떤 LLM 엔드포인트로 보낼 수 있는지 확인합니다. 이 항목은 아래 사용자 결정 사항입니다.

## 4. 틀리면 설계가 크게 바뀌는 가정 하나

> **"후보 단위의 국소 컨텍스트(진입점에서 sink까지의 경로에 있는 일부 파일)만 모아도 LLM이 취약 여부를 판단할 수 있고, 에이전트가 그 컨텍스트를 스스로 모을 수 있다."**

- 틀리면, 즉 판단에 서비스 전체나 여러 서비스에 걸친 이해가 필요하면, 후보 분할 구조 자체를 버리고 서비스 단위 요약이나 코드 그래프 같은 다른 구조로 가야 합니다.
- 맞다면 이후 작업은 정밀도 개선과 확장 문제가 됩니다.

## 5. 가장 작은 실험

**입력**: 위 정답 세트(알려진 취약점 15~20개와 안전 코드 몇 개)입니다. 수정 전 커밋 상태의 코드와 "이 핸들러를 분석하라"는 후보 지정만 줍니다. 취약점 설명은 주지 않습니다.

**비교 대상** (같은 모델, 같은 프롬프트 골격):
- **A. 상한선**: 사람이 표시한 최소 증거 슬라이스만 직접 입력합니다. 컨텍스트만 충분하면 LLM이 판단할 수 있는지를 봅니다.
- **B. 에이전트 탐색**: 진입점만 주고 grep, 파일 읽기, 참조 조회 도구로 스스로 탐색하게 합니다.
- **C. 임베딩 top-k**: 후보 코드를 질의로 하여 상위 k개 조각만 줍니다. 현재 검토 중인 방식의 기준선입니다.
- **D. (선택) Semgrep/CodeQL 기본 규칙**: 기존 도구 대비 가치를 확인합니다.

**실패로 판단할 관찰 결과** (수치는 제안이며 조정 가능합니다):
- A에서도 탐지율이 낮으면(예: 절반 미만), 국소 컨텍스트로 충분하다는 가정이나 모델의 판단 능력 자체가 문제입니다.
- A는 탐지하는데 B가 A의 절반 이하만 탐지하고, 놓친 사례의 로그에서 B가 증거 슬라이스의 source나 sink 파일을 열어 보지 못했다면, 에이전트의 컨텍스트 수집이 실패한 것입니다.
- B가 C보다 뚜렷하게 낫지 않으면(탐지 건수 차이가 1~2건 이내), 에이전트 방식의 추가 비용을 정당화하기 어렵습니다.
- 안전 코드에서 오탐이 많아 진짜 발견 1건당 사람이 확인해야 하는 후보가 지나치게 많으면(예: 10건 초과), 운영이 불가능합니다.

표본이 작아 통계적 결론은 아니고, 설계 방향을 가르는 신호로만 쓸 수 있습니다.

## 6. 실패했을 때: 직접 시도할 조치 vs 사용자 결정 필요 조건

**제가 직접 시도할 수 있는 조치** (추가 승인 없이 파일럿 범위 안에서):
- 도구 보강: 정의/참조 조회, 호출 그래프, CodeQL 결과를 에이전트에 제공합니다.
- 프롬프트 개선: source→sink 추적 절차를 명시하고 체크리스트를 추가합니다.
- 후보 분할 단위를 조정하고(핸들러, 모듈, 기능), 탐색 단계 수 상한을 바꿉니다.
- 검증 단계 추가나 강화, 출력 형식 조정을 합니다.
- 실패 사례를 유형별로 분류해(컨텍스트 미수집, 판단 오류, 프레임워크 암묵 동작 등) 원인을 보고합니다.
- 취약점 유형을 더 좁혀 재실험합니다.

**사용자 결정이 필요한 조건**:
- 소스코드를 외부 LLM API로 보낼 수 있는지, 아니면 사내 호스팅 모델만 써야 하는지 (데이터 정책, 모델 선택)
- 비용이나 토큰 예산 상한을 올려야 할 때
- 정답 데이터에 쓸 과거 취약점 정보에 접근할 권한이 필요할 때
- 합격 기준(탐지율, 허용 오탐률)을 낮추거나 정하는 일
- 목표를 바꿔야 할 때: 예를 들어 "자동 발견"에서 "정적 분석 결과 선별 보조"로 축소하거나, 서비스와 취약점 유형 범위를 줄이는 결정
- A조차 실패해 모델 능력 한계로 판단될 때, 프로젝트를 중단할지, 모델 업그레이드나 파인튜닝에 투자할지의 결정
- 실제 서비스에 동적 검증(재현 요청 실행)을 허용할지, 허용한다면 어떤 환경에서 할지
- 인력이나 일정 연장

원하시면 다음 단계로 정답 데이터 수집 양식과 하네스 스크립트의 뼈대를 만들어 드리겠습니다.
