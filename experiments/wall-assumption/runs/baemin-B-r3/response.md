# 초기 설계안

## 1. 설계 원칙

제시하신 초기 설계(고정 워크플로 + FAQ 키워드 자동응답)는 출발점으로는 안전하지만, 목표와 어긋나는 지점이 있습니다.

- 질문 유형이 열려 있어(용어, 주소, 담당자, 프로젝트, 성과 분석) 고정 순서로는 분기가 폭증합니다. 소스를 하나 붙일 때마다 워크플로를 고쳐야 합니다.
- 키워드 FAQ는 도구 기본 검색과 같은 한계(표현이 다르면 못 찾음)를 그대로 가집니다.
- "불만족 답변을 바로 개선"하려면 답이 어떤 근거로 나왔는지 추적되어야 합니다.

그래서 아래와 같이 제안합니다.

## 2. 구조

1. **라우터(질문 분류)**: 데이터 조회 / 사내 지식 / 담당자·조직 / 성과 분석 / 범위 밖. 확신이 낮으면 되묻기.
2. **에이전트 루프(소스별 도구 호출)**: 고정 순서 대신, 모델이 소스별 검색 도구(SQL, 위키, 이슈, 메신저, 문서, 포털)를 필요에 따라 고르고 반복 호출합니다. 단, 도구 집합·최대 호출 횟수·권한은 개발자가 제한합니다. 기존 SQL 워크플로는 하나의 도구로 감쌉니다.
3. **통합 검색 계층**: 소스별 커넥터가 문서를 공통 스키마(제목, 본문, 출처 URL, 수정일, 접근권한, 소유자)로 색인. 키워드 + 임베딩 하이브리드 검색, 접근권한 필터는 검색 단계에서 적용.
4. **대화 메모리**: 세션 내 히스토리 + 사용자별 요약. 질문 재작성(후속 질문을 독립 질문으로)으로 검색에 반영.
5. **답변 규칙**: 출처 링크 필수, 근거 없으면 "찾지 못함"과 담당 문의처 안내, 오래된 문서는 수정일 표기.
6. **피드백 루프**: 답변마다 👍/👎 + 사유, 질문·검색 결과·도구 호출 trace·답변을 저장. 👎는 리뷰 큐로 가서 "소스 누락 / 검색 실패 / 문서 오류 / 생성 오류"로 분류. 이를 평가셋에 누적.
7. **지원 채널 응대(단계적)**:
   - 1단계: 그림자 모드. 채널 질문을 읽고 답 초안만 만들어 담당자에게 비공개 제시(자동 게시 안 함).
   - 2단계: 과거 스레드(질문→담당자 답변)를 색인해 유사 질문 검색, 신뢰도 높고 위험이 낮은 유형만 자동 응답.
   - 모든 자동 응답에 "틀리면 담당자 호출" 버튼.

## 3. 구현 첫날 제안

코드보다 **현실 데이터 확인**부터 합니다.

1. (오전) 최근 몇 주간의 실제 질문 로그에서 약 100~200건을 뽑아 유형별로 분류: 데이터 조회, 용어, 담당자, 프로젝트, 성과 분석, 기타. 어느 소스에서 답이 나와야 하는지 정답 소스를 표기.
2. (오전) 지원 채널 중 문의량 상위 5~10개를 골라, 최근 스레드 중 "질문 → 담당자 답변" 쌍을 수십 건 추출(권한·개인정보 점검 포함).
3. (오후) 가장 접근이 쉬운 소스 2개(예: 위키, 메신저 지원 채널)의 커넥터 스파이크: 권한 모델과 API 제한 확인.
4. (오후) 위 질문 샘플로 가장 작은 실험(아래)을 돌립니다.

## 4. 설계를 크게 바꿀 수 있는 가정 하나

**가정: "반복되는 지원 채널 질문은 과거 담당자 답변을 의미 검색해 재사용하면 충분히 정확히 응대할 수 있다."**

틀리면 2단계 자동응답 설계가 무너집니다. 답이 시점·개인 상황·진행 중 이슈에 의존한다면, 과거 답변 재사용이 아니라 현재 상태를 조회하는 도구(이슈 상태, 데이터, 담당 로스터)를 중심으로 재설계하고, 자동 응답은 안내/라우팅 중심으로 축소해야 합니다. 또한 라이브 소스 중심으로 바뀌면 색인 계층 비중이 줄어듭니다.

## 5. 가장 작은 실험

- **입력**: 상위 지원 채널 5~10개에서 최근 3개월 스레드의 질문 100건(과거 담당자 답변이 있는 것). 시간순으로 나눠 앞 80%의 스레드를 색인하고, 뒤 20% 이상의 질문을 테스트로 사용(미래 정보 누출 방지). 정답은 해당 스레드의 담당자 답변.
- **비교 대상**:
  - A: 현재 계획의 키워드 FAQ 매칭(질문–답 쌍 키워드 검색)
  - B: 과거 스레드 임베딩+키워드 하이브리드 검색 후 답 초안 생성
  - 기준: 담당자 답변을 정답으로 한 담당자(또는 팀원 2명)의 블라인드 채점(정답 / 부분 정답 / 오답 / 시점 의존으로 재사용 불가).
- **실패 판단 관찰 결과** (실험 전에 확정해 두는 임계값 제안):
  - B에서 "정답"으로 판정된 비율이 낮아 자동 응답 후보(신뢰도 상위 구간)에서도 오답이 약 5% 이상 나온다.
  - 또는 테스트 질문의 상당수(예: 40% 이상)가 "시점 의존/개인 상황 의존으로 재사용 불가"로 채점된다.
  - 또는 B가 A에 비해 정답률 개선이 미미하다(예: 10%p 미만). 이 경우 복잡도를 정당화하지 못합니다.

(임계값은 제 제안이며, 채널의 위험도에 따라 조정해야 합니다.)

## 6. 실패 시 조치

**직접 시도할 수 있는 조치(사용자 결정 불필요)**
- 청킹 단위 변경(스레드 전체 vs 질문–답 쌍), 검색 파라미터 조정, 질문 재작성 추가, 재순위화 적용.
- 채널·유형별로 쪼개 결과 확인, 성공하는 유형(예: 권한 신청 절차, 정책 안내)만 따로 평가.
- 오래된 스레드 제외, 최신 답변 가중치 적용.
- 실패 사례를 원인(검색 실패 vs 생성 오류 vs 재사용 불가)으로 분류해 보고.
- 현재 상태 조회 도구(이슈/로스터) 후보를 추가해 같은 샘플로 재측정.

**사용자 결정이 필요한 조건**
- 자동 게시 범위를 "일부 유형만"으로 축소하거나 안내/라우팅 전용으로 바꾸는 결정(제품 범위·위험 허용도).
- 오답 허용 기준(예: 5%)을 완화하는 결정.
- 메신저 대화를 색인·평가에 쓰는 데 대한 개인정보·보안·채널 소유자 동의, 추가 권한 요청.
- 평가 채점에 담당자 시간을 더 투입하는 결정, 외부 모델/벤더 사용 변경에 따른 비용·데이터 반출 판단.
- 라이브 상태 조회 중심으로 아키텍처를 바꿔 로드맵·인력을 재배분하는 결정.

## 7. 정리

- 고정 워크플로는 SQL 같은 검증된 경로에만 남기고, 나머지는 제한된 도구를 쓰는 에이전트 루프로 확장합니다.
- 첫날은 실제 질문·스레드 샘플링과 실험으로 위 가정을 먼저 검증합니다.
- 결과에 따라 지원 채널 자동응답의 범위(전면 / 유형 한정 / 초안·라우팅만)를 결정합니다.
