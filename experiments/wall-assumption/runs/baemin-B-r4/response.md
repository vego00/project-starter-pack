# 초기 설계안과 구현 첫날 제안

## 1. 초기 설계 (요구 기준으로 다시 짠 것)

주어진 초기 설계(고정 워크플로 + 키워드 FAQ)는 출발점으로는 유효하지만, 목표 4개 중 두 개(이전 대화 이어가기, 즉시 개선)와 질문 범위 확장에 약합니다. 그래서 다음처럼 잡습니다.

**구조: 라우터 + 소스별 검색 도구 + 제한된 에이전트 루프**

1. **질문 분류/라우팅**: 데이터 조회(기존 text-to-SQL 경로), 사내 지식(용어·주소·담당자·프로젝트), 성과 분석(SQL + 문서 결합), 지원 채널 문의로 나눕니다. 기존 SQL 경로는 그대로 두고 앞단에만 분기를 둡니다.
2. **지식 소스 커넥터**: 포털, 위키, 이슈 도구, 메신저, 문서 저장소를 각각 같은 형태(문서 조각 + 출처 + 권한 + 수정일)로 색인합니다. 키워드와 임베딩을 함께 쓰는 하이브리드 검색을 사용합니다.
3. **답변 생성**: 개발자가 정한 고정 순서 대신, 소스 도구를 호출하는 에이전트 루프를 쓰되 단계 수·도구 집합을 제한합니다. 모든 답에 출처 링크를 붙이고, 근거가 없으면 모른다고 답합니다.
4. **대화 기억**: 세션 내 대화 이력을 질문 재작성(대명사·생략 해소)에 사용합니다. 장기 기억은 일단 만들지 않습니다.
5. **피드백 루프**: 답변마다 👍/👎와 사유를 저장하고, 질문·검색 결과·최종 답·출처를 로그로 남깁니다. 👎 사례는 평가 세트로 쌓이고, 담당자가 정답 문서나 교정 답을 지정하면 다음 검색에 반영됩니다.
6. **지원 채널 응대**: FAQ 키워드 매칭 대신, 과거 채널 스레드(질문 → 담당자 답변)를 색인해 유사 질문을 찾고, 확신도가 높을 때만 답하며 낮으면 담당자에게 넘깁니다. 초기에는 자동 게시가 아니라 담당자에게 초안 제안으로 운영합니다.
7. **권한**: 질문자 권한으로 검색 결과를 필터링합니다. 비공개 채널과 문서가 섞이므로 이 부분은 설계 초기에 정해야 합니다.

## 2. 틀리면 설계를 크게 바꿔야 하는 가정

**가정: 지원 채널의 과거 스레드(질문 → 담당자 답변)에서 유사 질문을 검색하면, 사람이 검수 없이도 쓸 만한 답을 충분한 비율로 찾을 수 있다.**

이 가정이 맞으면 FAQ를 미리 등록하는 대신 스레드 기반 검색으로 간다. 틀리면(스레드 답이 맥락 의존적이거나 오래되어 재사용이 안 되면) 지원 채널은 자동 응대가 아니라 "담당자 보조 초안" 또는 FAQ 큐레이션 파이프라인으로 설계를 바꿔야 하고, 메신저 색인 전체의 가치도 재평가해야 합니다.

## 3. 가장 작은 실험

- **입력**: 지원 채널 5~10개(질문량 상위)에서 최근 3~6개월 스레드. 시간순으로 앞 80%를 색인하고, 뒤 20%에서 질문 약 100~200건을 샘플링해 테스트 질문으로 씁니다. 비공개 내용은 마스킹하거나 데이터팀이 접근 가능한 채널로 한정합니다.
- **비교 대상**:
  - A: 현재 계획의 키워드 FAQ 방식(상위 반복 질문 일부를 FAQ로 등록해 키워드 매칭)
  - B: 스레드 색인 + 하이브리드 검색으로 과거 답변을 찾아 답 생성
  - 기준선: 실제 담당자가 단 답변
- **판정 방법**: 담당자 2명이 각 응답을 "그대로 게시 가능 / 수정 필요 / 틀림"으로 블라인드 채점합니다. "틀림"은 잘못된 정보나 오래된 안내를 포함한 경우입니다.
- **실패로 판단할 관찰 결과** (실험 전에 확정해 둘 임계값 예시):
  - B의 "그대로 게시 가능" 비율이 약 30% 미만이거나 A와 의미 있는 차이가 없음
  - 또는 B가 확신도 높다고 낸 답 중 "틀림"이 5~10%를 넘음 (확신도로 걸러지지 않음)
  - 또는 정답 스레드가 존재하는데도 상위 5개 검색 결과에 못 찾는 비율이 높음

임계값은 제 추정이므로 담당자와 합의해 조정해야 합니다.

## 4. 실패 시 조치

**직접 시도할 것 (사용자 결정 불필요)**
- 청킹 단위를 메시지 단위에서 스레드 단위로 바꾸기, 질문 재작성, 하이브리드 가중치·리랭커 조정
- 오래된 스레드 감점, 담당자 답변만 색인하는 등 필터 변경
- 확신도 임계값 상향, 스레드를 요약해 "질문–답" 쌍으로 정제한 뒤 색인
- 실패 사례를 원인별로 분류(검색 실패 / 답이 맥락 의존 / 답이 낡음 / 생성 오류)해 보고

**사용자(데이터팀·채널 담당자) 결정이 필요한 조건**
- 원인이 데이터 자체의 한계(답이 맥락 의존적이거나 낡음)로 판명되어, 위 조정 후에도 임계값 미달일 때 → 자동 응대 포기 후 "담당자 초안 보조"나 FAQ 큐레이션으로 범위 변경할지
- 비공개 채널 스레드 접근 또는 메신저 데이터 사용 승인이 필요할 때
- 임계값 자체(허용 오답률)를 완화해야 할 때
- 담당자 채점 인력을 추가로 요청해야 할 때

## 5. 구현 첫날 할 일

1. **오전: 범위·접근 확인**: 실험 대상 채널 목록, 메신저 API/내보내기 접근 권한, 데이터 사용 승인 여부를 확인합니다. 막히면 가장 먼저 사용자에게 올릴 항목입니다.
2. **오전: 데이터 추출**: 선택한 채널의 스레드를 추출해 질문–답변 구조로 정리하고, 시간순 분할로 테스트 세트를 고정합니다. 이 세트는 이후 모든 변경의 회귀 평가 세트가 됩니다.
3. **오후: 기준선(A) 구축**: 키워드 매칭 FAQ를 빠르게 만들어 기준선 점수를 얻습니다.
4. **오후: 방식 B의 최소 구현**: 스레드 색인과 하이브리드 검색만 붙이고, 생성 단계는 상위 결과를 그대로 보여 주는 수준으로 시작해 "검색이 정답 스레드를 찾는가"부터 확인합니다.
5. **하루 끝**: 채점 시트(질문, A·B 응답, 담당자 실제 답, 3단계 채점란)를 만들어 담당자에게 넘길 준비를 합니다.

기존 SQL 경로 수정, 다른 지식 소스 커넥터, 장기 기억은 이 실험 결과가 나오기 전에는 착수하지 않습니다.
