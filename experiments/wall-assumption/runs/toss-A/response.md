# 초기 설계안: LLM 기반 소스코드 취약점 분석 자동화

## 1. 검토 중인 두 방식에 대한 판단

| 방식 | 문제 |
|---|---|
| **임베딩 + 검색(RAG)** | 취약점은 "입력이 들어와서 위험한 함수까지 가는 흐름"이라 여러 파일에 걸쳐 있습니다. 의미 유사도 검색은 비슷한 코드를 찾을 뿐 호출 흐름을 따라가지 못합니다. 청킹, 인덱싱, 코드 변경 시 재색인 같은 운영 부담도 큽니다. |
| **저장소 전체를 압축해 투입** | 큰 서비스는 압축해도 컨텍스트에 들어가지 않습니다. 들어가더라도 긴 컨텍스트에서는 정확도가 떨어지고, 수백 개 서비스에 반복하면 비용이 큽니다. |

두 방식 모두 "LLM에게 무엇을 줄지 사람이 미리 정한다"는 전제입니다. 대신 **LLM이 grep, 파일 읽기, 정의 찾기 같은 도구로 직접 코드를 탐색하는 에이전트 방식**을 기본으로 하길 권합니다. 사람 연구자가 코드를 읽는 방식과 같고, 외부 연구에서 성과를 낸 방식도 대체로 이쪽입니다. 임베딩은 나중에 필요하면 보조 도구로 추가하면 되고, 처음부터 투자할 필요는 없습니다.

## 2. 전체 파이프라인

```
[0 서비스 우선순위] → [1 공격 표면 지도] → [2 진입점별 에이전트 분석]
                                              → [3 검증/반박] → [4 중복 제거·리포트·사람 리뷰]
                                                                        ↓ 피드백
```

**0. 서비스 우선순위화**
- 수백 개를 한꺼번에 돌리지 않습니다.
- 외부 노출 여부, 인증/결제/개인정보 취급 여부, 언어와 프레임워크로 점수를 매겨 상위 몇 개부터 시작합니다.

**1. 공격 표면 지도 (저장소를 쪼개는 기준)**
- 코드를 크기로 나누지 않고 **진입점(HTTP 라우트, RPC 핸들러, 메시지 컨슈머, 파일 파서 등)** 으로 나눕니다.
- ctags, tree-sitter, Semgrep 같은 기존 도구로 진입점 목록과 파일 트리, 시그니처 요약("repo map")을 만듭니다. 이 요약은 에이전트가 길을 잃지 않게 하는 용도이며, 전체를 압축해 넣는 방식의 좋은 부분만 취한 것입니다.

**2. 진입점별 에이전트 분석**
- 에이전트 하나가 진입점 하나를 맡습니다. 입력이 어디서 들어와 어떤 sink(쿼리, 명령 실행, 역직렬화, 파일 경로, 외부 요청 등)에 닿는지 도구로 따라가게 합니다.
- 도구는 `grep`, `read_file(범위 지정)`, `list_dir`, 정의/참조 찾기 정도로 최소화합니다.
- 토큰, 시간, 도구 호출 횟수에 상한을 둡니다.
- 출력은 구조화된 JSON(가설, 근거 파일·라인, 입력부터 sink까지의 경로, 확신도)으로 받습니다.
- CodeQL이나 Semgrep 결과가 있으면 힌트로만 제공합니다. 없어도 동작해야 합니다.

**3. 검증 (오탐 억제의 핵심)**
- 별도 에이전트가 발견 내용을 반박해 보게 합니다. 이 경로에 인증이나 검증이 있는지, 실제로 도달 가능한지 확인합니다.
- 가능하면 격리된 환경에서 재현(PoC)까지 시도합니다. 이 단계는 처음에는 생략하고 2단계로 미뤄도 됩니다.

**4. 리포트와 사람 리뷰**
- 중복을 제거하고 심각도를 매겨 담당 연구자가 판정합니다. 판정 결과(TP/FP와 사유)를 반드시 기록해 평가 데이터와 프롬프트 개선에 씁니다.

## 3. 안전, 보안 제약 (초기에 정해 둘 것)
- 에이전트 실행 환경은 **읽기 전용 소스, 네트워크 차단, 사내 시크릿 미노출** 샌드박스로 합니다. 코드 속 주석이나 문자열에 의한 프롬프트 인젝션을 전제로 합니다.
- 소스코드를 외부 모델 API에 보내도 되는지, 보관과 학습 이용 조건이 어떤지를 보안·법무와 먼저 확인합니다.
- 모든 도구 호출과 결과를 로그로 남겨 나중에 재현하고 비용을 분석할 수 있게 합니다.

## 4. 평가 방식 (자원이 한정될수록 중요)
- **정답 있는 평가셋**을 먼저 만듭니다. 사내 과거 취약점 리포트와 패치 이력을 쓰고, 부족하면 공개 CVE를 사내와 비슷한 스택에서 가져옵니다.
- 지표는 재현율(known bug를 찾는가), 정밀도(사람이 볼 가치가 있는 비율), **유효 발견 1건당 비용과 시간**입니다.
- 이 지표가 없으면 임베딩이든 에이전트든 비교할 수 없고, 프로젝트가 계속 투자받을 근거도 약해집니다.

## 5. 구현 첫날 제안

**목표: "되는지 안 되는지"를 하루 만에 한 서비스에서 확인합니다. 인프라는 만들지 않습니다.**

1. **(1시간) 대상 선정**: 사내 과거 취약점 이력이 있고 패치 전 커밋을 구할 수 있는 서비스 1~2개를 고릅니다. 중간 규모에 익숙한 언어가 좋습니다. 데이터 반출 정책도 같이 확인합니다.
2. **(1시간) 샌드박스**: 해당 커밋을 읽기 전용으로 마운트한 컨테이너나 작업 디렉터리를 만들고 네트워크를 차단합니다.
3. **(2~3시간) 최소 에이전트**: 기존 에이전트 프레임워크(예: Claude Agent SDK)에 `grep`, `read_file`, `list_dir`만 연결합니다. 프롬프트는 "이 진입점에서 시작해 입력이 위험한 sink에 닿는 경로를 추적하고, 근거와 함께 JSON으로 보고하라"로 시작합니다.
4. **(1시간) 진입점 목록**: 라우트 정의를 grep이나 간단한 스크립트로 뽑아 10~20개의 분석 단위를 만듭니다. 정교한 도구는 나중에 붙입니다.
5. **(1~2시간) 실행과 기록**: 진입점별로 돌리고 소요 시간, 토큰, 비용, 결과를 표로 남깁니다.
6. **(마지막 1시간) 비교와 회고**: 과거 취약점을 찾았는지, 오탐은 몇 개인지, 에이전트가 어디서 헤맸는지(파일을 못 찾음, 흐름을 놓침, 같은 곳을 반복 탐색 등)를 정리합니다.

**첫날의 산출물은 다음과 같습니다.**
- 한 서비스에서의 재현율, 오탐 수, 비용 수치
- 실패 유형 목록. 이것이 둘째 주 우선순위가 됩니다. 예를 들어 "정의 찾기가 필요하다"가 나오면 LSP나 ctags를 붙이고, "서비스 간 호출을 못 따라간다"가 나오면 그때 검색 도구 도입을 검토합니다.

## 6. 이후 순서 (참고)
1주차는 첫날 실험을 3~5개 서비스로 확장하고 평가셋을 정리합니다. 2~3주차는 검증/반박 단계와 구조화 출력, 중복 제거를 붙입니다. 이후 서비스 우선순위 자동화와 CI 연동(PR 단위 증분 분석)으로 넘어갑니다.

원하시면 에이전트 프롬프트 초안, 평가셋 구성 방법, 또는 서비스 우선순위 점수 기준을 더 구체적으로 작성해 드리겠습니다.
