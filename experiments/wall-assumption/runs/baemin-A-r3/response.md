# 사내 지식 QA 서비스 초기 설계안

## 1. 제안 설계안의 문제

| 항목 | 문제 |
|---|---|
| 고정 워크플로에 소스 추가 | 질문 유형이 열려 있습니다(용어, 주소, 담당자, 프로젝트, 성과 분석). 소스가 늘수록 분기와 조합이 폭발하고, "검색→요약→검색→답변" 순서가 맞지 않는 질문이 계속 생깁니다. |
| 키워드 FAQ 자동응답 | 기존 도구 검색의 한계(키워드 매칭)를 그대로 반복합니다. 표현이 조금만 달라도 못 찾고, 수작업 등록 FAQ는 금방 낡습니다. 수백 개 채널 규모에서는 관리가 불가능합니다. |
| 개선 방식 | 불만족 답변을 고치려면 개발자가 워크플로를 수정해야 해서 "바로 개선"이 어렵습니다. |

**결론:** 확정된 경로(질문 → SQL 조회)는 워크플로로 두고, 열린 질문은 도구를 가진 에이전트가 검색 경로를 스스로 정하게 합니다. 지원 채널은 과거 해결 스레드에서 지식을 자동으로 만들고, 사람이 검수하는 단계적 방식으로 갑니다.

## 2. 전체 구조

```
사용자(웹/메신저 봇)
   │
[대화 계층] 세션 저장, 후속 질문 재작성(대명사·생략 보완)
   │
[에이전트 루프] ── 도구 호출을 반복하며 근거 수집, 부족하면 재검색
   │   ├─ search_wiki / search_portal / search_issue / search_docs
   │   ├─ search_messenger (공개 채널, 해결된 스레드 위주)
   │   ├─ find_owner (담당자 조회: 문서 소유자, 이슈 담당자, 채널 답변 빈도)
   │   ├─ text_to_sql (기존 서비스를 도구로 감쌈)
   │   └─ get_table_metadata (기존 검색 재사용)
   │
[답변 생성] 출처 링크 필수, 근거 없으면 "모르겠다"와 담당자 안내
   │
[트레이스 저장] 질문, 도구 호출, 검색 결과, 답변, 사용자 피드백
```

### 인덱싱 계층 (소스 공통)
- 소스별 커넥터가 공통 스키마로 정규화합니다: `source, url, title, body, owner, updated_at, acl, type`.
- 검색은 하이브리드(키워드 + 임베딩)에 리랭커를 붙입니다. 사내 고유 용어와 약어는 키워드가 강하고, 의미 질문은 임베딩이 강합니다.
- 사내 용어집(약어, 서비스명, 별칭)을 쿼리 확장에 사용합니다.
- 최신성 메타(`updated_at`)를 랭킹과 답변에 반영해, 오래된 문서는 "N년 전 문서"라고 표기합니다.

### 권한
- 검색 시점에 질문자 권한(ACL)으로 필터링합니다. 비공개 채널과 문서는 권한이 없으면 근거로 쓰지 않습니다.
- 메신저는 공개 채널부터 시작하고, 개인정보는 인덱싱 전에 마스킹합니다.
- 초기부터 넣어야 합니다. 나중에 붙이면 구조를 갈아엎게 됩니다.

### 성과 분석 질문
SQL 조회와 문서 검색(지표 정의, 프로젝트 배경)을 에이전트가 함께 호출합니다. 지표 정의 문서를 먼저 찾고 SQL을 생성하면 정확도가 올라갑니다.

## 3. 이전 대화 이어가기
- 세션별 최근 N턴과 요약을 저장하고, 매 턴 "독립 질문"으로 재작성한 뒤 검색합니다.
- 사용자 장기 메모리(소속, 관심 서비스)는 2단계로 미룹니다. 권한 및 개인정보 이슈가 있습니다.

## 4. 바로 개선할 수 있는 구조
1. 모든 응답에 👍/👎와 사유(틀림, 오래됨, 못 찾음, 권한)를 받습니다.
2. 트레이스를 보고 실패 원인을 분류합니다: 문서 없음, 검색 실패, 잘못된 도구 선택, 생성 오류.
3. 실패 사례는 **평가셋**에 추가하고, 프롬프트, 도구 설명, 용어집 변경 후 회귀 테스트를 돌립니다.
4. 대부분의 수정은 코드 배포 없이 설정으로 해결되게 합니다: 용어집, 도구 설명, 우선 소스, 정정 답변(오버라이드).
5. 답변 하단에 "이 답변 정정하기"를 두고, 담당자가 정정하면 검증된 지식 항목으로 우선 검색되게 합니다.

## 5. 지원 채널 자동 응대 (단계적)
1. **학습 대상 구성:** 채널별 스레드에서 "질문 → 담당자 답변 → 해결 표시(✅, 감사 인사 등)" 쌍을 자동 추출하고, 유사 질문을 군집화해 반복 빈도를 계산합니다.
2. **검색:** 키워드 매칭이 아니라 의미 검색으로 과거 해결 스레드와 관련 문서를 찾아 답변을 합성하고, 원 스레드 링크를 붙입니다.
3. **신뢰도 게이트:** 유사도, 근거 일치, 최신성으로 점수를 매깁니다.
   - 낮음: 응답하지 않고 담당자에게 넘깁니다.
   - 중간: **담당자에게 초안 제안**(담당자가 승인/수정 후 게시)
   - 높음: 자동 응답. 단, 반복 빈도가 높고 위험이 낮은 유형부터 시작합니다.
4. **학습 루프:** 담당자의 수정과 승인이 곧 라벨입니다. 이를 다시 지식과 평가셋에 반영합니다.
5. 자동 응답에는 "봇 답변, 틀리면 👎 또는 담당자 호출" 버튼을 둡니다.

## 6. 단계별 로드맵
| 단계 | 내용 |
|---|---|
| 0 (1~2주) | 질문 로그 분석, 평가셋, 트레이스 로깅, 소스 2개와 에이전트 PoC |
| 1 | 소스 확대, 하이브리드 검색, 권한 필터, 대화 이어가기, 피드백 UI |
| 2 | 지원 채널 2~3곳에서 초안 제안 모드(섀도우) |
| 3 | 고신뢰 유형만 자동 응답, 담당자 정정 루프, 대시보드 |

## 7. 위험과 대응
- **환각:** 근거 인용 필수, 근거가 없으면 거절하고 담당자를 안내합니다.
- **권한 유출:** 검색 단계에서 ACL을 적용하고, 권한 테스트를 평가셋에 포함합니다.
- **오래된 정보:** 최신성 표기, 정정 오버라이드, 담당자 재검증 알림을 둡니다.
- **에이전트 비용과 지연:** 도구 호출 횟수 상한, 단순 질문은 단일 검색 경로, 캐시를 둡니다.
- **오답 자동 응대로 인한 신뢰 하락:** 섀도우 → 초안 → 자동 순으로 단계를 지킵니다.

# 구현 첫날 제안

**목표:** 코드를 많이 쓰기보다, 무엇을 만들고 어떻게 좋아졌는지 판단할 근거부터 확보합니다.

### 오전: 현실 파악
1. **질문 로그 수집 및 분류 (약 100~200건).** 최근 질문을 유형별로 나눕니다: 용어, 주소/정책, 담당자, 프로젝트, 성과 분석, 데이터 조회, 기타. 각 유형이 어떤 소스에 답이 있는지도 표시합니다. 이것으로 **먼저 붙일 소스 2개**를 정합니다. 예를 들면 위키와 이슈 관리 도구입니다.
2. **지원 채널 반복 문의 규모 측정.** 메신저 API로 상위 채널 3~5개의 최근 3개월 스레드를 내려받아, 질문 수, 담당자 답변 비율, 반복 유사 질문 비율을 간단히 계산합니다. 자동 응대의 우선순위와 기대 효과를 여기서 정합니다.
3. **보안 확인.** 접근 가능한 데이터 범위, 비공개 채널 처리, 개인정보 마스킹 원칙을 보안 담당자와 합의합니다.

### 오후: 최소 뼈대
4. **평가셋 v0.** 분류한 질문 중 30~50개에 정답 또는 정답 문서를 사람이 붙입니다. 이것이 이후 모든 변경의 기준입니다.
5. **트레이스 로깅.** 질문, 도구 호출, 검색 결과, 답변, 피드백을 한 레코드로 저장합니다. 이것이 "바로 개선"의 기반입니다.
6. **기존 text-to-SQL을 도구로 감싸기.** 입력과 출력 인터페이스만 정의합니다.
7. **커넥터 1개 + 하이브리드 인덱스.** 가장 질문이 많은 소스 하나를 공통 스키마로 인덱싱하고, 검색 도구 하나로 노출합니다.
8. **최소 에이전트 루프.** 도구 2~3개를 가진 루프를 만들고, 평가셋으로 첫 베이스라인 점수를 기록합니다.

### 첫날 종료 시 산출물
- 질문 유형 분포표와 소스 우선순위
- 지원 채널 반복 문의 통계
- 평가셋 v0와 베이스라인 점수
- 트레이스가 쌓이는 최소 동작 에이전트 (소스 1개 + SQL 도구)

이후 며칠은 소스를 하나씩 추가하며 평가 점수 변화를 확인하고, 지원 채널은 섀도우 모드로 먼저 붙이는 순서를 권합니다.
