# 초기 설계안: LLM 기반 소스코드 취약점 탐지 자동화

## 1. 방향: 임베딩도 전체 압축도 아닌 "에이전트가 코드를 탐색하는 방식"

두 후보 모두 단독으로는 이 문제에 맞지 않습니다.

| 방식 | 한계 |
|---|---|
| 임베딩 + 검색(RAG) | 취약점은 대개 입력 지점에서 위험한 함수까지 이어지는 여러 파일에 걸친 데이터 흐름입니다. 임베딩은 비슷해 보이는 코드를 가져올 뿐, 실제 호출자·피호출자를 가져오지 못합니다. 청킹이 흐름을 끊고, 인덱스 구축·갱신 비용도 수백 개 서비스에 곱해집니다. |
| 저장소 전체 압축 | 큰 서비스는 여전히 컨텍스트에 들어가지 않습니다. 들어가더라도 긴 컨텍스트에서 정확도가 떨어지고, 서비스마다 비용이 큽니다. |

대안은 LLM 에이전트에 `grep`, 파일 읽기, 디렉터리 탐색, 정의·참조 찾기 같은 도구를 주고, 사람 리뷰어처럼 필요한 코드만 따라가며 읽게 하는 것입니다. 인덱스를 따로 만들 필요가 없고 새로 배울 기술도 적습니다. 공개된 LLM 취약점 탐지 연구 사례도 대체로 이 구조를 씁니다. 임베딩은 나중에 보조 검색 도구로 추가할 수 있습니다.

작은 서비스(대략 10만 토큰 이하)는 전체를 한 번에 넣는 방식이 가장 간단한 기준선입니다. 이 방식은 기준선과 소형 서비스용으로만 씁니다.

## 2. 파이프라인

```
[서비스 선별] → [공격 표면 식별] → [진입점별 분석 에이전트] → [검증/반박 패스] → [사람 트리아ージュ]
                                         ↑ 도구: grep, read, (Semgrep/CodeQL 결과)
```

1. **서비스 우선순위**: 외부 노출, 인증·결제·개인정보 처리 여부로 점수를 매깁니다. 수백 개를 한꺼번에 돌리지 않습니다.
2. **공격 표면 식별**: HTTP 라우트, RPC 핸들러, 큐 컨슈머 같은 진입점을 목록화합니다. 프레임워크별 Semgrep 규칙이나 tree-sitter, 또는 LLM으로 추출합니다.
3. **진입점 단위 분석**: "저장소 전체"가 아니라 "이 핸들러에서 시작되는 흐름"을 분석 단위로 삼으면 문제 크기가 줄어듭니다. 에이전트는 취약점 유형별 체크리스트(인가 누락/IDOR, 인젝션, SSRF, 역직렬화, 하드코딩 비밀 등)를 따라 입력부터 싱크까지 추적합니다. 토큰과 턴 예산을 제한합니다.
4. **정적 분석 결합**: Semgrep이나 CodeQL 결과를 후보 생성기 또는 에이전트의 도구로 씁니다. LLM은 후보의 도달 가능성 판단과 오탐 제거, 그리고 규칙으로 못 잡는 논리 결함(인가 등)을 맡습니다.
5. **검증 패스**: 별도 프롬프트나 에이전트가 "이 발견을 반박하라"는 관점으로 재검토합니다. 가능하면 샌드박스에서 테스트나 PoC로 재현합니다. 오탐이 가장 큰 운영 비용이므로 이 단계가 핵심입니다.
6. **출력 스키마 고정**: 서비스, 파일:라인, 유형, source→sink 경로, 근거, 신뢰도, 재현 방법을 JSON으로 받아 중복 제거와 추적에 씁니다.

## 3. 보안·운영 제약 (초기에 못 박을 것)

- **코드 반출 승인**: 사내 소스를 외부 LLM API로 보내도 되는지 정책, 법무, 보안 승인과 데이터 보존 없음(zero retention) 계약을 확인합니다. 가장 먼저 확인할 항목입니다.
- **샌드박스**: 분석 대상 코드는 신뢰하지 않습니다. 코드 주석에 심은 프롬프트 인젝션이 가능하므로, 에이전트는 읽기 전용 체크아웃, 네트워크 차단, 비밀 정보 없는 환경에서 돌립니다. 도구는 읽기와 검색만 허용합니다.
- **비용 계측**: 서비스당 토큰, 시간, 발견 건수 대비 유효 건수를 처음부터 기록합니다.

## 4. 성공 기준

- 정답 데이터: 과거 모의해킹, 버그바운티, 보안 사고에서 확인된 취약점이 있는 서비스를 정답셋으로 삼습니다.
- 지표: 재현율(과거 취약점을 찾는가), 정밀도(리뷰어가 유효로 판정한 비율), 서비스당 비용, 리뷰어 소요 시간.
- 목표 예시: 파일럿에서 "리뷰어가 유효로 인정한 발견 비율 X% 이상, 서비스당 비용 Y 이하"를 사전에 합의합니다.

## 5. 구현 첫날 제안

**오전: 전제 정리**
1. 코드 외부 전송 정책을 확인합니다. 승인 전이면 사내 호스팅 모델이나 승인된 엔터프라이즈 계약 경로로 한정합니다.
2. 파일럿 서비스 3개를 고릅니다. 소형 1개, 중형 1개, 과거 취약점 이력이 있는 서비스 1개로 하고, 이력 서비스에서 알려진 취약점 목록(정답셋)을 모읍니다.

**오후: 가장 단순한 엔드투엔드 1회**
3. 읽기 전용, 네트워크 차단 환경에 3개 서비스를 체크아웃합니다.
4. 기성 에이전트 프레임워크(Claude Agent SDK 등)로, 도구는 `grep`/`read`/`ls`만 주고 단순한 프롬프트를 만듭니다. "진입점을 찾고, 각 진입점에서 입력이 위험한 싱크에 도달하는지 추적하고, 고정 JSON 스키마로 보고하라"는 내용입니다. 직접 에이전트를 만들지 않습니다.
5. 소형 서비스에서 전체 투입 방식(기준선)과 에이전트 방식을 둘 다 돌려 비교합니다.
6. 같은 서비스에 Semgrep 기본 규칙셋을 돌려 비교 기준으로 둡니다.

**마감 전: 기록**
7. 결과를 직접 검토해 유효/오탐/놓침을 표로 만들고, 토큰, 시간, 비용을 기록합니다. 정답셋 취약점을 찾았는지 확인합니다.
8. 둘째 날 결정 사항을 정리합니다. 어떤 방식이 나았는지, 오탐 패턴이 무엇인지, 검증 패스를 먼저 넣을지 진입점 추출을 먼저 개선할지를 정합니다.

첫날의 목표는 좋은 시스템이 아니라 숫자가 있는 기준선 하나입니다. 이 숫자가 있어야 임베딩 추가나 정적 분석 결합 같은 이후 투자를 근거 있게 결정할 수 있습니다.

원하시면 에이전트 프롬프트 초안, 출력 JSON 스키마, 정답셋 양식 중 하나를 바로 작성해 드리겠습니다.
