당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

사내 구성원의 데이터 질문에 답하는 AI 서비스를 운영하는 데이터팀입니다. 지금 서비스는 질문을 SQL로 바꿔 데이터를 조회하고, 테이블 정의·메타데이터·SQL 예시를 검색해 답하는 검색 기반 서비스입니다.

최근 질문이 데이터 조회를 넘어 사내 전반의 지식으로 넓어졌습니다. 예를 들어 업무 용어의 뜻, 회사 주소, 특정 업무의 담당자, 사내 프로젝트 설명, 서비스 성과 분석을 묻습니다. 이런 정보는 사내 포털, 위키, 이슈 관리 도구, 메신저 대화, 문서 저장소에 흩어져 있고, 각 도구의 기본 검색은 키워드 매칭이라 문서 목록만 보여 줍니다. 메신저에는 업무 지원 채널이 수백 개 있고, 담당자가 같은 질문에 여러 번 답합니다.

목표: 사내 지식 전반에 대한 질문에 한 곳에서 답한다. 이전 대화를 이어서 답한다. 불만족스러운 답이 나오면 바로 개선할 수 있게 한다. 반복되는 지원 채널 문의도 자동으로 응대한다.

초기 설계: 지금처럼 개발자가 처리 순서를 정한 워크플로(예: 검색 → 요약 → 검색 → 답변)에 새 지식 소스를 붙여 넓힌다. 지원 채널은 미리 등록한 질문–답변 쌍을 키워드로 찾아 답하는 FAQ 자동응답으로 시작한다.

# 사내 지식 AI 서비스 초기 설계안

## 1. 제안한 초기 설계에 대한 판단

| 항목 | 문제 | 조정 방향 |
|---|---|---|
| 고정 워크플로에 소스 추가 | 질문 유형(용어, 주소, 담당자, 프로젝트, 성과 분석)마다 경로가 달라 소스가 늘수록 분기가 폭발합니다. "검색→요약→검색"이 맞지 않는 질문도 많습니다. | 소스별 검색 도구를 주고 모델이 호출 순서와 횟수를 정하는 **도구 사용형 에이전트 루프**로 갑니다. 기존 SQL 경로는 도구 하나로 감쌉니다. |
| FAQ 키워드 자동응답 | 같은 질문도 표현이 제각각이라 키워드로는 놓칩니다. QA 쌍을 사람이 등록하고 갱신해야 해서 수백 개 채널에서는 유지가 안 됩니다. | **과거 스레드(질문과 채택된 답)를 인덱싱해 의미 검색**하고, 신뢰도에 따라 응대 수준을 단계화합니다. |

핵심은 이렇습니다. 데이터 조회 경로처럼 절차가 확정된 곳은 워크플로를 유지하고, 질문 범위가 열려 있는 곳은 에이전트에게 맡깁니다. 그리고 **개선 루프(로그, 평가셋)를 기능보다 먼저 만듭니다.**

## 2. 구성

```
질문 ─▶ [대화 컨텍스트 처리: 히스토리 + 질문 재작성]
      ─▶ [에이전트 루프 (최대 스텝, 출처 인용 강제)]
            ├ search_wiki / search_issues / search_docs / search_chat
            ├ search_support_threads (과거 지원 답변)
            ├ lookup_owner (담당자 조회)
            └ run_data_query (기존 text-to-SQL + 메타데이터 검색)
      ─▶ 답변 + 출처 + 기준일 + 👍/👎
      ─▶ [Trace 로그] ─▶ 리뷰 큐 ─▶ 평가셋 ─▶ 회귀 테스트
```

**수집/인덱싱**
- 소스별 커넥터가 공통 스키마(`source, url, title, body, author, updated_at, acl, type`)로 변환해 적재합니다.
- 하이브리드 검색(키워드 + 임베딩)을 쓰고, 문서는 구조 단위로 청킹합니다. 메신저는 메시지 단위가 아니라 **스레드 단위**로 묶습니다.
- 증분 동기화를 하고, 삭제와 권한 변경도 반영합니다.

**권한**
- 문서 ACL을 인덱스에 보존하고 **질문자 권한으로 검색 단계에서 필터링**합니다. 비공개 채널과 인사·재무 문서가 가장 큰 사고 위험이라 설계 초기에 확정합니다.

**신뢰도와 최신성**
- 모든 답에 출처 링크와 문서 수정일을 표시합니다.
- 소스 간 충돌(오래된 위키 vs 최근 공지) 시 최신성과 공식성 우선순위를 두고, 근거가 없으면 "찾지 못함"과 담당 문의처를 안내합니다.

**대화 이어가기**
- 세션 히스토리를 저장하고, 후속 질문("그건 누가 담당해?")은 독립 질문으로 재작성한 뒤 검색합니다.
- 개인 장기 기억은 권한과 프라이버시 이슈가 있어 2단계로 미룹니다.

**개선 루프**
- 모든 요청의 질문, 도구 호출, 검색 결과, 최종 답, 프롬프트/모델 버전을 trace로 저장합니다.
- 👎에는 사유(틀림/못 찾음/오래됨/권한)를 받습니다.
- 실패 건을 리뷰해 원인을 분류합니다(소스 누락, 검색 실패, 도구 설명 부족, 프롬프트, 문서 자체 오류). 수정 후 평가셋에 편입하고, 변경마다 평가셋을 자동 실행합니다.
- 프롬프트와 도구 설명은 코드 배포 없이 버전 관리하며 바꿀 수 있게 합니다.

**지원 채널 자동응대 (단계적)**
1. **섀도우 모드**: 답하지 않고 내부 로그에 초안만 쌓아, 담당자의 실제 답과 비교해 정확도를 측정합니다.
2. **초안 제안**: 담당자에게만 보이는 초안을 주고, 승인 또는 수정 여부를 기록합니다.
3. **자동 응답**: 채널별로 정확도가 기준을 넘고 신뢰도가 높은 질문 유형만 직접 답하며, 담당자 호출 버튼과 "해결됨" 확인을 붙입니다. 나머지는 담당자에게 넘깁니다.
- 담당자가 고친 답은 지식으로 환류합니다.
- FAQ 쌍은 폐기하지 않고, 검증된 고빈도 항목에 한해 우선순위가 높은 소스로 씁니다.

## 3. 주요 리스크
- 권한 유출(최우선)
- 메신저 잡음과 오래된 답변이 정답처럼 노출되는 문제
- 에이전트의 비용·지연 증가(스텝 상한, 캐시, 소형 모델 분기로 완화)
- 자동응대 오답이 채널 신뢰를 깎는 문제(단계적 승격으로 완화)

## 4. 구현 첫날 제안

코드보다 **무엇을 맞혀야 하는지**부터 정합니다.

1. **질문 표본 수집 (오전)**: 최근 서비스 로그와 지원 채널 2~3곳에서 실제 질문 80~100개를 뽑아 유형(용어/주소/담당자/프로젝트/성과분석/데이터조회/기타)과 정답 소스를 표기합니다. 이것이 첫 평가셋입니다.
2. **범위 확정**: 첫 소스 2개(위키 + 지원 채널 1~2개)와 권한 정책(공개 채널만 먼저)을 정합니다. 팀장과 보안 담당 합의가 필요합니다.
3. **trace 로그 스키마와 저장소 (오후 초반)**: 이후 모든 개선의 기반이라 에이전트보다 먼저 만듭니다.
4. **얇은 에이전트 골격 (오후)**: 기존 검색·SQL 기능을 도구로 감싸고 위키 검색 도구 하나를 추가해, 출처 인용과 최대 스텝 제한이 있는 루프를 end-to-end로 돌립니다.
5. **베이스라인 측정 (마감 전)**: 평가셋을 돌려 유형별 정답률과 실패 원인 분류를 만듭니다. 이것이 이후 변경(소스 추가, 지원 채널 섀도우 모드)의 비교 기준입니다.

**첫 주 목표**: 위키 + 지원 채널 스레드 인덱싱, 👍/👎 수집, 지원 채널 한 곳의 섀도우 모드 가동.

원하시면 trace 스키마나 평가셋 포맷 초안부터 구체화해 드리겠습니다.

## 응답 R-D329

# 초기 설계안과 구현 첫날 제안

## 1. 초기 설계 (요구 기준으로 다시 짠 것)

주어진 초기 설계(고정 워크플로 + 키워드 FAQ)는 출발점으로는 유효하지만, 목표 4개 중 두 개(이전 대화 이어가기, 즉시 개선)와 질문 범위 확장에 약합니다. 그래서 다음처럼 잡습니다.

**구조: 라우터 + 소스별 검색 도구 + 제한된 에이전트 루프**

1. **질문 분류/라우팅**: 데이터 조회(기존 text-to-SQL 경로), 사내 지식(용어·주소·담당자·프로젝트), 성과 분석(SQL + 문서 결합), 지원 채널 문의로 나눕니다. 기존 SQL 경로는 그대로 두고 앞단에만 분기를 둡니다.
2. **지식 소스 커넥터**: 포털, 위키, 이슈 도구, 메신저, 문서 저장소를 각각 같은 형태(문서 조각 + 출처 + 권한 + 수정일)로 색인합니다. 키워드와 임베딩을 함께 쓰는 하이브리드 검색을 사용합니다.
3. **답변 생성**: 개발자가 정한 고정 순서 대신, 소스 도구를 호출하는 에이전트 루프를 쓰되 단계 수·도구 집합을 제한합니다. 모든 답에 출처 링크를 붙이고, 근거가 없으면 모른다고 답합니다.
4. **대화 기억**: 세션 내 대화 이력을 질문 재작성(대명사·생략 해소)에 사용합니다. 장기 기억은 일단 만들지 않습니다.
5. **피드백 루프**: 답변마다 👍/👎와 사유를 저장하고, 질문·검색 결과·최종 답·출처를 로그로 남깁니다. 👎 사례는 평가 세트로 쌓이고, 담당자가 정답 문서나 교정 답을 지정하면 다음 검색에 반영됩니다.
6. **지원 채널 응대**: FAQ 키워드 매칭 대신, 과거 채널 스레드(질문 → 담당자 답변)를 색인해 유사 질문을 찾고, 확신도가 높을 때만 답하며 낮으면 담당자에게 넘깁니다. 초기에는 자동 게시가 아니라 담당자에게 초안 제안으로 운영합니다.
7. **권한**: 질문자 권한으로 검색 결과를 필터링합니다. 비공개 채널과 문서가 섞이므로 이 부분은 설계 초기에 정해야 합니다.

## 2. 틀리면 설계를 크게 바꿔야 하는 가정

**가정: 지원 채널의 과거 스레드(질문 → 담당자 답변)에서 유사 질문을 검색하면, 사람이 검수 없이도 쓸 만한 답을 충분한 비율로 찾을 수 있다.**

이 가정이 맞으면 FAQ를 미리 등록하는 대신 스레드 기반 검색으로 간다. 틀리면(스레드 답이 맥락 의존적이거나 오래되어 재사용이 안 되면) 지원 채널은 자동 응대가 아니라 "담당자 보조 초안" 또는 FAQ 큐레이션 파이프라인으로 설계를 바꿔야 하고, 메신저 색인 전체의 가치도 재평가해야 합니다.

## 3. 가장 작은 실험

- **입력**: 지원 채널 5~10개(질문량 상위)에서 최근 3~6개월 스레드. 시간순으로 앞 80%를 색인하고, 뒤 20%에서 질문 약 100~200건을 샘플링해 테스트 질문으로 씁니다. 비공개 내용은 마스킹하거나 데이터팀이 접근 가능한 채널로 한정합니다.
- **비교 대상**:
  - A: 현재 계획의 키워드 FAQ 방식(상위 반복 질문 일부를 FAQ로 등록해 키워드 매칭)
  - B: 스레드 색인 + 하이브리드 검색으로 과거 답변을 찾아 답 생성
  - 기준선: 실제 담당자가 단 답변
- **판정 방법**: 담당자 2명이 각 응답을 "그대로 게시 가능 / 수정 필요 / 틀림"으로 블라인드 채점합니다. "틀림"은 잘못된 정보나 오래된 안내를 포함한 경우입니다.
- **실패로 판단할 관찰 결과** (실험 전에 확정해 둘 임계값 예시):
  - B의 "그대로 게시 가능" 비율이 약 30% 미만이거나 A와 의미 있는 차이가 없음
  - 또는 B가 확신도 높다고 낸 답 중 "틀림"이 5~10%를 넘음 (확신도로 걸러지지 않음)
  - 또는 정답 스레드가 존재하는데도 상위 5개 검색 결과에 못 찾는 비율이 높음

임계값은 제 추정이므로 담당자와 합의해 조정해야 합니다.

## 4. 실패 시 조치

**직접 시도할 것 (사용자 결정 불필요)**
- 청킹 단위를 메시지 단위에서 스레드 단위로 바꾸기, 질문 재작성, 하이브리드 가중치·리랭커 조정
- 오래된 스레드 감점, 담당자 답변만 색인하는 등 필터 변경
- 확신도 임계값 상향, 스레드를 요약해 "질문–답" 쌍으로 정제한 뒤 색인
- 실패 사례를 원인별로 분류(검색 실패 / 답이 맥락 의존 / 답이 낡음 / 생성 오류)해 보고

**사용자(데이터팀·채널 담당자) 결정이 필요한 조건**
- 원인이 데이터 자체의 한계(답이 맥락 의존적이거나 낡음)로 판명되어, 위 조정 후에도 임계값 미달일 때 → 자동 응대 포기 후 "담당자 초안 보조"나 FAQ 큐레이션으로 범위 변경할지
- 비공개 채널 스레드 접근 또는 메신저 데이터 사용 승인이 필요할 때
- 임계값 자체(허용 오답률)를 완화해야 할 때
- 담당자 채점 인력을 추가로 요청해야 할 때

## 5. 구현 첫날 할 일

1. **오전: 범위·접근 확인**: 실험 대상 채널 목록, 메신저 API/내보내기 접근 권한, 데이터 사용 승인 여부를 확인합니다. 막히면 가장 먼저 사용자에게 올릴 항목입니다.
2. **오전: 데이터 추출**: 선택한 채널의 스레드를 추출해 질문–답변 구조로 정리하고, 시간순 분할로 테스트 세트를 고정합니다. 이 세트는 이후 모든 변경의 회귀 평가 세트가 됩니다.
3. **오후: 기준선(A) 구축**: 키워드 매칭 FAQ를 빠르게 만들어 기준선 점수를 얻습니다.
4. **오후: 방식 B의 최소 구현**: 스레드 색인과 하이브리드 검색만 붙이고, 생성 단계는 상위 결과를 그대로 보여 주는 수준으로 시작해 "검색이 정답 스레드를 찾는가"부터 확인합니다.
5. **하루 끝**: 채점 시트(질문, A·B 응답, 담당자 실제 답, 3단계 채점란)를 만들어 담당자에게 넘길 준비를 합니다.

기존 SQL 경로 수정, 다른 지식 소스 커넥터, 장기 기억은 이 실험 결과가 나오기 전에는 착수하지 않습니다.
