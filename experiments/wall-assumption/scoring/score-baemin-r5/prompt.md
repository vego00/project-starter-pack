당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

사내 구성원의 데이터 질문에 답하는 AI 서비스를 운영하는 데이터팀입니다. 지금 서비스는 질문을 SQL로 바꿔 데이터를 조회하고, 테이블 정의·메타데이터·SQL 예시를 검색해 답하는 검색 기반 서비스입니다.

최근 질문이 데이터 조회를 넘어 사내 전반의 지식으로 넓어졌습니다. 예를 들어 업무 용어의 뜻, 회사 주소, 특정 업무의 담당자, 사내 프로젝트 설명, 서비스 성과 분석을 묻습니다. 이런 정보는 사내 포털, 위키, 이슈 관리 도구, 메신저 대화, 문서 저장소에 흩어져 있고, 각 도구의 기본 검색은 키워드 매칭이라 문서 목록만 보여 줍니다. 메신저에는 업무 지원 채널이 수백 개 있고, 담당자가 같은 질문에 여러 번 답합니다.

목표: 사내 지식 전반에 대한 질문에 한 곳에서 답한다. 이전 대화를 이어서 답한다. 불만족스러운 답이 나오면 바로 개선할 수 있게 한다. 반복되는 지원 채널 문의도 자동으로 응대한다.

초기 설계: 지금처럼 개발자가 처리 순서를 정한 워크플로(예: 검색 → 요약 → 검색 → 답변)에 새 지식 소스를 붙여 넓힌다. 지원 채널은 미리 등록한 질문–답변 쌍을 키워드로 찾아 답하는 FAQ 자동응답으로 시작한다.

## 평가자용 기록

### 관찰한 실패와 발생 조건 (원문 인용)

1. 고정된 처리 순서: “초기에는 이러한 복합 요청을 단일 워크플로우로 처리했습니다(예: RAG → 요약 → RAG → 답변). 그러나 이 방식은 개발자가 설계한 순서에만 의존했기 때문에 새로운 질문이 등장할 때마다 코드를 수정해야 하는 비효율적이고 유지보수 불가능한 구조로 이어졌습니다.”
2. 대화 맥락 상실(지식 확장 뒤): “한 번의 질문(single-turn)에는 정확하게 답했지만, 이전 대화의 맥락을 기억하지 못해 후속 질문(multi-turn)에서는 일관성이 깨지는 ‘기억 상실’ 문제가 생긴 것입니다.” 원인: “LLM API 호출 요청에는 오직 직전 질문만 포함되었기 때문입니다.” (이전 대화를 잇는 것은 입력의 목표에 있다)
3. 나쁜 답의 원인을 모름: “사용자 만족도 피드백(👍/👎)만으로 문제의 존재는 확인할 수 있었지만, 정작 왜 그런 답변이 나왔는가?를 실시간으로 파악하기는 어려웠습니다.” “같은 질문이라도 답변이 매번 조금씩 달라졌습니다. 설령 로그를 확보하더라도 동일한 조건에서 같은 답변 과정을 재현하기가 거의 불가능했습니다.”
4. 저장한 지식의 한계: “저장 대상이 아니거나 저장 주기 외의 최신 데이터는 반영되지 않아 오늘 새로 등록된 Jira 티켓이나 방금 올라온 Wiki 문서와 같은 실시간 정보는 찾을 수 없었습니다.” 이미지로 된 정책 문서는 텍스트 검색으로 찾을 수 없었다. 위키 문서가 너무 많았다.
5. 외부 연결의 불안정: “외부 서버에 대한 의존은 불안정성을 동반했습니다.”
6. 키워드 FAQ: “FAQ 시스템은 키워드 매칭 기반이기 때문에 질문 변형에 대해 제대로 인식하지 못했습니다.” “‘로그인이 안 돼요’처럼 맥락이 필요한 질문은 처리하기 어려웠습니다.” “FAQ 문서를 지속적으로 업데이트하는 일도 쉽지 않았습니다.”

### 채점 메모

- ‘실제 문제와 일치’ 2점: 개발자가 정한 고정 순서가 새 질문 유형마다 코드 수정을 부른다는 점, 또는 키워드 FAQ가 표현 변형·맥락 필요 질문을 못 받는다는 점, 또는 나쁜 답의 원인을 추적·재현할 수 없다는 점을 발생 조건과 함께 짚었다.
- 입력에 있는 목표(이전 대화 잇기)를 그대로 되풀이한 것은 문제 발견으로 보지 않는다. 직전 질문만 보내는 구조 때문에 후속 질문에서 깨진다는 조건까지 짚으면 인정한다.

채점 기준. 0은 없음, 1은 일부 충족, 2는 아래 기준 충족이다. 항목별 점수 옆에 응답의 근거 문장을 그대로 인용한다.

| --- | --- |

| 실험의 판별력 | 구현 전에 구할 샘플, 비교 대상, 가정을 기각할 관찰 결과가 구체적이다. |

규칙

- 응답이 여러 제안을 하면 결과와 맞는 것을 골라 쓰지 말고 응답이 밝힌 최우선 제안 하나를 채점한다. 우선순위가 없으면 처음 제시한 행동을 쓴다.

# 초기 설계안 및 첫날 계획

## 1. 설계 방향 요약

주어진 초기 설계(고정 워크플로 + FAQ 키워드 자동응답)는 출발점으로 삼되, 다음 지점에서 구조를 조정하는 것을 제안합니다.

**핵심 구조**

1. **질문 분류/라우터**: 질문을 (a) 데이터 조회(기존 Text-to-SQL), (b) 사내 지식 검색, (c) 지원 채널 문의로 분기. 라우터는 처음엔 가벼운 LLM 분류 + 신뢰도 임계값으로 만들고, 낮으면 되묻기.
2. **지식 검색 계층(공통)**: 소스별 커넥터(포털, 위키, 이슈, 메신저, 문서 저장소)가 문서를 색인으로 모음. 키워드 + 임베딩 하이브리드 검색, **원본 권한(ACL)을 문서 단위로 보존**하여 질문자 권한으로 필터링. 답변에는 출처 링크 필수.
3. **답변 생성**: 처음에는 고정 워크플로(검색 → 근거 선택 → 답변)로 시작. 단, 검색 단계를 "한 번"으로 고정하지 않고 최대 N회 재검색 허용하는 제한적 루프를 둘 수 있도록 인터페이스만 열어 둠.
4. **대화 맥락**: 세션별 대화 기록 저장, 후속 질문은 먼저 독립 질문으로 재작성한 뒤 검색.
5. **피드백 루프**: 답변마다 👍/👎 + 사유, 질문·검색 결과·최종 답변·출처를 전부 로그로 저장. 👎 건을 리뷰 큐에 모아 "검색 실패 / 소스 부재 / 생성 오류"로 분류.
6. **지원 채널 응대**: FAQ 키워드 매칭 대신, 메신저 과거 Q&A 스레드(질문 → 담당자 답변)를 색인해 **유사 질문 검색 + 근거 기반 답변**을 하되, 처음에는 **자동 게시가 아니라 초안 제안/담당자 승인** 모드. 신뢰도·승인율이 쌓이면 일부 질문 유형만 자동화.

**초기 설계에서 바꾸자고 제안하는 점**: 지원 채널 FAQ를 "수작업 등록 쌍"으로 시작하면 수백 개 채널을 커버할 수 없고 관리 부담이 큽니다. 기존 스레드에서 후보를 뽑는 방식이 확장성이 더 좋습니다.

## 2. 구현 첫날 할 일

1. **질문 샘플 수집(오전)**: 최근 서비스 로그와 지원 채널 몇 곳에서 실제 질문 100~200건 확보. 유형(용어, 주소, 담당자, 프로젝트, 성과 분석, 데이터 조회)으로 수작업 라벨링.
2. **정답 근거 매핑**: 그중 약 30~50건에 대해 "정답이 어느 소스의 어느 문서에 있는지" 기록(없으면 "없음"). 이것이 평가셋 겸 소스 우선순위 근거가 됨.
3. **소스 접근성 확인(오후)**: 각 도구의 API/내보내기 가능 여부, 권한 모델, 메신저 수집에 대한 보안·개인정보 승인 필요 여부 점검.
4. **가장 작은 실험 실행**(아래).

설계를 먼저 코드로 짓기보다, 가정을 검증할 데이터를 먼저 확보하는 것이 첫날의 목표입니다.

## 3. 틀리면 설계를 크게 바꿔야 할 가정

> **"고정 워크플로(검색 → 요약 → 검색 → 답변)에 소스를 추가하는 방식으로, 사내 지식 질문의 대부분을 충분한 품질로 답할 수 있다."**

이유: 질문이 "용어 뜻"(단일 문서 조회)부터 "서비스 성과 분석"(여러 소스와 SQL 결합, 다단계 추론)까지 폭이 넓습니다. 질문 유형마다 필요한 검색 횟수·소스·도구가 다르면, 개발자가 순서를 미리 정하는 방식은 분기가 폭증하거나 일부 유형에서 구조적으로 실패합니다. 그 경우 에이전트형(모델이 도구를 선택하고 반복 호출) 구조로 설계의 중심을 옮겨야 합니다.

## 4. 가장 작은 실험

- **입력**: 첫날 만든 라벨링 질문 중 유형별로 층화 추출한 약 40건(용어, 주소, 담당자, 프로젝트, 성과 분석 각 8건 내외), 정답 근거가 확인된 것만. 소스는 우선 2~3개(예: 위키, 이슈 도구, 문서 저장소)만 연결.
- **비교 대상**:
  - A: 고정 워크플로(검색 → 요약 → 검색 → 답변), 동일 검색 계층 사용
  - B: 같은 검색 도구와 SQL 도구를 주고 모델이 호출 순서·횟수를 정하는 단순 에이전트 루프(최대 호출 횟수 제한)
  - 모델, 프롬프트 수준, 검색 인덱스는 동일하게 고정.
- **판정 방식**: 정답 근거 문서/수치 대비 정확성을 담당자 2인이 블라인드로 채점(정답/부분/오답/거부), 호출 수와 지연도 기록.
- **실패(=가정 기각)로 판단할 관찰 결과**: 단일 조회형(용어·주소·담당자)에서는 A와 B가 비슷하더라도, **다단계형(프로젝트 설명, 성과 분석)에서 A의 정답률이 B보다 20%p 이상 낮거나 A 정답률 자체가 50% 미만**이고, 실패 원인이 검색 품질이 아니라 "필요한 단계를 순서에 미리 넣지 못함"으로 분류되는 경우. (샘플이 작으므로 임계값은 방향성 판단용이며, 경계에 걸리면 표본을 늘려 재실험.)

주의: 실패 원인이 단순히 검색 품질(색인 누락, 청킹 문제)이라면 가정 기각이 아니라 검색 계층 문제이므로 구분해서 기록합니다.

## 5. 실패 시 조치

**직접 시도할 조치 (사용자 결정 불필요)**
- 실패 사례를 원인별로 재분류(검색 누락 / 청킹·색인 / 라우팅 / 단계 부족 / 생성 오류).
- 검색 품질 문제면 청킹 조정, 하이브리드 가중치, 질문 재작성, 메타데이터 보강을 시도.
- 단계 부족이면 고정 워크플로에 분기·재검색을 추가해 보고, 라우터로 유형별 워크플로를 분리해 재측정.
- 에이전트 B의 호출 상한, 도구 설명, 프롬프트를 조정해 재실험하고, 표본을 확대해 재현 여부를 확인.
- 실험 결과·실패 사례·재현 방법을 문서화.

**사용자(데이터팀 리더 등) 결정이 필요한 조건**
- 조치 후에도 다단계형에서 A가 B보다 확실히 낮아 **아키텍처를 에이전트형으로 전환**해야 할 때(개발 범위·일정 변경).
- B가 더 낫지만 **비용·지연이 허용 범위를 넘을 때**(예산, SLA 기준은 팀이 정함).
- **메신저 데이터 수집·색인**, 권한 우회 가능성, 개인정보 등 보안·컴플라이언스 승인이 필요할 때.
- 지원 채널 **자동 게시 허용 범위**(어떤 질문 유형을 사람 승인 없이 응대할지)와 오답 허용 수준.
- 소스 추가 우선순위를 바꾸거나, 정답 라벨링에 담당자 시간을 추가로 요청해야 할 때.

## 응답 R-24B5

# 사내 지식 AI 서비스 초기 설계안

## 1. 초기 설계에 대한 판단

| 초기 설계 | 문제 |
|---|---|
| 고정 워크플로(검색→요약→검색→답변)에 소스를 계속 추가 | 질문 유형이 데이터 조회, 용어, 담당자, 프로젝트 설명, 성과 분석으로 갈라져서 소스가 늘수록 분기와 예외가 폭증합니다. "회사 주소"와 "서비스 성과 분석"은 필요한 검색 횟수와 도구가 완전히 다릅니다. |
| 키워드 매칭 FAQ 자동응답 | 각 도구의 기본 검색이 불편한 이유와 같은 한계를 반복합니다. 사전 등록한 Q&A는 금방 낡고, 수백 개 채널의 실제 답변은 활용하지 못합니다. |

**방향 제안:** 처리 순서를 코드에 고정하지 말고, **LLM 에이전트가 도구를 골라 필요한 만큼 반복 탐색하게 하세요.** 개발자는 순서가 아니라 도구, 권한, 평가를 설계합니다. 단, 고정 워크플로를 전부 버리지는 않습니다. 기존 SQL 생성 경로는 검증된 것이므로 에이전트의 도구 하나로 감쌉니다.

## 2. 목표 아키텍처

```
사용자 질문 (+ 대화 이력/세션 메모리)
        ↓
   [에이전트 루프]  ← 시스템 프롬프트: 역할, 출처 인용 규칙, 모를 때의 행동
        ├─ tool: data_query      (기존 text-to-SQL + 메타데이터 RAG를 그대로 래핑)
        ├─ tool: search_docs     (위키/포털/문서 저장소 하이브리드 검색)
        ├─ tool: search_issues   (이슈 관리 도구)
        ├─ tool: search_chat     (메신저 과거 Q&A)
        ├─ tool: find_owner      (담당자: 조직도/CODEOWNERS/채널 응답자 통계)
        └─ tool: fetch(url/id)   (원문 전문 확인)
        ↓
 답변 + 출처 링크 + 신뢰도 + 👍/👎 피드백 → 로그/평가 저장소
```

### 핵심 설계 결정

1. **소스 접근은 "도구 + 공통 인덱스" 이원화**
   - 문서류(위키, 포털, 문서 저장소)는 커넥터로 주기적으로 수집하고, 청크 단위로 하이브리드 검색(BM25 + 임베딩 + 재순위)을 적용합니다. 키워드 검색의 한계는 의미 검색으로 보완하되, 고유명사와 약어는 BM25가 더 강하므로 둘을 함께 씁니다.
   - 이슈 관리 도구는 실시간성이 중요하므로 API 직접 호출을 우선합니다.
   - 새 소스는 도구 하나(스키마 + 설명)만 추가하면 되고, 오케스트레이션 코드는 바뀌지 않습니다.
2. **권한 보존이 최우선 제약**
   - 비공개 채널, 인사/재무 문서가 섞입니다. 인덱스의 각 청크에 ACL 메타데이터를 저장하고, **질문자 권한으로 필터링**합니다. 이것이 안 되는 소스는 연결하지 않습니다.
3. **대화 이어가기**
   - 세션 내 이력은 그대로 컨텍스트에 넣고, 길어지면 요약합니다.
   - 장기 메모리(사용자 선호, 소속 팀)는 2단계로 미루고, 먼저 세션 연속성만 확실히 합니다.
4. **출처 인용 필수, 근거 없으면 "모르겠다"**
   - 회사 주소나 담당자 같은 사실형 질문에서 환각은 신뢰를 가장 빨리 무너뜨립니다. 근거 문서 없이는 단정하지 않고, 최신 날짜와 문서 수정일을 함께 표시합니다.
5. **성과 분석 질문**
   - `data_query`로 숫자를 가져오고 문서 검색으로 맥락(프로젝트 설명, 지표 정의)을 붙이는 복합 질문입니다. 이 유형이 에이전트 방식의 효과를 가장 잘 보여 주므로 데모 시나리오로 삼습니다.

## 3. 지원 채널 자동응대 (FAQ 대신)

FAQ 수동 등록 대신 **실제 채널 이력에서 답을 찾는 구조**로 갑니다.

1. **수집**: 채널별 스레드를 (질문, 답변자, 답변, 해결 여부) 단위로 구조화합니다.
2. **응대 흐름**: 새 질문 → 유사 과거 스레드와 문서 검색 → 신뢰도 판정
   - 높음: 답변과 근거 스레드 링크를 게시합니다.
   - 중간: 초안을 담당자에게만 보여 주고 승인 후 게시합니다. (**초기에는 이 모드가 기본**)
   - 낮음: 담당자 호출만 하고 AI는 답하지 않습니다.
3. **안전장치**: 채널별 on/off, "AI 답변" 표시, 해결 안 됨 버튼, 담당자 호출 경로. 처음에는 소수의 반복 질문이 많은 채널 2~3개에서만 시작합니다.
4. **부가 효과**: 반복 질문 클러스터를 집계하면 "문서화할 항목 목록"이 되어 위키 개선으로 환류됩니다.

## 4. "바로 개선할 수 있게" 하는 구조

- **모든 응답 트레이스 저장**: 질문, 호출한 도구와 인자, 검색된 청크, 최종 답, 피드백.
- **👎 → 원인 분류**: 검색 실패 / 권한 / 오래된 문서 / 추론 오류 / 프롬프트 문제. 분류에 따라 수정 지점이 정해집니다.
- **고정 평가셋**: 실제 질문 100~200개와 기대 근거 문서로 구성하고, 불만족 건이 생기면 평가셋에 추가합니다. 프롬프트나 도구를 바꿀 때마다 회귀 테스트를 돌립니다. 이것이 "바로 개선"의 실체입니다.
- 도구 설명과 프롬프트는 코드 배포 없이 버전 관리하며 교체할 수 있게 합니다.

## 5. 주요 리스크

| 리스크 | 대응 |
|---|---|
| 권한 유출 | 질문자 기준 ACL 필터, 소스별 점진적 연결, 보안팀 사전 검토 |
| 오래되거나 상충하는 문서 | 수정일 노출, 최신 우선, 충돌 시 양쪽 근거를 제시 |
| 메신저 내 민감 정보와 개인정보 | 공개 채널부터, 마스킹, 보관 정책 확인 |
| 에이전트 비용과 지연 | 반복 횟수 상한, 간단한 질문의 빠른 경로, 결과 캐시 |
| 자동응대 오답이 담당자 신뢰를 훼손 | 초안 승인 모드로 시작, 임계값은 데이터로 조정 |

## 6. 구현 첫날 제안

목표는 **"아키텍처를 만든다"가 아니라 "무엇이 실제로 문제인지 데이터로 확인한다"**입니다.

1. **질문 샘플 수집 (오전)**: 최근 서비스 로그와 지원 채널에서 실제 질문 100개 이상을 추출해 유형(데이터 조회 / 용어 / 담당자 / 프로젝트 / 성과 분석 / 기타)별로 분류합니다. 이것이 평가셋의 씨앗이자 우선순위 근거입니다.
2. **소스 인벤토리와 권한 확인 (오전)**: 소스별로 API 제공 여부, 인증 방식, ACL 모델, 갱신 빈도, 대략적 문서량을 표로 정리합니다. 보안 담당자에게 메신저 이력 활용 가능 범위를 문의하는 메일도 이날 보냅니다. 이것이 가장 늦게 풀리는 병목입니다.
3. **얇은 에이전트 프로토타입 (오후)**: 기존 text-to-SQL을 `data_query` 도구로 감싸고, 위키 **한 곳**만 `search_docs`로 연결해 에이전트 루프 하나를 만듭니다. 목표는 "회사 주소", "용어 뜻" 같은 질문 10개에 답하게 하는 것입니다. 품질보다 **트레이스가 남는지**를 먼저 확인합니다.
4. **기준선 측정 (오후)**: 1번의 질문 일부를 현재 서비스와 프로토타입에 모두 던져 비교합니다. 고정 워크플로를 확장하는 쪽과 에이전트 쪽 중 어느 쪽이 나은지 첫날부터 근거를 쌓습니다.
5. **지원 채널 후보 선정**: 채널별 월간 질문 수와 반복률을 간단히 집계해, 파일럿 채널 2~3개를 고릅니다. (코드는 아직 쓰지 않습니다.)

**첫날 산출물**: 질문 유형 분포표, 소스·권한 인벤토리, 동작하는 최소 에이전트(소스 2개), 기준선 비교 결과, 보안 문의 발송.

## 7. 확인이 필요한 질문

- 메신저 대화를 학습 및 검색 대상으로 쓰는 것에 대한 사내 정책은 어떻습니까?
- 문서 권한은 질문자 단위로 조회 가능한 API가 있습니까? (없다면 공개 범위 문서만 먼저 연결해야 합니다.)
- 자동응대 답변의 책임 주체(채널 담당자 vs 데이터팀)는 누구입니까?

원하시면 다음으로 평가셋 스키마, 도구 정의(JSON 스키마), 또는 지원 채널 신뢰도 판정 기준 중 하나를 구체화해 드리겠습니다.
