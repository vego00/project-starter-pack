### 응답 R-2AAE
- 구현 첫날 첫 행동(응답 문장 그대로 인용): "**작업 폴더 만들기** (예: `review-labeler/`) 후 안에 `data/`, `docs/` 폴더 생성", 이어서 "**샘플 데이터 추출 (30분):** 과거에 손으로 라벨링한 리뷰 중 약 100건을 CSV로 저장"
- 채점한 최우선 제안(응답 문장 그대로 인용, 없으면 '없음'): "LLM(Claude API)에 리뷰와 라벨 정의를 주고 분류시키는 방식을 첫 도구로 삼으세요."
- 실제 문제와 일치: 1 — 근거: "코딩 지식이 없어도 \"라벨 정의 문서 + 예시\"를 다듬는 것이 핵심 작업이라", "각 값마다 한 줄 정의와 실제 리뷰 예시 1~2개를 붙임", "틀린 사례를 정의 문서의 예시/규칙에 반영하고 다시 측정" / 평가자용 기록의 'OpenAI API 결과물의 완성도 부족 → 예시 데이터 학습 요청' 단계와 대응합니다. 응답은 손으로 붙인 라벨을 예시로 쓰는 방향을 일부 담고 있습니다. 그러나 예시 없이 맥락만으로 분류시키면 완성도가 부족하다는 실패와 그 발생 조건은 짚지 않았습니다. 키워드 매핑을 비판한 부분은 입력의 제약을 되풀이한 것이라 점수에 반영하지 않았습니다.
- 실험의 판별력: 1 — 근거: "이미 손으로 라벨링한 과거 리뷰 200~300건(라벨 골고루)을 따로 보관", "사람이 붙인 과거 라벨 대비 일치율 85% 이상 (라벨별로 따로 측정)" / 샘플과 비교 대상(과거 라벨)은 있습니다. 하지만 기각할 가정이 명시되지 않았고, 85%는 성공 목표로만 제시되었습니다. 키워드 방식 같은 기준선 비교도 없습니다. 또 예시로 쓰는 데이터와 평가 데이터를 분리하지 않았습니다.
- 실패 후 행동: 2 — 근거: "**개선 반복:** 틀린 사례를 정의 문서의 예시/규칙에 반영하고 다시 측정" / 바꿀 요소(정의 문서의 예시와 규칙)가 구체적이고, 같은 정답 세트로 재측정해 개선을 확인할 수 있습니다.
- 사용자 개입 판단: 1 — 근거: "외부 API 전송 전에 사내 정책을 확인하고 필요하면 마스킹합니다.", "사내에서 외부 AI API로 리뷰 데이터를 보내도 되는지 확인되었나요?" / 권한과 비용 문제를 질문과 위험 요소로 언급했습니다. 그러나 스스로 시도할 조치와 사용자 결정이 필요한 조건을 구별해 제시하지는 않았습니다.

### 응답 R-EFCE
- 구현 첫날 첫 행동(응답 문장 그대로 인용): "**지금까지 손으로 붙인 라벨 데이터를 모읍니다.** 최근 2~3개월치면 충분합니다. 이것이 정답지가 됩니다."
- 채점한 최우선 제안(응답 문장 그대로 인용, 없으면 '없음'): "**키워드 매핑을 주 방식으로 쓰지 않고, LLM 분류를 주 방식으로, 사람 검수를 안전장치로** 두는 설계를 제안합니다."
- 실제 문제와 일치: 1 — 근거: "대표 예시 2~3개. 이것이 프롬프트의 핵심 재료입니다.", "사람이 고친 건은 예시로 쌓아 다음 달 프롬프트에 반영합니다.", "LLM-기존 라벨 일치율이 낮아도 사람 자기 일치율이 높다면 문제는 프롬프트 쪽이고" / 평가자용 기록의 '맥락 기반 API 분류의 완성도 부족 → 예시 데이터 활용' 단계와 부분적으로 대응합니다. 응답은 예시를 프롬프트 재료로 쓰고 프롬프트 쪽 실패를 구분하는 조건을 제시했습니다. 그러나 예시 없는 LLM 분류가 부족하다는 실패를 직접 짚지는 않았습니다. 응답이 핵심으로 내세운 가정(수작업 라벨의 일관성)은 기록에 없는 실패입니다.
- 실험의 판별력: 2 — 근거: "이미 라벨을 붙인 리뷰 중 무작위 100건. 이 100건을 **2주 이상 간격을 두고 같은 사람이 다시 라벨링**합니다", "서비스 라벨 일치율이 90% 미만이거나, 유형 일치율이 80% 미만, 세부 유형 일치율이 70% 미만이면 정답지로 쓰기 어렵다고 판단합니다.", "같은 평가 샘플에서 키워드 방식과 LLM 방식의 정확도를 비교해 두면" / 샘플, 비교 대상(재라벨, 동료 라벨, LLM, 키워드 기준선), 기각 기준이 모두 구체적입니다.
- 실패 후 행동: 2 — 근거: "불일치가 몰린 라벨 쌍을 뽑아 정의서에 경계 기준과 예시를 추가하고, 같은 100건으로 재측정" / 바꿀 요소가 구체적이고, 같은 100건으로 개선을 확인할 수 있습니다.
- 사용자 개입 판단: 2 — 근거: "**직접 시도할 조치 (사용자 결정 불필요)**", "**사용자 결정이 필요한 조건** … 리뷰를 외부 LLM API로 보내는 것이 규정상 불가하거나 승인이 필요할 때 … 비용 상한을 정해야 할 때" / 직접 시도할 조치와, 권한·비용·리포트 형식이 바뀌어 사용자 결정이 필요한 조건을 명확히 구별했습니다.

두 응답의 구현 첫날 첫 행동은 실질적으로 같습니다. 둘 다 과거 수작업 라벨 데이터를 모아 라벨 목록을 정리한 뒤, AI 코딩 도구로 LLM 분류 스크립트를 소량 건에 돌려 봅니다. R-EFCE는 평가용 샘플 분리와 사내 규정 확인을 더했다는 차이만 있습니다.
