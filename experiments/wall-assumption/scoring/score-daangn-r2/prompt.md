당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

서비스 운영팀의 운영 담당자입니다. 앱 리뷰 데이터를 관리하면서 매월 리포트로 구성원에게 공유합니다. 리포트에 넣을 시각화 자료를 만들려고, 매일 리뷰마다 ‘관련 서비스’, ‘유형’, ‘세부 유형’ 라벨을 손으로 붙이고 있습니다. 이 반복 작업에 매월 6시간 이상이 들어 다른 기획 업무를 같이 하기 어렵습니다.

제약: 앱 리뷰는 문장이 정돈되어 있지 않아 단순 키워드 매칭으로는 분류하기 어렵고, 하나하나 맥락을 판단해야 합니다. 저는 개발 경험이 거의 없어서 AI 코딩 도구의 도움을 받아 직접 자동 라벨링 도구를 만들려고 합니다.

지금 생각한 방법: 키워드를 서비스와 유형에 대응시키는 매핑으로 첫 도구를 만든다.

### 관찰한 실패와 후속 시도 (원문 인용)

- 처음부터 알던 조건: “앱 리뷰는 텍스트가 정돈돼 있지 않아 단순 키워드 매칭이 어려웠어요. 하나하나 맥락을 판단해 라벨을 붙여야만 했죠.”
- 경과: “첫 결과물은 키워드 기반으로 맵핑하는 수준이었는데요. ‘맥락 기준으로 분류할 방법은 없을까?’라는 Sofia의 질문에 Cursor는 OpenAI API 활용을 제안했어요. 그 결과물의 완성도도 부족해서 ‘예시 데이터를 학습해 줄 수 있을까?’라는 추가 요청을 하게 됐고, 끝내 유사도 기반 임베딩 방식을 도입하여 분류 정확도를 크게 개선할 수 있었어요.”

- 결과(자체 보고): “수작업으로 6시간 걸리던 업무는 3분으로 줄었고, 검수 시간을 포함하더라도 1시간 이내로 마칠 수 있게 됐어요.” 정확도 수치는 없다.

### 채점 메모

- ‘실제 문제와 일치’ 2점: 예시 없이 모델에게 맥락으로 분류만 시키면(키워드 다음 단계) 완성도가 부족하다는 점, 즉 지금까지 손으로 붙인 라벨을 예시로 써야 한다는 점을 발생 조건과 함께 짚었다.
- “키워드 매칭으로는 어렵다”만 말한 답은 입력의 제약을 되풀이한 것이라 이 항목 0점. 토스와 같은 원칙이다(Claude가 적용, 작성자 확인 전). 판별력은 따로 채점한다.
- 원문이 공개되어 있어 실행 모델이 이 사례를 기억할 수 있다.

| 항목 | 2점 기준 |
| --- | --- |
| 실제 문제와 일치 | 원문에서 관찰한 실패와 발생 조건을 짚었다. |
| 실험의 판별력 | 구현 전에 구할 샘플, 비교 대상, 가정을 기각할 관찰 결과가 구체적이다. |

규칙

# 초기 설계안: 앱 리뷰 자동 라벨링 도구

## 0. 먼저 짚을 점: 키워드 매핑으로 시작하는 방식은 바꾸는 게 좋습니다

말씀하신 제약("문장이 정돈되어 있지 않고 맥락 판단이 필요")과 "키워드 매핑으로 첫 도구를 만든다"는 방법은 서로 충돌합니다. 키워드 매핑은 다음 문제가 있습니다.

- 부정문·반어("결제 잘 되네요 ㅋㅋ 또 오류")를 구분하지 못합니다.
- 오타·줄임말·신조어마다 규칙을 계속 추가해야 합니다.
- 한 리뷰에 서비스가 여러 개 언급되면 오분류됩니다.
- 규칙을 유지보수하는 일이 결국 새로운 반복 업무가 됩니다.

**제안:** LLM(Claude API)에 리뷰와 라벨 정의를 주고 분류시키는 방식을 첫 도구로 삼으세요. 코딩 지식이 없어도 "라벨 정의 문서 + 예시"를 다듬는 것이 핵심 작업이라, 운영 담당자의 도메인 지식이 그대로 활용됩니다. 키워드 매핑은 정확도를 높이는 보조 수단(예: 서비스명 사전)으로만 남깁니다.

## 1. 목표와 성공 기준

| 항목 | 기준 |
|---|---|
| 시간 절감 | 월 6시간 → 1시간 이내 (검수 시간 포함) |
| 정확도 | 사람이 붙인 과거 라벨 대비 일치율 85% 이상 (라벨별로 따로 측정) |
| 안전장치 | 확신이 낮은 건은 "검수 필요"로 표시 |

## 2. 전체 구조 (단순하게)

```
[리뷰 파일(CSV/엑셀)] → [라벨링 스크립트] → [결과 CSV + 검수 필요 표시] → [사람이 검수] → [리포트/시각화]
                              ↑
                   [라벨 정의 문서 + 예시 모음]
```

- **입력:** 지금 쓰는 리뷰 데이터를 CSV로 내보낸 파일
- **처리:** 파이썬 스크립트 하나가 리뷰를 묶음(예: 20~50건)으로 LLM에 보내 세 가지 라벨과 확신도를 JSON으로 받음
- **출력:** 원본 열 + `관련 서비스`, `유형`, `세부 유형`, `확신도`, `검수필요` 열이 추가된 CSV
- **검수:** 확신도가 낮거나 라벨이 애매한 건만 사람이 확인
- 서버, DB, 웹 화면은 만들지 않습니다. 처음에는 내 컴퓨터에서 명령어 한 줄로 실행하는 수준이 적당합니다.

## 3. 핵심 자산: 라벨 정의 문서

도구의 품질은 코드보다 이 문서가 좌우합니다. 항목별로 다음을 적습니다.

- 라벨 이름 / 한 줄 정의 / 포함 예시 2~3개 / 헷갈리는 경계 사례와 판단 기준
- 허용되는 값 목록 (목록 밖 값은 출력 불가로 강제)
- 한 리뷰에 여러 서비스·유형이 있을 때의 규칙 (대표 1개만 선택? 복수 허용?)

## 4. 품질 관리

1. **정답 세트 만들기:** 이미 손으로 라벨링한 과거 리뷰 200~300건(라벨 골고루)을 따로 보관
2. **비교 측정:** 도구 결과와 정답을 비교해 라벨별 일치율과 자주 틀리는 패턴 확인
3. **개선 반복:** 틀린 사례를 정의 문서의 예시/규칙에 반영하고 다시 측정
4. **운영 중 표본 검수:** 매월 결과의 5~10%를 무작위로 확인

## 5. 단계별 계획

| 단계 | 내용 | 기간(예상) |
|---|---|---|
| 1 | 라벨 체계 정리 + 정답 세트 준비 | 2~3일 |
| 2 | 100건 정도로 시험 분류, 정확도 확인 | 2~3일 |
| 3 | 정의 문서 개선, 전체 데이터 처리 | 1주 |
| 4 | 검수 흐름 정착, 월간 리포트에 적용 | 1주 |

## 6. 위험 요소와 대응

- **개인정보:** 리뷰에 이름·연락처가 섞여 있을 수 있어, 외부 API 전송 전에 사내 정책을 확인하고 필요하면 마스킹합니다.
- **비용:** 월 리뷰 수 기준으로 사전에 추정합니다(보통 수천 건이면 부담이 크지 않음).
- **라벨 체계 변경:** 정의 문서를 수정하고 정답 세트로 다시 측정하면 됩니다. 코드 수정은 불필요합니다.
- **개발 경험 부족:** AI 코딩 도구에 "이 파일을 읽고 이 문서대로 분류해서 CSV로 저장하는 스크립트"처럼 작은 단위로 요청하고, 매번 직접 실행해서 확인합니다.

## 7. 구현 첫날 할 일

코드를 짜기 전에 **재료 준비**부터 합니다. 하루 안에 끝낼 수 있습니다.

1. **작업 폴더 만들기** (예: `review-labeler/`) 후 안에 `data/`, `docs/` 폴더 생성
2. **샘플 데이터 추출 (30분):** 과거에 손으로 라벨링한 리뷰 중 약 100건을 CSV로 저장. 라벨이 골고루 섞이게 선택하고 `data/sample_labeled.csv`로 저장
3. **라벨 목록 정리 (1~2시간):** 현재 쓰는 `관련 서비스`, `유형`, `세부 유형`의 전체 값 목록을 `docs/labels.md`에 정리. 각 값마다 한 줄 정의와 실제 리뷰 예시 1~2개를 붙임
4. **헷갈리는 사례 메모 (30분):** 라벨링하면서 자주 고민했던 경계 사례 5~10개와 당시 판단 기준을 적음
5. **AI 코딩 도구로 첫 스크립트 요청 (1시간):** 다음처럼 작게 시작
   > "`data/sample_labeled.csv`의 리뷰 열을 읽어서, `docs/labels.md` 기준으로 Claude API로 분류하고, 결과를 새 CSV로 저장하는 파이썬 스크립트를 만들어줘. 먼저 5건만 처리하게 해줘."
6. **5건 실행 후 눈으로 확인:** 정답과 비교해 어디서 틀렸는지 메모. 오늘의 목표는 정확도가 아니라 "끝까지 한 번 돌아가는 것"입니다.

**첫날 완료 기준:** 라벨 정의 문서가 있고, 5건이 자동으로 라벨링되어 CSV로 나오며, 틀린 사례 메모가 남아 있는 상태.

## 확인이 필요한 질문

- 월 리뷰 수는 대략 몇 건인가요? (비용·처리 방식 결정)
- 리뷰 데이터는 어디서 가져오나요? (스토어 콘솔 CSV, 외부 수집 도구 등)
- 사내에서 외부 AI API로 리뷰 데이터를 보내도 되는지 확인되었나요?

이 답변을 주시면 설계안을 더 구체화하고, 첫 스크립트 요청문도 맞춰서 작성해 드리겠습니다.

# 초기 설계안: 리뷰 자동 라벨링 도구

## 1. 핵심 판단

말씀하신 키워드 매핑은 제약(정돈되지 않은 문장, 맥락 판단 필요)과 맞지 않습니다. 그래서 **키워드 매핑을 주 방식으로 쓰지 않고, LLM 분류를 주 방식으로, 사람 검수를 안전장치로** 두는 설계를 제안합니다. 키워드는 보조(사전 필터, 검증용 기준선)로만 씁니다.

## 2. 구조

```
[리뷰 파일(CSV/엑셀)]
   → ① 전처리 (중복·빈 값 제거, ID 부여)
   → ② LLM 분류 (서비스 / 유형 / 세부 유형 + 확신도 + 근거 한 줄)
   → ③ 규칙 검증 (허용된 라벨 목록에 있는지, 유형-세부유형 조합이 유효한지)
   → ④ 확신도 낮은 건만 "검수 대기" 시트로 분리
   → ⑤ 사람이 검수 후 확정 → 월간 집계/시각화용 파일
```

핵심 요소:
- **라벨 정의서**: 서비스·유형·세부 유형 목록과 각 항목의 정의, 경계 사례, 대표 예시 2~3개. 이것이 프롬프트의 핵심 재료입니다.
- **고정 출력 형식**: 라벨은 정해진 목록에서만 고르게 하고 JSON으로 받습니다.
- **검수 결과 누적**: 사람이 고친 건은 예시로 쌓아 다음 달 프롬프트에 반영합니다.
- **기술 선택**: Python 스크립트 하나 + 엑셀/CSV 입출력. 서버·DB·화면은 만들지 않습니다.

## 3. 구현 첫날 할 일

코딩 전에 데이터와 기준부터 정리합니다.

1. **지금까지 손으로 붙인 라벨 데이터를 모읍니다.** 최근 2~3개월치면 충분합니다. 이것이 정답지가 됩니다.
2. **라벨 목록을 한 장으로 정리합니다.** 서비스, 유형, 세부 유형의 전체 목록과 헷갈리는 경계 기준을 적습니다.
3. **평가용 샘플 200건 정도를 따로 떼어 둡니다.** 서비스·유형별로 골고루 뽑고, 이 건들은 프롬프트 작성에 쓰지 않습니다.
4. **AI 코딩 도구에 "CSV를 읽고 LLM에 보내 라벨을 받아 CSV로 저장하는 스크립트"를 요청**해 20건으로 먼저 돌려 봅니다.
5. 리뷰에 개인정보(이름, 연락처 등)가 있는지, 외부 LLM API로 보내도 되는지 사내 규정을 확인합니다.

## 4. 뒤집히면 설계가 크게 바뀌는 가정

> **"기존 수작업 라벨이 일관되어서, 그것을 정답지로 삼을 수 있다."**

이 가정이 틀리면, 즉 사람끼리도(또는 과거의 나와 지금의 나도) 같은 리뷰에 다른 라벨을 붙인다면, 정확도를 측정할 기준이 없고 LLM 프롬프트로 개선할 수 있는 한계도 낮습니다. 그 경우 설계의 중심이 "분류기 만들기"에서 **"라벨 체계(특히 세부 유형)를 먼저 정리·단순화하기"**로 바뀝니다.

## 5. 가장 작은 실험

- **입력**: 이미 라벨을 붙인 리뷰 중 무작위 100건. 이 100건을 **2주 이상 간격을 두고 같은 사람이 다시 라벨링**합니다(처음 라벨은 가려 둡니다). 시간이 허락되면 동료 1명도 같은 100건을 라벨링합니다. 약 1~1.5시간 분량입니다.
- **비교 대상**: 기존 라벨 vs 재라벨(자기 일치도), 가능하면 동료 라벨과도 비교. 별도로 LLM 결과 vs 기존 라벨도 같은 100건으로 확인합니다.
- **실패로 판단할 관찰 결과** (수치는 임시 기준이며, 첫 결과를 보고 조정합니다):
  - 서비스 라벨 일치율이 90% 미만이거나, 유형 일치율이 80% 미만, 세부 유형 일치율이 70% 미만이면 정답지로 쓰기 어렵다고 판단합니다.
  - 불일치가 특정 라벨 쌍(예: A유형↔B유형)에 몰려 있다면, 사람이 일관되지 않다는 뜻이 아니라 **그 라벨 정의가 모호하다는** 신호입니다.

(참고: LLM-기존 라벨 일치율이 낮아도 사람 자기 일치율이 높다면 문제는 프롬프트 쪽이고, 둘 다 낮으면 라벨 체계 쪽 문제입니다.)

## 6. 실패 시 대응

**직접 시도할 조치 (사용자 결정 불필요)**
- 불일치가 몰린 라벨 쌍을 뽑아 정의서에 경계 기준과 예시를 추가하고, 같은 100건으로 재측정
- LLM 프롬프트에 라벨별 예시를 넣고, 낮은 확신도 건을 검수로 보내는 기준 조정
- 분류를 한 번에 하지 않고 서비스 → 유형 → 세부 유형 순서로 나눠 정확도 비교
- 정답지에서 불일치 건을 제외한 "깨끗한 부분집합"으로 LLM 성능을 따로 측정

**사용자 결정이 필요한 조건**
- 세부 유형을 합치거나 삭제해야 할 때 (리포트 형식과 구성원이 보는 지표가 바뀜)
- 어떤 라벨은 자동화하지 않고 계속 수작업으로 남기기로 할 때
- 리뷰를 외부 LLM API로 보내는 것이 규정상 불가하거나 승인이 필요할 때
- 목표 정확도(예: "검수 후 월 1시간 이내")를 현실에 맞게 낮추거나, 비용 상한을 정해야 할 때
- 자기 일치율이 낮아 라벨 체계를 재설계해야 하는 경우, 과거 월간 리포트와의 연속성을 포기할지

## 7. 키워드 방식에 대한 보완

키워드 매핑은 버리기보다 **기준선**으로 씁니다. 같은 평가 샘플에서 키워드 방식과 LLM 방식의 정확도를 비교해 두면, LLM이 실제로 낫다는 근거가 생기고 월 6시간 → 검수 1~2시간이라는 목표 대비 효과도 숫자로 보여줄 수 있습니다.
