당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

보안 연구 담당자입니다. 회사에는 서비스가 수백 개 있고, 대부분 상당한 규모의 소스코드를 가지고 있습니다. LLM이 서비스 소스코드를 직접 분석해서 보안 취약점을 찾아 주는 자동화를 만들고 싶습니다. LLM이 스스로 소스코드를 분석해 취약점을 찾는 외부 연구 결과를 보고 가능성이 있다고 판단했고, 사내의 작은 프로젝트 모임으로 시작했습니다. 새로 공부할 기술은 많고 쓸 수 있는 자원은 한정되어 있습니다.

제약: 서비스 소스코드가 커서 전체 코드를 한 번에 LLM에 넣기 어렵습니다.

지금 검토 중인 방법: 코드를 벡터로 임베딩해 필요한 부분만 가져오는 방식, 또는 저장소 전체를 하나로 압축해 모델에 넣는 방식.

## 평가자용 기록

### 관찰한 실패와 발생 조건 (원문 #1 인용)

1. 벡터 검색: “코드를 벡터로 임베딩해서 필요한 부분만 가져오는 방식이었는데, 코드 간 연관관계를 제대로 파악하기 어려웠어요.”
2. 저장소 압축: “Repomix 같은 툴로 전체 소스코드를 압축해서 던져주는 것도 시도해 봤습니다. 하지만 결국 모든 시도가 토큰 문제로 실패” — 실행 입력의 제약과 같은 내용이다.
3. 정보 과다로 인한 환각: “설사 토큰 Context Size 안에 맞춘다고 해도 더 큰 문제가 있었어요. 바로 Hallucination이었습니다. 너무 많은 정보를 한 번에 처리하다 보니 LLM이 실제로는 없는 취약점을 만들어내거나, 코드의 흐름을 잘못 이해하는 경우가 빈번했거든요.”
4. 실행마다 다른 결과(코드 참조 문제를 푼 뒤): “XSS 취약점이 총 10개 있으면, 어떨 때는 8개만 찾고 2개를 빼먹고, 어떨 때는 10개를 다 찾기도 하고, 심지어 9개를 찾았다가 다시 돌리면 7개만 찾기도 하는 등 결과에 일관성이 없었어요.” (모델 Claude-Sonnet-4)

### 후속 시도와 결과

| 순서 | 시도 | 결과 (원문) |

### 채점 메모

- ‘실제 문제와 일치’ 2점: 잘라서 가져오는 검색이 코드 사이의 관계(호출·데이터 흐름)를 놓친다는 점, 또는 한꺼번에 많이 넣으면 없는 취약점을 만들거나 흐름을 잘못 읽는다는 점, 또는 같은 코드에서 실행마다 결과가 달라진다는 점을 발생 조건과 함께 짚었다.

- 원문이 공개되어 있어 실행 모델이 이 사례를 기억할 수 있다.

| 실험의 판별력 | 구현 전에 구할 샘플, 비교 대상, 가정을 기각할 관찰 결과가 구체적이다. |

규칙

- 응답이 여러 제안을 하면 결과와 맞는 것을 골라 쓰지 말고 응답이 밝힌 최우선 제안 하나를 채점한다. 우선순위가 없으면 처음 제시한 행동을 쓴다.

- 평가자용 기록에 없던 실패를 예상했어도 실험의 판별력은 독립적으로 채점한다.
- 사례 입력에 이미 적힌 제약을 되풀이한 것만으로는 ‘실제 문제와 일치’ 점수를 주지 않는다(평가자용 기록의 채점 메모 참고).

# 초기 설계안: LLM 기반 소스코드 취약점 분석 자동화

## 1. 핵심 판단: 두 후보 방식에 대하여

**임베딩 검색(RAG)과 저장소 통째 압축은 둘 다 1순위로 권하지 않습니다.**

| 방식 | 문제점 |
|---|---|
| 벡터 임베딩 검색 | 취약점은 "의미상 유사한 코드"가 아니라 **데이터 흐름**(입력 → 가공 → 위험 함수)에 있음. 유사도 검색은 source와 sink가 서로 다른 파일에 있을 때 연결을 놓침. 청킹, 인덱싱, 갱신 인프라도 별도로 필요함 |
| 저장소 압축 후 투입 | 컨텍스트 한도를 넘는 저장소가 다수일 것이고, 들어가더라도 긴 컨텍스트에서 정확도와 비용이 나빠짐. 수백 개 서비스에 반복하면 비용이 큼 |

**대안: 에이전트형 탐색 + 전통 정적 분석 도구의 결합.** LLM에게 코드를 "넣어 주는" 대신, LLM이 `grep`, 파일 읽기, 심볼 정의/참조 조회 같은 도구로 **필요한 부분을 스스로 찾아 읽게** 합니다. 외부 연구에서 성과를 보인 방식도 대체로 이 형태입니다. 사람 연구원이 코드를 읽는 방식과 같아서 대용량 코드 문제가 자연스럽게 해소됩니다.

## 2. 아키텍처

```
[서비스 저장소 목록]
      │
      ▼
① 트리아지/우선순위 (어떤 서비스부터?)
      │
      ▼
② 공격 표면 매핑 (엔트리포인트 추출)
   - HTTP 라우트, RPC 핸들러, 큐 컨슈머, 파일 파서 등
   - 정규식/tree-sitter/프레임워크별 규칙으로 결정적(deterministic)으로 추출
      │
      ▼
③ 후보 생성 (저비용)
   - Semgrep/CodeQL 등 기존 SAST 결과 + 위험 sink grep
   - 엔트리포인트 × 위험 sink 쌍을 "분석 단위"로 쪼갬
      │
      ▼
④ LLM 에이전트 분석 (분석 단위별, 컨텍스트 작게)
   - 도구: read_file, grep, find_definition, find_references, list_dir
   - 출력: 구조화된 가설 (취약점 유형, 경로, 근거 코드 위치, 신뢰도)
      │
      ▼
⑤ 검증 (오탐 제거)
   - 별도 LLM 패스로 반증 시도 (sanitizer, 인증, 도달 불가 여부)
   - 가능하면 샌드박스에서 PoC 실행으로 확인
      │
      ▼
⑥ 리포트/중복제거/사람 리뷰 큐
```

**핵심 설계 원칙**
- **분석 단위를 작게**: 저장소 단위가 아닌 "핸들러 1개 + 그 호출 체인" 단위로 실행. 컨텍스트 문제를 구조적으로 회피.
- **결정적 단계와 LLM 단계 분리**: 매핑·후보 생성은 싼 도구로, LLM은 판단이 필요한 곳에만 사용.
- **구조화 출력 + 근거 필수**: 파일/라인 인용이 없는 발견은 자동 폐기.
- **검증 단계를 별도로 둠**: 오탐률이 이 프로젝트의 성패를 가름. 연구원이 오탐에 지치면 프로젝트가 죽음.

## 3. 임베딩은 언제 쓰나

초기에는 쓰지 않습니다. 에이전트가 grep/정의 조회로 부족하다는 것이 **측정으로 확인될 때** 보조 도구(`semantic_search`)로 추가하세요. 그 시점에도 하나의 도구일 뿐, 아키텍처의 중심이 아닙니다.

## 4. 자원 한정 환경에서의 전략

- **새 기술 학습 최소화**: 직접 만들 것은 에이전트 루프와 평가 하네스 정도. 정적 분석(Semgrep 등)과 LLM 에이전트 SDK는 기성품 활용.
- **서비스 소수로 시작**: 수백 개 전체가 아니라 3~5개 대표 서비스(언어/프레임워크 다양하게, 가능하면 외부 노출도 높은 것)로 시작.
- **정답 데이터 확보**: 과거 사내 취약점 리포트, 모의해킹 결과, 버그바운티 건을 **재현 벤치마크**로 사용. 없으면 공개 취약 앱(예: OWASP Juice Shop 등)이나 CVE 패치 전 커밋을 보조로 사용.
- **비용 통제**: 분석 단위별 토큰/도구 호출 상한, 결과 캐시, 변경분(diff)만 재분석.
- **보안 거버넌스**: 소스코드가 외부 API로 나가므로 사내 정책, 계약(데이터 보존/학습 미사용), 또는 사내 호스팅/전용 엔드포인트 여부를 **초기에** 확인. 이것이 막히면 모든 게 막힘.

## 5. 성공 지표

- 재현율: 벤치마크의 알려진 취약점 중 몇 개를 찾는가
- 정밀도: 사람 리뷰 후 진짜 취약점의 비율 (목표 예: 리뷰 큐 항목의 30% 이상 유효)
- 비용: 서비스당, 유효 발견당 비용
- 리뷰 시간: 발견 1건당 사람이 소비하는 시간

## 6. 구현 첫날 제안

목표: **"한 서비스, 한 취약점 유형, 끝까지 한 번 돌려보기"** (얇은 수직 슬라이스)

1. **(오전, 1~2시간) 선결 조건 확인**
   - 외부 LLM API로 소스코드 전송 가능한지 보안/법무 정책 확인 (불가 시 대안 경로 조기 확정)
   - 모임 구성원 간 역할 분담: 평가 데이터 담당 / 에이전트 담당 / 인프라 담당

2. **(오전) 대상 선정**
   - 서비스 1개 선택: 중간 규모, 알려진 취약점 이력이 있는 것(정답이 있어야 평가 가능), 팀 대부분이 읽을 수 있는 언어
   - 해당 서비스의 과거 취약점 3~5건을 정답 목록으로 정리 (취약 파일/함수/유형)

3. **(오후) 가장 단순한 에이전트 프로토타입**
   - 에이전트 SDK로 도구 3개만 제공: `grep`, `read_file`, `list_dir` (읽기 전용, 샌드박스/읽기 전용 마운트)
   - 프롬프트: "이 핸들러에서 시작해 사용자 입력이 도달하는 위험 sink를 추적하고 SQL 인젝션/인증 누락 중 하나를 판단하라. 근거 파일·라인을 인용하라."
   - 출력 JSON 스키마 고정 (유형, 위치, 근거, 신뢰도)

4. **(오후 늦게) 첫 결과 평가**
   - 알려진 취약점 몇 개를 찾았는지, 오탐은 어떤 유형인지 수기 분류
   - 실패 사례 목록을 만들어 다음 주 우선순위로 삼음(예: 호출 체인 추적 실패 → `find_references` 도구 추가)

5. **(마감) 기록**
   - 사용한 프롬프트, 모델, 토큰 비용, 소요 시간, 결과를 1페이지로 기록. 이후 모든 개선을 이 기준선과 비교.

**첫날에 하지 말 것**: 임베딩 파이프라인 구축, 전 서비스 대상 실행, 인프라/스케줄러/대시보드 작업, 파인튜닝.

## 7. 이후 로드맵 (요약)

- **주 2~3**: 엔트리포인트 매핑 자동화, SAST 결과 연동, 검증(반증) 패스 추가
- **주 4~6**: 취약점 유형 확장, 3~5개 서비스로 확대, 정밀도/비용 측정 리포트
- **이후**: 변경분 기반 CI 연동, 서비스 우선순위 스코어링, 필요 시 임베딩 보조 검색 도입

원하시면 다음으로 (a) 에이전트 프롬프트와 출력 스키마 초안, (b) 평가 벤치마크 구성 방법, (c) 엔트리포인트 추출 규칙 예시 중 하나를 구체화해 드릴 수 있습니다.

## 응답 R-23CD

# 초기 설계안

## 0. 설계 원칙

두 후보(임베딩 검색, 저장소 통째 압축)는 둘 다 "코드를 어떻게 모델에 넣을까"에 대한 답입니다. 그런데 취약점 탐지에서 중요한 것은 **source(외부 입력) → sink(위험 함수)로 이어지는 데이터 흐름을 따라가는 것**입니다. 이 흐름은 의미적으로 비슷한 코드 조각을 모은다고 얻어지지 않고, 압축한다고 보존되지도 않습니다. 그래서 다음 구조를 제안합니다.

> **LLM이 코드베이스를 에이전트처럼 탐색한다 (grep, 파일 열기, 정의/호출 지점 찾기). 사전 분석으로 후보 지점을 좁혀서 탐색의 출발점을 준다.**

임베딩 인덱스와 전체 압축은 1차 설계에서 제외하고, 실험으로 필요성이 확인되면 추가합니다.

## 1. 파이프라인

```
[서비스 선별] → [진입점/위험 지점 추출] → [후보 단위 생성]
      → [LLM 에이전트 분석 (도구로 코드 탐색)]
      → [재현/검증] → [중복 제거·심각도] → [사람 검토 큐]
```

1. **서비스 선별**: 수백 개를 한꺼번에 다루지 않습니다. 인터넷 노출, 민감 데이터 처리, 언어/프레임워크 동질성 기준으로 3~5개 파일럿 서비스를 고릅니다.
2. **진입점/위험 지점 추출 (결정적 도구)**: 라우트 핸들러, 외부 입력 수신부, 위험 sink(SQL 실행, 명령 실행, 역직렬화, 파일 경로, HTTP 요청, 인증/인가 체크 등)를 tree-sitter, Semgrep, CodeQL 등으로 뽑습니다. 이미 사내에 SAST가 있으면 그 결과도 재활용합니다.
3. **후보 단위 생성**: "핸들러 하나 + 호출 체인 몇 단계"처럼 모델이 한 번에 다룰 수 있는 작업 단위로 쪼갭니다. 전체 저장소가 아니라 이 단위가 분석의 기본 입력입니다.
4. **LLM 에이전트 분석**: 후보 단위를 주고, 모델이 도구(파일 읽기, 심볼 검색, 호출자/피호출자 조회, grep)로 필요한 코드를 직접 찾아보며 "취약한가"를 판단하게 합니다. 출력은 구조화된 형식(근거 코드 위치, 입력 경로, 악용 시나리오, 확신도)으로 강제합니다.
5. **검증**: 가능하면 PoC 또는 테스트 요청을 만들어 격리된 환경에서 실행합니다. 불가능하면 두 번째 LLM 호출이 반증을 시도하게 합니다.
6. **사람 검토 큐**: 보고서 형식으로 정리하고, 검토 결과(참/거짓 양성)를 기록해 다음 반복의 평가 데이터로 씁니다.

## 2. 두 후보 방식에 대한 판단

| 방식 | 장점 | 약점 |
|---|---|---|
| 임베딩 검색 | 구현이 쉽고 규모 확장에 유리 | 취약점은 "비슷한 코드"가 아니라 "연결된 코드"에 있음. 검색 결과가 호출 체인을 끊음. 청킹·인덱스 관리 비용 |
| 저장소 전체 압축 | 아이디어가 단순 | 압축하면 세부(검증 누락, 조건 분기)가 사라지고, 사라진 부분이 바로 취약점인 경우가 많음. 압축 후에도 크기 한계 |
| 에이전트형 탐색 + 정적 분석 (제안) | 실제 보안 연구자의 작업 방식과 동일, 근거 위치 추적 가능 | 토큰·시간 비용이 크고, 탐색 품질이 모델에 좌우됨 |

임베딩은 "이 서비스에서 인증 관련 코드가 어디인가" 같은 탐색 보조로는 쓸모가 있으므로, 에이전트의 도구 중 하나로 나중에 추가할 수 있습니다.

## 3. 평가 체계 (가장 먼저 필요)

자동화를 만들기 전에 "좋은지 나쁜지"를 재는 방법이 있어야 합니다.

- **정답 세트**: 과거 사내 취약점 리포트, 버그바운티 건, 모의해킹 결과 중 코드 위치가 특정되는 것을 모읍니다. 가능하면 수정 전 커밋을 기준 코드로 씁니다.
- **지표**: 재현율(알려진 취약점을 몇 개 찾는가), 정밀도(보고된 것 중 실제 취약점 비율), 건당 비용, 건당 검토 시간.
- **기준선**: 기존 SAST 결과와 비교합니다. LLM이 SAST가 못 찾는 것을 찾아야 의미가 있습니다.

## 4. 구현 첫날 계획

목표는 "완성된 시스템"이 아니라 **하나의 서비스에서 알려진 취약점 하나를 모델이 찾는지 보는 것**입니다.

1. (오전) 파일럿 서비스 1개와, 코드 위치가 확실한 과거 취약점 3~5건을 고릅니다. 수정 전 커밋을 체크아웃합니다.
2. (오전) 서비스 규모를 측정합니다: 파일 수, 토큰 수, 언어, 진입점 수. 이 숫자가 이후 설계 판단의 근거입니다.
3. (오후) 가장 단순한 에이전트를 만듭니다. 파일 목록, 파일 읽기, grep 세 가지 도구만 주고, "이 서비스의 보안 취약점을 찾아라"가 아니라 "이 핸들러 하나를 분석하라"고 지시합니다.
4. (오후) 알려진 취약점이 있는 핸들러에서 실행해 결과를 사람이 읽고, 어디서 막히는지 기록합니다.
5. (저녁) 실험 결과를 정리해 다음 단계(정적 분석 연동, 평가 자동화)의 우선순위를 정합니다.

임베딩, 압축, 대규모 병렬화는 첫날 하지 않습니다.

## 5. 뒤집히면 설계가 크게 바뀌는 가정 하나

> **가정: "핸들러 하나 + 모델이 스스로 탐색한 주변 코드"만으로도 알려진 취약점을 찾을 수 있다. 즉, 취약점 판단에 필요한 맥락이 후보 단위 주변에서 도구 탐색으로 회수 가능하다.**

틀리면 (취약점이 서비스 간 호출, 설정 파일, 프레임워크 미들웨어, 인프라 정책 등 먼 곳의 맥락에 의존한다면) 후보 단위 중심 설계 자체가 무너지고, 서비스 전체의 구조 모델(아키텍처 요약, 서비스 간 신뢰 경계, 전역 호출 그래프)을 먼저 만드는 설계로 바뀝니다. 비용 구조도 달라집니다.

## 6. 가장 작은 실험

- **입력**: 파일럿 서비스 1개의 수정 전 커밋, 알려진 취약점 5건(유형이 섞이도록: 인젝션, 인가 누락, 경로 조작 등). 각 건마다 해당 핸들러(진입점)만 지정해서 줍니다. 모델에는 파일 목록/읽기/grep 도구만 제공합니다. 정답 위치는 알려주지 않습니다.
- **비교 대상**:
  - (A) 핸들러 코드만 주고 도구 없이 분석 (맥락 없음)
  - (B) 핸들러 + 도구 탐색 (제안 방식)
  - (C) 취약점 수정 커밋에서 사람이 판단한 "필요 맥락 파일"을 모두 직접 넣어줌 (상한선)
  
  B가 A보다 얼마나 낫고, C에 얼마나 가까운지를 봅니다. 각 조건은 3회 반복해 변동성을 확인합니다.
- **실패 판정** (사전에 정해 둡니다):
  - B가 5건 중 2건 미만을 찾고, **C는 4건 이상 찾는 경우** → 모델 능력이 아니라 맥락 회수가 병목이라는 뜻이므로 가정이 틀림.
  - 또는 B의 실패 원인을 읽어 보았을 때 절반 이상이 "필요한 파일을 열지 않았다/찾지 못했다"인 경우.
  - 참고: C도 2건 미만이면 가정 이전에 모델 또는 프롬프트의 문제이므로 별도로 다룹니다. 이 경우는 맥락 설계 문제가 아닙니다.

## 7. 실패했을 때: 직접 시도할 조치와 사용자 결정이 필요한 조건

**제가 직접 시도할 수 있는 조치** (사용자 승인 없이 진행 가능한 범위)
- 도구 확장: 심볼 정의/참조 조회, 호출자 조회 도구 추가 후 재실험
- 프롬프트 개선: 체크리스트(입력 경로, 검증 위치, 인가 확인 지점) 제공
- 후보 단위 확장: 호출 체인 깊이를 늘려 미리 묶어서 제공
- 임베딩 검색을 도구 하나로 추가해 B와 비교
- 실패 사례 분류 (맥락 부족 / 추론 오류 / 형식 문제) 후 보고
- 위 조치를 같은 5건에서 재측정

**사용자 결정이 필요한 조건**
- 서비스 코드를 외부 LLM API로 보내도 되는지 (보안·법무 정책), 또는 사내 호스팅 모델만 써야 하는지. 이는 실험 이전에 확인이 필요합니다.
- 서비스 간 맥락이 필요해서 여러 저장소 접근 권한이나 인프라 설정 열람이 필요한 경우
- 조치를 해도 B가 C에 크게 못 미쳐서 전역 구조 모델 구축(큰 설계 변경, 수 주 단위 투자)으로 전환할지 여부
- 비용 한도: 건당 토큰 비용이 예산 가정을 넘을 때 범위를 줄일지 결정
- PoC 실행을 위한 격리 환경 확보 (스테이징 접근, 네트워크 정책)
- 정답 세트로 쓸 과거 취약점 정보의 열람 권한

## 8. 오늘 확인이 필요한 질문

1. 사용 가능한 모델/API와 코드 외부 전송 허용 여부
2. 주 언어와 프레임워크 (정적 분석 도구 선택에 영향)
3. 사내 기존 SAST·모의해킹 결과가 있는지, 정답 세트로 쓸 수 있는지
4. 팀 규모와 첫 마일스톤 기한
