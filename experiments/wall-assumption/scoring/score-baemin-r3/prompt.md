당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

사내 구성원의 데이터 질문에 답하는 AI 서비스를 운영하는 데이터팀입니다. 지금 서비스는 질문을 SQL로 바꿔 데이터를 조회하고, 테이블 정의·메타데이터·SQL 예시를 검색해 답하는 검색 기반 서비스입니다.

최근 질문이 데이터 조회를 넘어 사내 전반의 지식으로 넓어졌습니다. 예를 들어 업무 용어의 뜻, 회사 주소, 특정 업무의 담당자, 사내 프로젝트 설명, 서비스 성과 분석을 묻습니다. 이런 정보는 사내 포털, 위키, 이슈 관리 도구, 메신저 대화, 문서 저장소에 흩어져 있고, 각 도구의 기본 검색은 키워드 매칭이라 문서 목록만 보여 줍니다. 메신저에는 업무 지원 채널이 수백 개 있고, 담당자가 같은 질문에 여러 번 답합니다.

목표: 사내 지식 전반에 대한 질문에 한 곳에서 답한다. 이전 대화를 이어서 답한다. 불만족스러운 답이 나오면 바로 개선할 수 있게 한다. 반복되는 지원 채널 문의도 자동으로 응대한다.

초기 설계: 지금처럼 개발자가 처리 순서를 정한 워크플로(예: 검색 → 요약 → 검색 → 답변)에 새 지식 소스를 붙여 넓힌다. 지원 채널은 미리 등록한 질문–답변 쌍을 키워드로 찾아 답하는 FAQ 자동응답으로 시작한다.

## 평가자용 기록

### 관찰한 실패와 발생 조건 (원문 인용)

1. 고정된 처리 순서: “초기에는 이러한 복합 요청을 단일 워크플로우로 처리했습니다(예: RAG → 요약 → RAG → 답변). 그러나 이 방식은 개발자가 설계한 순서에만 의존했기 때문에 새로운 질문이 등장할 때마다 코드를 수정해야 하는 비효율적이고 유지보수 불가능한 구조로 이어졌습니다.”
2. 대화 맥락 상실(지식 확장 뒤): “한 번의 질문(single-turn)에는 정확하게 답했지만, 이전 대화의 맥락을 기억하지 못해 후속 질문(multi-turn)에서는 일관성이 깨지는 ‘기억 상실’ 문제가 생긴 것입니다.” 원인: “LLM API 호출 요청에는 오직 직전 질문만 포함되었기 때문입니다.” (이전 대화를 잇는 것은 입력의 목표에 있다)
3. 나쁜 답의 원인을 모름: “사용자 만족도 피드백(👍/👎)만으로 문제의 존재는 확인할 수 있었지만, 정작 왜 그런 답변이 나왔는가?를 실시간으로 파악하기는 어려웠습니다.” “같은 질문이라도 답변이 매번 조금씩 달라졌습니다. 설령 로그를 확보하더라도 동일한 조건에서 같은 답변 과정을 재현하기가 거의 불가능했습니다.”
4. 저장한 지식의 한계: “저장 대상이 아니거나 저장 주기 외의 최신 데이터는 반영되지 않아 오늘 새로 등록된 Jira 티켓이나 방금 올라온 Wiki 문서와 같은 실시간 정보는 찾을 수 없었습니다.” 이미지로 된 정책 문서는 텍스트 검색으로 찾을 수 없었다. 위키 문서가 너무 많았다.
5. 외부 연결의 불안정: “외부 서버에 대한 의존은 불안정성을 동반했습니다.”
6. 키워드 FAQ: “FAQ 시스템은 키워드 매칭 기반이기 때문에 질문 변형에 대해 제대로 인식하지 못했습니다.” “‘로그인이 안 돼요’처럼 맥락이 필요한 질문은 처리하기 어려웠습니다.” “FAQ 문서를 지속적으로 업데이트하는 일도 쉽지 않았습니다.”

# 사내 지식 QA 서비스 초기 설계안

## 1. 제안 설계안의 문제

| 항목 | 문제 |
|---|---|
| 고정 워크플로에 소스 추가 | 질문 유형이 열려 있습니다(용어, 주소, 담당자, 프로젝트, 성과 분석). 소스가 늘수록 분기와 조합이 폭발하고, "검색→요약→검색→답변" 순서가 맞지 않는 질문이 계속 생깁니다. |
| 키워드 FAQ 자동응답 | 기존 도구 검색의 한계(키워드 매칭)를 그대로 반복합니다. 표현이 조금만 달라도 못 찾고, 수작업 등록 FAQ는 금방 낡습니다. 수백 개 채널 규모에서는 관리가 불가능합니다. |
| 개선 방식 | 불만족 답변을 고치려면 개발자가 워크플로를 수정해야 해서 "바로 개선"이 어렵습니다. |

**결론:** 확정된 경로(질문 → SQL 조회)는 워크플로로 두고, 열린 질문은 도구를 가진 에이전트가 검색 경로를 스스로 정하게 합니다. 지원 채널은 과거 해결 스레드에서 지식을 자동으로 만들고, 사람이 검수하는 단계적 방식으로 갑니다.

## 2. 전체 구조

```
사용자(웹/메신저 봇)
   │
[대화 계층] 세션 저장, 후속 질문 재작성(대명사·생략 보완)
   │
[에이전트 루프] ── 도구 호출을 반복하며 근거 수집, 부족하면 재검색
   │   ├─ search_wiki / search_portal / search_issue / search_docs
   │   ├─ search_messenger (공개 채널, 해결된 스레드 위주)
   │   ├─ find_owner (담당자 조회: 문서 소유자, 이슈 담당자, 채널 답변 빈도)
   │   ├─ text_to_sql (기존 서비스를 도구로 감쌈)
   │   └─ get_table_metadata (기존 검색 재사용)
   │
[답변 생성] 출처 링크 필수, 근거 없으면 "모르겠다"와 담당자 안내
   │
[트레이스 저장] 질문, 도구 호출, 검색 결과, 답변, 사용자 피드백
```

### 인덱싱 계층 (소스 공통)
- 소스별 커넥터가 공통 스키마로 정규화합니다: `source, url, title, body, owner, updated_at, acl, type`.
- 검색은 하이브리드(키워드 + 임베딩)에 리랭커를 붙입니다. 사내 고유 용어와 약어는 키워드가 강하고, 의미 질문은 임베딩이 강합니다.
- 사내 용어집(약어, 서비스명, 별칭)을 쿼리 확장에 사용합니다.
- 최신성 메타(`updated_at`)를 랭킹과 답변에 반영해, 오래된 문서는 "N년 전 문서"라고 표기합니다.

### 권한
- 검색 시점에 질문자 권한(ACL)으로 필터링합니다. 비공개 채널과 문서는 권한이 없으면 근거로 쓰지 않습니다.
- 메신저는 공개 채널부터 시작하고, 개인정보는 인덱싱 전에 마스킹합니다.
- 초기부터 넣어야 합니다. 나중에 붙이면 구조를 갈아엎게 됩니다.

### 성과 분석 질문
SQL 조회와 문서 검색(지표 정의, 프로젝트 배경)을 에이전트가 함께 호출합니다. 지표 정의 문서를 먼저 찾고 SQL을 생성하면 정확도가 올라갑니다.

## 3. 이전 대화 이어가기
- 세션별 최근 N턴과 요약을 저장하고, 매 턴 "독립 질문"으로 재작성한 뒤 검색합니다.
- 사용자 장기 메모리(소속, 관심 서비스)는 2단계로 미룹니다. 권한 및 개인정보 이슈가 있습니다.

## 4. 바로 개선할 수 있는 구조
1. 모든 응답에 👍/👎와 사유(틀림, 오래됨, 못 찾음, 권한)를 받습니다.
2. 트레이스를 보고 실패 원인을 분류합니다: 문서 없음, 검색 실패, 잘못된 도구 선택, 생성 오류.
3. 실패 사례는 **평가셋**에 추가하고, 프롬프트, 도구 설명, 용어집 변경 후 회귀 테스트를 돌립니다.
4. 대부분의 수정은 코드 배포 없이 설정으로 해결되게 합니다: 용어집, 도구 설명, 우선 소스, 정정 답변(오버라이드).
5. 답변 하단에 "이 답변 정정하기"를 두고, 담당자가 정정하면 검증된 지식 항목으로 우선 검색되게 합니다.

## 5. 지원 채널 자동 응대 (단계적)
1. **학습 대상 구성:** 채널별 스레드에서 "질문 → 담당자 답변 → 해결 표시(✅, 감사 인사 등)" 쌍을 자동 추출하고, 유사 질문을 군집화해 반복 빈도를 계산합니다.
2. **검색:** 키워드 매칭이 아니라 의미 검색으로 과거 해결 스레드와 관련 문서를 찾아 답변을 합성하고, 원 스레드 링크를 붙입니다.
3. **신뢰도 게이트:** 유사도, 근거 일치, 최신성으로 점수를 매깁니다.
   - 낮음: 응답하지 않고 담당자에게 넘깁니다.
   - 중간: **담당자에게 초안 제안**(담당자가 승인/수정 후 게시)
   - 높음: 자동 응답. 단, 반복 빈도가 높고 위험이 낮은 유형부터 시작합니다.
4. **학습 루프:** 담당자의 수정과 승인이 곧 라벨입니다. 이를 다시 지식과 평가셋에 반영합니다.
5. 자동 응답에는 "봇 답변, 틀리면 👎 또는 담당자 호출" 버튼을 둡니다.

## 6. 단계별 로드맵
| 단계 | 내용 |
|---|---|
| 0 (1~2주) | 질문 로그 분석, 평가셋, 트레이스 로깅, 소스 2개와 에이전트 PoC |
| 1 | 소스 확대, 하이브리드 검색, 권한 필터, 대화 이어가기, 피드백 UI |
| 2 | 지원 채널 2~3곳에서 초안 제안 모드(섀도우) |
| 3 | 고신뢰 유형만 자동 응답, 담당자 정정 루프, 대시보드 |

## 7. 위험과 대응
- **환각:** 근거 인용 필수, 근거가 없으면 거절하고 담당자를 안내합니다.
- **권한 유출:** 검색 단계에서 ACL을 적용하고, 권한 테스트를 평가셋에 포함합니다.
- **오래된 정보:** 최신성 표기, 정정 오버라이드, 담당자 재검증 알림을 둡니다.
- **에이전트 비용과 지연:** 도구 호출 횟수 상한, 단순 질문은 단일 검색 경로, 캐시를 둡니다.
- **오답 자동 응대로 인한 신뢰 하락:** 섀도우 → 초안 → 자동 순으로 단계를 지킵니다.

# 구현 첫날 제안

**목표:** 코드를 많이 쓰기보다, 무엇을 만들고 어떻게 좋아졌는지 판단할 근거부터 확보합니다.

### 오전: 현실 파악
1. **질문 로그 수집 및 분류 (약 100~200건).** 최근 질문을 유형별로 나눕니다: 용어, 주소/정책, 담당자, 프로젝트, 성과 분석, 데이터 조회, 기타. 각 유형이 어떤 소스에 답이 있는지도 표시합니다. 이것으로 **먼저 붙일 소스 2개**를 정합니다. 예를 들면 위키와 이슈 관리 도구입니다.
2. **지원 채널 반복 문의 규모 측정.** 메신저 API로 상위 채널 3~5개의 최근 3개월 스레드를 내려받아, 질문 수, 담당자 답변 비율, 반복 유사 질문 비율을 간단히 계산합니다. 자동 응대의 우선순위와 기대 효과를 여기서 정합니다.
3. **보안 확인.** 접근 가능한 데이터 범위, 비공개 채널 처리, 개인정보 마스킹 원칙을 보안 담당자와 합의합니다.

### 오후: 최소 뼈대
4. **평가셋 v0.** 분류한 질문 중 30~50개에 정답 또는 정답 문서를 사람이 붙입니다. 이것이 이후 모든 변경의 기준입니다.
5. **트레이스 로깅.** 질문, 도구 호출, 검색 결과, 답변, 피드백을 한 레코드로 저장합니다. 이것이 "바로 개선"의 기반입니다.
6. **기존 text-to-SQL을 도구로 감싸기.** 입력과 출력 인터페이스만 정의합니다.
7. **커넥터 1개 + 하이브리드 인덱스.** 가장 질문이 많은 소스 하나를 공통 스키마로 인덱싱하고, 검색 도구 하나로 노출합니다.
8. **최소 에이전트 루프.** 도구 2~3개를 가진 루프를 만들고, 평가셋으로 첫 베이스라인 점수를 기록합니다.

### 첫날 종료 시 산출물
- 질문 유형 분포표와 소스 우선순위
- 지원 채널 반복 문의 통계
- 평가셋 v0와 베이스라인 점수
- 트레이스가 쌓이는 최소 동작 에이전트 (소스 1개 + SQL 도구)

이후 며칠은 소스를 하나씩 추가하며 평가 점수 변화를 확인하고, 지원 채널은 섀도우 모드로 먼저 붙이는 순서를 권합니다.

# 초기 설계안

## 1. 설계 원칙

제시하신 초기 설계(고정 워크플로 + FAQ 키워드 자동응답)는 출발점으로는 안전하지만, 목표와 어긋나는 지점이 있습니다.

- 질문 유형이 열려 있어(용어, 주소, 담당자, 프로젝트, 성과 분석) 고정 순서로는 분기가 폭증합니다. 소스를 하나 붙일 때마다 워크플로를 고쳐야 합니다.
- 키워드 FAQ는 도구 기본 검색과 같은 한계(표현이 다르면 못 찾음)를 그대로 가집니다.
- "불만족 답변을 바로 개선"하려면 답이 어떤 근거로 나왔는지 추적되어야 합니다.

그래서 아래와 같이 제안합니다.

## 2. 구조

1. **라우터(질문 분류)**: 데이터 조회 / 사내 지식 / 담당자·조직 / 성과 분석 / 범위 밖. 확신이 낮으면 되묻기.
2. **에이전트 루프(소스별 도구 호출)**: 고정 순서 대신, 모델이 소스별 검색 도구(SQL, 위키, 이슈, 메신저, 문서, 포털)를 필요에 따라 고르고 반복 호출합니다. 단, 도구 집합·최대 호출 횟수·권한은 개발자가 제한합니다. 기존 SQL 워크플로는 하나의 도구로 감쌉니다.
3. **통합 검색 계층**: 소스별 커넥터가 문서를 공통 스키마(제목, 본문, 출처 URL, 수정일, 접근권한, 소유자)로 색인. 키워드 + 임베딩 하이브리드 검색, 접근권한 필터는 검색 단계에서 적용.
4. **대화 메모리**: 세션 내 히스토리 + 사용자별 요약. 질문 재작성(후속 질문을 독립 질문으로)으로 검색에 반영.
5. **답변 규칙**: 출처 링크 필수, 근거 없으면 "찾지 못함"과 담당 문의처 안내, 오래된 문서는 수정일 표기.
6. **피드백 루프**: 답변마다 👍/👎 + 사유, 질문·검색 결과·도구 호출 trace·답변을 저장. 👎는 리뷰 큐로 가서 "소스 누락 / 검색 실패 / 문서 오류 / 생성 오류"로 분류. 이를 평가셋에 누적.
7. **지원 채널 응대(단계적)**:
   - 1단계: 그림자 모드. 채널 질문을 읽고 답 초안만 만들어 담당자에게 비공개 제시(자동 게시 안 함).
   - 2단계: 과거 스레드(질문→담당자 답변)를 색인해 유사 질문 검색, 신뢰도 높고 위험이 낮은 유형만 자동 응답.
   - 모든 자동 응답에 "틀리면 담당자 호출" 버튼.

## 3. 구현 첫날 제안

코드보다 **현실 데이터 확인**부터 합니다.

1. (오전) 최근 몇 주간의 실제 질문 로그에서 약 100~200건을 뽑아 유형별로 분류: 데이터 조회, 용어, 담당자, 프로젝트, 성과 분석, 기타. 어느 소스에서 답이 나와야 하는지 정답 소스를 표기.
2. (오전) 지원 채널 중 문의량 상위 5~10개를 골라, 최근 스레드 중 "질문 → 담당자 답변" 쌍을 수십 건 추출(권한·개인정보 점검 포함).
3. (오후) 가장 접근이 쉬운 소스 2개(예: 위키, 메신저 지원 채널)의 커넥터 스파이크: 권한 모델과 API 제한 확인.
4. (오후) 위 질문 샘플로 가장 작은 실험(아래)을 돌립니다.

## 4. 설계를 크게 바꿀 수 있는 가정 하나

**가정: "반복되는 지원 채널 질문은 과거 담당자 답변을 의미 검색해 재사용하면 충분히 정확히 응대할 수 있다."**

틀리면 2단계 자동응답 설계가 무너집니다. 답이 시점·개인 상황·진행 중 이슈에 의존한다면, 과거 답변 재사용이 아니라 현재 상태를 조회하는 도구(이슈 상태, 데이터, 담당 로스터)를 중심으로 재설계하고, 자동 응답은 안내/라우팅 중심으로 축소해야 합니다. 또한 라이브 소스 중심으로 바뀌면 색인 계층 비중이 줄어듭니다.

## 5. 가장 작은 실험

- **입력**: 상위 지원 채널 5~10개에서 최근 3개월 스레드의 질문 100건(과거 담당자 답변이 있는 것). 시간순으로 나눠 앞 80%의 스레드를 색인하고, 뒤 20% 이상의 질문을 테스트로 사용(미래 정보 누출 방지). 정답은 해당 스레드의 담당자 답변.
- **비교 대상**:
  - A: 현재 계획의 키워드 FAQ 매칭(질문–답 쌍 키워드 검색)
  - B: 과거 스레드 임베딩+키워드 하이브리드 검색 후 답 초안 생성
  - 기준: 담당자 답변을 정답으로 한 담당자(또는 팀원 2명)의 블라인드 채점(정답 / 부분 정답 / 오답 / 시점 의존으로 재사용 불가).
- **실패 판단 관찰 결과** (실험 전에 확정해 두는 임계값 제안):
  - B에서 "정답"으로 판정된 비율이 낮아 자동 응답 후보(신뢰도 상위 구간)에서도 오답이 약 5% 이상 나온다.
  - 또는 테스트 질문의 상당수(예: 40% 이상)가 "시점 의존/개인 상황 의존으로 재사용 불가"로 채점된다.
  - 또는 B가 A에 비해 정답률 개선이 미미하다(예: 10%p 미만). 이 경우 복잡도를 정당화하지 못합니다.

(임계값은 제 제안이며, 채널의 위험도에 따라 조정해야 합니다.)

## 6. 실패 시 조치

**직접 시도할 수 있는 조치(사용자 결정 불필요)**
- 청킹 단위 변경(스레드 전체 vs 질문–답 쌍), 검색 파라미터 조정, 질문 재작성 추가, 재순위화 적용.
- 채널·유형별로 쪼개 결과 확인, 성공하는 유형(예: 권한 신청 절차, 정책 안내)만 따로 평가.
- 오래된 스레드 제외, 최신 답변 가중치 적용.
- 실패 사례를 원인(검색 실패 vs 생성 오류 vs 재사용 불가)으로 분류해 보고.
- 현재 상태 조회 도구(이슈/로스터) 후보를 추가해 같은 샘플로 재측정.

**사용자 결정이 필요한 조건**
- 자동 게시 범위를 "일부 유형만"으로 축소하거나 안내/라우팅 전용으로 바꾸는 결정(제품 범위·위험 허용도).
- 오답 허용 기준(예: 5%)을 완화하는 결정.
- 메신저 대화를 색인·평가에 쓰는 데 대한 개인정보·보안·채널 소유자 동의, 추가 권한 요청.
- 평가 채점에 담당자 시간을 더 투입하는 결정, 외부 모델/벤더 사용 변경에 따른 비용·데이터 반출 판단.
- 라이브 상태 조회 중심으로 아키텍처를 바꿔 로드맵·인력을 재배분하는 결정.

## 7. 정리

- 고정 워크플로는 SQL 같은 검증된 경로에만 남기고, 나머지는 제한된 도구를 쓰는 에이전트 루프로 확장합니다.
- 첫날은 실제 질문·스레드 샘플링과 실험으로 위 가정을 먼저 검증합니다.
- 결과에 따라 지원 채널 자동응답의 범위(전면 / 유형 한정 / 초안·라우팅만)를 결정합니다.
