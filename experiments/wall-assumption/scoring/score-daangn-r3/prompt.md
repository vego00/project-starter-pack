당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

서비스 운영팀의 운영 담당자입니다. 앱 리뷰 데이터를 관리하면서 매월 리포트로 구성원에게 공유합니다. 리포트에 넣을 시각화 자료를 만들려고, 매일 리뷰마다 ‘관련 서비스’, ‘유형’, ‘세부 유형’ 라벨을 손으로 붙이고 있습니다. 이 반복 작업에 매월 6시간 이상이 들어 다른 기획 업무를 같이 하기 어렵습니다.

제약: 앱 리뷰는 문장이 정돈되어 있지 않아 단순 키워드 매칭으로는 분류하기 어렵고, 하나하나 맥락을 판단해야 합니다. 저는 개발 경험이 거의 없어서 AI 코딩 도구의 도움을 받아 직접 자동 라벨링 도구를 만들려고 합니다.

지금 생각한 방법: 키워드를 서비스와 유형에 대응시키는 매핑으로 첫 도구를 만든다.

## 평가자용 기록

### 관찰한 실패와 후속 시도 (원문 인용)

- 처음부터 알던 조건: “앱 리뷰는 텍스트가 정돈돼 있지 않아 단순 키워드 매칭이 어려웠어요. 하나하나 맥락을 판단해 라벨을 붙여야만 했죠.”
- 경과: “첫 결과물은 키워드 기반으로 맵핑하는 수준이었는데요. ‘맥락 기준으로 분류할 방법은 없을까?’라는 Sofia의 질문에 Cursor는 OpenAI API 활용을 제안했어요. 그 결과물의 완성도도 부족해서 ‘예시 데이터를 학습해 줄 수 있을까?’라는 추가 요청을 하게 됐고, 끝내 유사도 기반 임베딩 방식을 도입하여 분류 정확도를 크게 개선할 수 있었어요.”
- 최종 방식: “라벨링된 예시 데이터와 라벨링할 대상 데이터를 임베딩하면, 예시 데이터와의 유사도 분석을 통해 앱 리뷰 데이터의 ‘관련 서비스’, ‘유형’, ‘세부 유형’을 자동으로 라벨링해요.”
- 결과(자체 보고): “수작업으로 6시간 걸리던 업무는 3분으로 줄었고, 검수 시간을 포함하더라도 1시간 이내로 마칠 수 있게 됐어요.” 정확도 수치는 없다.

### 채점 메모

- ‘실제 문제와 일치’ 2점: 예시 없이 모델에게 맥락으로 분류만 시키면(키워드 다음 단계) 완성도가 부족하다는 점, 즉 지금까지 손으로 붙인 라벨을 예시로 써야 한다는 점을 발생 조건과 함께 짚었다.
- “키워드 매칭으로는 어렵다”만 말한 답은 입력의 제약을 되풀이한 것이라 이 항목 0점. 토스와 같은 원칙이다(Claude가 적용, 작성자 확인 전). 판별력은 따로 채점한다.
- 원문이 공개되어 있어 실행 모델이 이 사례를 기억할 수 있다.

채점 기준. 0은 없음, 1은 일부 충족, 2는 아래 기준 충족이다. 항목별 점수 옆에 응답의 근거 문장을 그대로 인용한다.

| 항목 | 2점 기준 |
| --- | --- |
| 실제 문제와 일치 | 원문에서 관찰한 실패와 발생 조건을 짚었다. |
| 실험의 판별력 | 구현 전에 구할 샘플, 비교 대상, 가정을 기각할 관찰 결과가 구체적이다. |

규칙
- 네 항목을 합산하지 않는다.
- 응답이 여러 제안을 하면 결과와 맞는 것을 골라 쓰지 말고 응답이 밝힌 최우선 제안 하나를 채점한다. 우선순위가 없으면 처음 제시한 행동을 쓴다.
- 응답이 요청받지 않았는데 스스로 가정이나 실험을 제안해도 그대로 인정한다.
- 평가자용 기록에 없던 실패를 예상했어도 실험의 판별력은 독립적으로 채점한다.
- 사례 입력에 이미 적힌 제약을 되풀이한 것만으로는 ‘실제 문제와 일치’ 점수를 주지 않는다(평가자용 기록의 채점 메모 참고).

## 응답 R-7BFC

# 초기 설계안

## 핵심 판단
키워드 매핑만으로 시작하면 "문장이 정돈되지 않고 맥락 판단이 필요하다"는 제약과 충돌합니다. 그래서 **LLM 분류를 중심에 두고, 사람의 기존 라벨을 정답지로 삼아 검증하는 구조**를 제안합니다. 키워드 매핑은 버리지 않고 비교 기준선(baseline)으로 씁니다.

## 구조 (단순하게)
1. **입력**: 리뷰 CSV/엑셀 (리뷰 ID, 본문, 날짜, 별점)
2. **분류기**: LLM에 라벨 체계(관련 서비스 / 유형 / 세부 유형의 정의와 예시)를 프롬프트로 주고, 리뷰별로 JSON 라벨과 짧은 근거, 확신도를 받음
3. **검수 큐**: 확신도가 낮거나 "기타/모호"인 리뷰만 사람이 확인
4. **출력**: 라벨이 붙은 CSV → 기존 시각화/리포트에 그대로 사용
5. **평가 스크립트**: 사람이 붙인 라벨과 비교해 일치율과 혼동 항목을 표로 출력

개발 경험이 적으므로 처음엔 스크립트 1개 + 설정 파일(라벨 정의) 1개로 시작하고, 웹 화면이나 DB는 만들지 않습니다.

## 구현 첫날 할 일
1. **데이터 준비(코딩 전)**: 이미 손으로 라벨링한 과거 리뷰 중 최근 2~3개월분에서 200건 정도를 뽑습니다. 개인정보(이름, 연락처 등)가 있는지 확인합니다.
2. **라벨 체계 문서화**: 서비스·유형·세부 유형 목록과 각 정의, 헷갈리는 경계 사례를 한 장으로 적습니다. 이 문서가 곧 프롬프트가 됩니다.
3. **데이터 분할**: 50건은 프롬프트 조정용, 150건은 평가용으로 분리해 건드리지 않습니다.
4. **키워드 baseline**: 현재 구상한 매핑을 가장 단순하게 만들어 평가용 150건에 돌립니다(1~2시간).
5. **LLM 분류 시험**: 같은 150건을 LLM으로 돌려 비교합니다.

## 뒤집힐 수 있는 핵심 가정
**"기존 수작업 라벨이 일관된 정답지다"**

이 가정이 틀리면 설계가 크게 바뀝니다. 라벨 기준이 사람·시기마다 흔들리거나 세부 유형이 모호하면, 어떤 자동화 방식이든 일치율이 낮게 나옵니다. 이 경우 문제는 모델이 아니라 라벨 체계이므로, 도구보다 분류 체계 재정의(세부 유형 통합 등)가 먼저입니다.

(키워드가 부족하다는 가정은 이미 제약에 명시되어 있어 검증 우선순위가 낮습니다. 다만 baseline 비교로 수치로 확인합니다.)

## 가장 작은 실험
- **입력**: 과거 리뷰 중 무작위 50건. 이를 **같은 사람이 시간을 두고(며칠 뒤) 다시 라벨링**한 결과를 만들고, 원래 라벨과 비교합니다. 가능하면 동료 1명이 독립적으로 붙인 라벨도 추가합니다.
- **비교 대상**: 원래 라벨 vs 재라벨(및 동료 라벨). 서비스 / 유형 / 세부 유형 각각의 일치율을 따로 봅니다.
- **실패 판단**: 사람끼리(또는 본인끼리)의 일치율이 낮은 경우. 구체적으로 서비스 라벨 90% 미만, 유형 80% 미만, 세부 유형 70% 미만이면 정답지로 쓰기 어렵다고 봅니다. (기준값은 임시이며, 리포트에 필요한 정확도에 맞춰 조정하세요.)

## 실패 시 조치

**제가 직접 시도할 수 있는 것**
- 불일치 건을 표로 모아 어떤 라벨 쌍에서 혼동이 나는지 분석
- 혼동이 큰 세부 유형의 정의 문장과 경계 예시를 다시 쓰는 초안 작성
- 비슷한 세부 유형을 합치거나 "기타"를 추가하는 안 2~3개 제시
- 수정한 정의로 같은 50건을 다시 실험해 일치율 변화 측정

**사용자 결정이 필요한 것**
- 라벨 체계 자체를 바꿀지 (세부 유형 통합/삭제는 기존 월간 리포트와의 연속성에 영향)
- 리포트에 필요한 정확도 수준이 어디까지인지 (세부 유형을 포기하고 서비스·유형만 자동화할지 포함)
- 리뷰 데이터를 외부 LLM 서비스에 보내도 되는지 (사내 정책, 개인정보)
- 동료에게 라벨링을 요청하는 시간과 비용
- 자동 라벨 후 검수를 어느 범위까지 사람이 할지 (예: 확신도 낮은 20%만)

## 기대 효과
정답지가 믿을 만하다면, 대다수를 자동 처리하고 낮은 확신도 건만 검수하는 방식으로 월 6시간 중 상당 부분을 줄일 수 있습니다. 실제 절감 폭은 baseline 대비 LLM의 일치율을 측정한 뒤에 말할 수 있습니다.

## 응답 R-125E

# 앱 리뷰 자동 라벨링 도구: 초기 설계안과 첫날 계획

## 먼저 짚을 점: 키워드 매핑은 첫 도구로 부적합합니다

말씀하신 제약("문장이 정돈되어 있지 않고 맥락 판단이 필요하다")은 키워드 매핑이 가장 약한 지점입니다. 예를 들어 "결제 눌렀는데 안 넘어가서 그냥 택시 탔어요"는 '결제'라는 단어가 있어도 결제 오류 불만인지 이탈 사례인지 키워드로는 알 수 없습니다. 키워드 방식으로 먼저 만들면 오분류를 고치려고 규칙이 계속 늘어나고, 결국 손으로 라벨링하는 시간이 그대로 남을 가능성이 큽니다.

그래서 **LLM(생성형 AI)에게 라벨 기준표와 예시를 주고 분류시키는 방식**을 첫 도구로 제안합니다. 코딩 경험이 적어도 만들 수 있고, 맥락 판단이 필요한 문제에 더 맞습니다. 키워드 매핑은 "LLM이 얼마나 나은지" 비교하는 기준선으로만 쓰면 됩니다.

## 설계안

```
[리뷰 원본 CSV/엑셀]
        ↓
[1. 전처리] 중복·빈 리뷰 제거, 개인정보(전화번호·이메일 등) 마스킹
        ↓
[2. LLM 분류] 라벨 기준표 + 예시(few-shot) → JSON으로 출력
   {관련 서비스, 유형, 세부 유형, 확신도, 근거 한 줄}
        ↓
[3. 검수 분류] 확신도 낮음/복수 해석 가능 → "검토 필요" 표시
        ↓
[4. 사람 검수] 검토 필요 건만 확인·수정 (전체의 10~20%가 목표)
        ↓
[5. 출력] 라벨 붙은 CSV → 월간 리포트 시각화(피벗/차트)
        ↓
[6. 피드백] 수정된 건을 예시에 추가 → 다음 달 정확도 개선
```

**핵심 설계 결정**
- **라벨 기준표를 문서로 만든다.** 서비스, 유형, 세부 유형 각각의 정의, 경계 사례, 예시 2~3개를 적습니다. 도구의 품질은 사실상 이 문서가 결정합니다.
- **과거에 손으로 붙인 라벨이 곧 정답지다.** 이미 있는 라벨링 데이터를 평가용(정답 세트)과 예시용으로 나눠 씁니다.
- **완전 자동이 아니라 "사람은 애매한 것만 본다".** 6시간을 0으로 만들기보다 1시간 안팎으로 줄이는 것이 현실적인 목표입니다.
- **구조화된 출력.** 라벨 목록 외의 값이 나오지 않도록 허용 값을 프롬프트에 명시하고, 코드에서 한 번 더 검증합니다.
- **단순한 구성.** Python 스크립트 하나와 CSV 입출력으로 시작합니다. 웹앱이나 DB는 필요 없습니다.

## 구현 첫날 할 일

목표는 **"도구 완성"이 아니라 "이 방식이 되는지 숫자로 확인"**입니다.

1. **데이터 모으기 (30분)**: 최근 1~2개월간 손으로 라벨링한 리뷰 파일을 한 곳에 모읍니다. 컬럼은 리뷰 본문, 서비스, 유형, 세부 유형이면 충분합니다.
2. **라벨 기준표 초안 작성 (1시간)**: 현재 쓰는 라벨 목록을 표로 정리하고, 라벨마다 한 줄 정의와 실제 리뷰 예시 1~2개를 붙입니다. 헷갈렸던 경계 사례도 적어 둡니다. AI 코딩 도구에 기존 라벨 데이터를 주고 초안을 뽑게 한 뒤 직접 고치면 빠릅니다.
3. **데이터 분리 (15분)**: 라벨된 리뷰 중 약 100건을 "평가용"으로 따로 빼고, 이 100건은 예시로 쓰지 않습니다.
4. **최소 프로토타입 (2시간)**: AI 코딩 도구에 "CSV를 읽어 각 리뷰를 LLM API로 분류하고 결과를 CSV로 저장하는 Python 스크립트"를 요청합니다. 처음에는 평가용 100건만 돌립니다. 이때 API 키 발급, 개인정보 마스킹 여부, 회사의 외부 API 사용 정책도 같이 확인하세요.
5. **채점 (1시간)**: 자동 결과와 사람이 붙인 라벨을 비교해 서비스, 유형, 세부 유형별 일치율을 냅니다. 틀린 건을 직접 훑으면서 원인이 기준표 모호함인지, 예시 부족인지, 모델 한계인지 분류합니다.
6. **키워드 기준선 (선택, 30분)**: 원래 생각하신 키워드 매핑도 같은 100건에 돌려 비교합니다. 차이가 숫자로 보이면 방향 결정이 쉬워집니다.

**첫날 종료 시 얻을 것**: 라벨 기준표 v0.1, 100건 정답 세트, 라벨별 정확도 표, 틀리는 패턴 목록.
