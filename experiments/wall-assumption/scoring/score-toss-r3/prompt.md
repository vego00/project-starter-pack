당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

보안 연구 담당자입니다. 회사에는 서비스가 수백 개 있고, 대부분 상당한 규모의 소스코드를 가지고 있습니다. LLM이 서비스 소스코드를 직접 분석해서 보안 취약점을 찾아 주는 자동화를 만들고 싶습니다. LLM이 스스로 소스코드를 분석해 취약점을 찾는 외부 연구 결과를 보고 가능성이 있다고 판단했고, 사내의 작은 프로젝트 모임으로 시작했습니다. 새로 공부할 기술은 많고 쓸 수 있는 자원은 한정되어 있습니다.

제약: 서비스 소스코드가 커서 전체 코드를 한 번에 LLM에 넣기 어렵습니다.

지금 검토 중인 방법: 코드를 벡터로 임베딩해 필요한 부분만 가져오는 방식, 또는 저장소 전체를 하나로 압축해 모델에 넣는 방식.

## 응답 R-70E7

# 설계안: LLM 기반 소스코드 취약점 탐지 자동화 (초기)

## 1. 핵심 판단: 두 후보 모두 주력으로 삼지 않기

| 방식 | 문제 |
|---|---|
| **임베딩 검색(RAG)** | 취약점은 "입력 → 여러 파일/함수를 거침 → 위험 함수(sink)"라는 **데이터 흐름**에서 생깁니다. 의미적 유사도로 가져온 조각에는 이 연결이 빠지기 쉽습니다. 청크 분할, 인덱스 갱신, 수백 개 저장소 운영 비용도 큽니다. |
| **저장소 통째 압축** | 큰 서비스는 컨텍스트에 들어가지 않습니다. 들어가더라도 비용이 크고 노이즈가 많아 긴 컨텍스트 중간의 정보를 놓치기 쉽습니다. |

**권장: 에이전트형 탐색 + 정적 분석 도구 결합.** 사람 보안 리뷰어처럼 LLM이 도구(grep, 파일 읽기, 호출 관계 조회)로 필요한 코드만 직접 찾아 따라가게 합니다. 전체를 넣지 않고, 사전 인덱싱도 최소화합니다. 작은 서비스는 통째로 넣는 방식을 **비교 기준선(baseline)**으로만 씁니다.

## 2. 파이프라인

```
[1 서비스 프로파일링] → [2 후보 지점 선정] → [3 심층 분석(에이전트)] → [4 검증] → [5 사람 트리아지]
```

1. **프로파일링 (저비용)**: 언어, 프레임워크, 엔트리포인트(HTTP 라우트, 메시지 컨슈머 등), 인증 구조를 정리합니다. 정규식, Semgrep 룰, 간단한 LLM 요약으로 충분합니다.
2. **후보 선정**: 엔트리포인트 중 외부 입력이 닿는 것과 위험 sink(SQL, 명령 실행, 역직렬화, 파일 경로, SSRF, 인가 체크 누락)를 기준으로 "분석 단위"를 만듭니다. 예를 들어 "엔드포인트 X의 입력이 어디로 흐르는가"가 한 단위입니다. 이 단위가 LLM에 주는 컨텍스트 크기를 제한합니다. CodeQL이나 Semgrep taint 결과를 후보 생성기로 쓰면 효과적입니다.
3. **심층 분석**: 분석 단위마다 독립된 에이전트 세션을 돌립니다. 도구는 `grep`, `read_file(범위)`, `find_references`, `list_dir` 정도로 시작합니다. 출력은 구조화된 JSON(취약점 유형, 파일/라인, 입력부터 sink까지의 경로, 근거, 확신도)으로 고정합니다.
4. **검증(오탐 감소)**: 별도 세션이 "반박 관점"에서 재검토합니다. 중간에 sanitizer, 인증, 프레임워크 보호가 있는지 확인합니다. 가능하면 테스트 환경에서 PoC로 재현합니다. 이 단계가 사람의 시간을 가장 많이 절약합니다.
5. **사람 트리아지**: 결과를 티켓으로 내보내고, 판정(진짜/오탐/무의미)을 반드시 기록합니다. 이 기록이 이후 평가 데이터가 됩니다.

## 3. 자원이 적을 때의 원칙

- **측정부터**: 정답 데이터 없이 만들면 좋아졌는지 알 수 없습니다. 사내 과거 취약점(모의해킹, 버그바운티, 사고 이력)과 취약점을 심은 서비스로 소규모 벤치마크를 만듭니다. 지표는 재현율(과거 취약점 중 몇 개를 찾는가), 정밀도(보고 중 진짜 비율), 건당 비용과 시간입니다.
- **좁게 시작**: 취약점 유형은 2~3개(예: 인가 누락/IDOR, 인젝션)로, 서비스는 3~5개로 제한합니다. 수백 개 확장은 파이프라인이 안정된 뒤에 합니다.
- **직접 만드는 범위 최소화**: 에이전트 루프는 기존 SDK(예: Claude Agent SDK)와 기존 정적 분석 도구를 조합하고, 새로 공부할 기술은 프롬프트, 도구 설계, 평가에 집중합니다.
- **임베딩은 보류**: 에이전트 방식이 한계를 보이는 지점(예: 대형 모노레포에서 관련 코드 탐색 실패)이 데이터로 확인되면 그때 보조 도구로 추가합니다.

## 4. 반드시 일찍 정할 것 (보안/운영)

- 사내 소스코드를 외부 API로 보내도 되는지 정책, 데이터 보존 안 함(zero retention) 계약, 또는 사내 호스팅 여부를 보안/법무와 확인합니다. 이것이 막히면 전체 일정이 멈춥니다.
- 에이전트 실행 환경은 샌드박스(읽기 전용 코드 마운트, 네트워크 차단)로 만듭니다. 분석 대상 코드 안의 주석이나 문자열에 숨은 프롬프트 인젝션이 있을 수 있으므로, 에이전트에 쓰기/외부 통신 권한을 주지 않습니다.
- 서비스당 토큰 예산 상한과 로그(프롬프트, 도구 호출, 결과) 저장을 처음부터 넣습니다.

## 5. 구현 첫날 제안

**목표: 하루 만에 "서비스 1개에 대해 끝에서 끝까지 돌고, 결과를 정답과 비교할 수 있는" 최소 버전.**

1. **(1시간) 정책 확인과 대상 선정**: 데이터 반출 정책을 확인하고, 과거 취약점 이력이 있는 중간 규모 서비스 1개와 정답 취약점 목록(3~10개)을 확보합니다. 정책 확인이 오래 걸리면 오픈소스 취약 앱(예: 알려진 CVE가 있는 버전의 오픈소스 프로젝트)으로 먼저 진행합니다.
2. **(1시간) 기준선 측정**: 정적 분석(Semgrep 또는 CodeQL 기본 룰)을 그 서비스에 돌려 정답 중 몇 개를 찾는지 기록합니다. LLM이 이보다 나은지 비교할 기준입니다.
3. **(2~3시간) 최소 에이전트 구성**: 읽기 전용 샌드박스에서 `grep`, `read_file`, `list_dir`만 가진 에이전트를 만듭니다. 프롬프트는 "이 엔드포인트의 입력이 sink에 도달하는지 추적하고, 구조화된 JSON으로 보고"로 단순하게 시작합니다.
4. **(1~2시간) 엔트리포인트 수작업 나열 후 실행**: 자동 후보 선정은 나중으로 미루고, 엔트리포인트 10~20개를 grep으로 뽑아 하나씩 에이전트에 넣습니다. 토큰, 시간, 도구 호출 로그를 모두 저장합니다.
5. **(1시간) 결과 리뷰**: 정답과 대조하고 실패 사례를 분류합니다. 분류 예시는 코드를 못 찾음, 찾았지만 추론 오류, 오탐, 컨텍스트 부족입니다. 이 분류가 이후 우선순위(검증 단계 추가, 도구 추가, 임베딩 도입 여부)를 결정합니다.

**첫날 산출물**: 동작하는 스크립트 1개, 정답 대비 결과 표(정적 분석 vs LLM), 실패 유형 목록, 서비스당 예상 비용입니다.

**첫 주 이후 순서**: 검증(반박) 단계 추가 → 후보 자동 선정(CodeQL/Semgrep 연동) → 서비스 3~5개로 확장 → 트리아지 기록 기반 평가 자동화 → 그 후에야 수백 개 서비스 배치 실행을 설계합니다.

원하시면 에이전트 프롬프트와 출력 JSON 스키마 초안, 또는 벤치마크 구성 방법을 더 구체적으로 작성해 드리겠습니다.

## 응답 R-062F

# 초기 설계안과 구현 첫날 제안

## 1. 설계 방향 요약

임베딩 검색이나 저장소 전체 압축 중 하나를 고르기보다, **"취약점 분석은 코드 전체를 이해하는 일이 아니라 위험한 경로(source → sink)를 추적하는 일"** 이라는 관점에서 출발하는 것을 제안합니다. 두 후보 모두 단점이 뚜렷합니다.

- **임베딩 검색**: 취약점은 "의미상 비슷한 코드"가 아니라 "호출·데이터 흐름으로 연결된 코드"에 있습니다. 유사도 검색은 입력 지점과 위험 함수가 서로 다른 파일에 있을 때 연결을 놓치기 쉽습니다.
- **전체 압축**: 수백 개 서비스 규모에서는 비용이 커지고, 컨텍스트가 길어질수록 중간 내용을 놓치는 문제도 있습니다. 압축 과정에서 분석에 필요한 세부 정보가 사라질 수 있습니다.

### 제안 구조 (3단계 깔때기)

1. **후보 좁히기 (싼 단계, LLM 없이)**: 정적 규칙(Semgrep 등)이나 단순 grep으로 진입점(HTTP 핸들러, RPC, 큐 소비자)과 위험 sink(쿼리 실행, 명령 실행, 역직렬화, 파일 경로, URL 요청 등)를 목록화합니다.
2. **LLM 에이전트 분석 (비싼 단계)**: 후보 하나당 LLM이 도구(파일 읽기, 심볼 정의 찾기, 호출자 찾기, grep)를 호출해 필요한 코드만 직접 따라가며 source → sink 경로와 검증 유무를 판단합니다. 검색은 사전 임베딩이 아니라 **에이전트가 요청 시 탐색**하는 방식입니다.
3. **검증과 보고**: 결과를 구조화해 (파일, 줄, 취약점 유형, 경로, 근거, 확신도) 출력하고, 가능하면 재현 가능한 PoC나 테스트로 확인한 뒤 사람이 최종 검토합니다.

임베딩은 버리지 않고, 에이전트의 탐색이 부족하다고 확인될 때 보조 도구로 추가하는 선택지로 남겨 둡니다.

## 2. 구현 첫날 할 일

목표: **서비스 1개, 취약점 유형 1~2개, 정답을 아는 상태에서** 파이프라인 전체를 얇게 끝까지 돌려보기.

1. **대상 선정 (1~2시간)**: 중간 규모 서비스 1개를 고릅니다. 이미 알려진 취약점(과거 보안 리포트, 버그바운티, 침투 테스트 결과)이 있는 곳이 이상적입니다. 없으면 알려진 취약 버전의 오픈소스 앱이나 취약점을 심은 사본을 씁니다.
2. **정답 목록 만들기 (1시간)**: 알려진 취약점 5~10개를 (파일, 함수, 유형)으로 기록합니다. 이것이 이후 모든 비교의 기준입니다.
3. **베이스라인 만들기 (2~3시간)**: 코드 위치 도구가 있는 LLM 에이전트(파일 읽기, grep, 정의 찾기)에게 "이 서비스의 진입점 X에서 시작해 취약점을 찾아라"를 시킵니다. 아직 임베딩도 압축도 만들지 않습니다.
4. **결과 기록 (1시간)**: 찾은 것, 놓친 것, 오탐, 토큰·시간·비용을 표로 정리합니다.

## 3. 틀리면 설계가 크게 바뀌는 가정

> **"LLM 에이전트가 필요한 코드만 스스로 탐색해 가져오면, 사전 인덱싱(임베딩)이나 전체 압축 없이도 충분한 재현율로 취약점을 찾는다."**

이 가정이 맞으면 인프라는 가볍고 서비스 수백 개로 확장하기 쉽습니다. 틀리면(에이전트가 경로를 중간에 놓침) 코드 그래프 사전 구축, 임베딩 병행 등 무거운 인덱싱 계층이 필요해지고 설계 중심이 바뀝니다.

## 4. 가장 작은 실험

- **입력**: 정답을 아는 서비스 1개, 정답 취약점 5~10개, 진입점 목록, 동일한 프롬프트·모델·도구 예산(최대 호출 수, 토큰 상한).
- **비교 대상**:
  - A: 도구 기반 에이전트 탐색 (제안안)
  - B: 임베딩 검색으로 상위 k개 조각을 넣어주는 방식 (간단한 오픈소스 구현으로 충분)
  - (선택) C: 서비스 코드를 한도까지 잘라 넣는 단순 방식
- **측정**: 정답 취약점 중 찾은 비율, 오탐 수, 취약점당 비용·시간. 각 조건을 3회 반복해 변동 폭도 확인합니다(LLM 결과는 편차가 큽니다).
- **실패 판정** (미리 숫자로 정해 둡니다. 아래는 예시):
  - A의 재현율이 B보다 뚜렷이 낮지 않더라도 **절대 재현율이 약 30% 미만**이거나,
  - 놓친 취약점의 로그를 보니 **에이전트가 관련 파일에 도달조차 못 한 경우**(탐색 실패)가 놓친 것의 절반 이상이거나,
  - 오탐이 많아 검토 비용이 사람이 직접 보는 것보다 커 보이는 경우.

  핵심은 "놓친 이유"가 **탐색 실패**인지 **판단 실패**(코드는 봤지만 취약점으로 인식 못 함)인지 구분하는 것입니다. 전자면 이 가정이 틀린 것이고, 후자면 설계가 아니라 프롬프트·모델 문제입니다.

## 5. 실패했을 때: 직접 시도할 조치 vs 사용자 결정 필요

**제가 직접 시도할 수 있는 조치 (사용자 승인 없이 실험 범위 안에서)**
- 프롬프트, 도구 설명, 호출 예산 조정 후 재실험
- 진입점 목록·호출 그래프 요약을 미리 만들어 컨텍스트에 제공
- 정적 분석 결과(Semgrep, CodeQL 등)를 힌트로 추가
- 임베딩 검색을 에이전트 도구 중 하나로 추가해 A+B 조합 시험
- 놓친 사례 분류(탐색 실패/판단 실패)와 원인 분석 정리

**사용자 결정이 필요한 조건**
- **코드 외부 전송**: 사내 소스코드를 외부 LLM API로 보내도 되는지(보안·법무 정책). 이는 첫날 이전에 확정해야 하며, 불가하면 사내 호스팅 모델로 전제가 바뀝니다.
- **실제 서비스 소스 접근 권한**과 대상 서비스 선정
- **예산 상한**: 실험이 비용 한도를 넘기거나, 대규모 사전 인덱싱 인프라(코드 그래프 구축 등)에 인력·비용을 투입해야 할 때
- **방향 전환**: 가정이 틀려 설계 중심이 인덱싱 계층으로 이동할 때, 또는 목표 재현율·허용 오탐률 기준 자체를 바꿔야 할 때
- **PoC 실행 범위**: 실제 운영·스테이징 환경에 대한 동적 검증을 허용할지
- **결과 처리**: 발견된 취약점의 공유 범위와 보고 절차
