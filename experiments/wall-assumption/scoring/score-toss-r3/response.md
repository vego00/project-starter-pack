### 응답 R-70E7
- 구현 첫날 첫 행동(응답 문장 그대로 인용): "(1시간) 정책 확인과 대상 선정: 데이터 반출 정책을 확인하고, 과거 취약점 이력이 있는 중간 규모 서비스 1개와 정답 취약점 목록(3~10개)을 확보합니다."
- 채점한 최우선 제안(응답 문장 그대로 인용, 없으면 '없음'): "권장: 에이전트형 탐색 + 정적 분석 도구 결합. 사람 보안 리뷰어처럼 LLM이 도구(grep, 파일 읽기, 호출 관계 조회)로 필요한 코드만 직접 찾아 따라가게 합니다."
- 실제 문제와 일치: 2 — 근거: "취약점은 \"입력 → 여러 파일/함수를 거침 → 위험 함수(sink)\"라는 데이터 흐름에서 생깁니다. 의미적 유사도로 가져온 조각에는 이 연결이 빠지기 쉽습니다." / 실패 1(벡터 검색이 코드 간 연관관계를 놓침)에 대응하며, 발생 조건(입력과 sink가 여러 파일·함수를 거치는 데이터 흐름)을 함께 짚었다. 압축 방식에 대한 "노이즈가 많아 긴 컨텍스트 중간의 정보를 놓치기 쉽습니다"는 실패 3과 일부만 겹친다. 없는 취약점을 만들어 내는 환각은 언급하지 않았다.
- 실험의 판별력: 1 — 근거: "정적 분석(Semgrep 또는 CodeQL 기본 룰)을 그 서비스에 돌려 정답 중 몇 개를 찾는지 기록합니다. LLM이 이보다 나은지 비교할 기준입니다." / "정답과 대조하고 실패 사례를 분류합니다." 샘플(정답 3~10개를 아는 서비스 1개)과 비교 대상(정적 분석 vs LLM)은 구체적이다. 그러나 가정을 기각할 관찰 결과나 수치 기준이 없고, 반복 실행으로 변동을 확인하는 설계도 없다.
- 실패 후 행동: 1 — 근거: "분류 예시는 코드를 못 찾음, 찾았지만 추론 오류, 오탐, 컨텍스트 부족입니다. 이 분류가 이후 우선순위(검증 단계 추가, 도구 추가, 임베딩 도입 여부)를 결정합니다." 바꿀 설계 요소 후보는 나열했다. 하지만 어떤 실패 유형이 어떤 변경으로 이어지는지 대응시키지 않았고, 같은 실험으로 개선을 판정할 기준도 밝히지 않았다.
- 사용자 개입 판단: 1 — 근거: "사내 소스코드를 외부 API로 보내도 되는지 정책, 데이터 보존 안 함(zero retention) 계약, 또는 사내 호스팅 여부를 보안/법무와 확인합니다. 이것이 막히면 전체 일정이 멈춥니다." 정책과 권한 문제는 짚었다. 하지만 주어진 권한 안에서 스스로 시도할 조치와 사용자 결정이 필요한 조건(비용 상한 초과, 방향 전환 등)을 나누어 제시하지 않았다.

### 응답 R-062F
- 구현 첫날 첫 행동(응답 문장 그대로 인용): "대상 선정 (1~2시간): 중간 규모 서비스 1개를 고릅니다. 이미 알려진 취약점(과거 보안 리포트, 버그바운티, 침투 테스트 결과)이 있는 곳이 이상적입니다."
- 채점한 최우선 제안(응답 문장 그대로 인용, 없으면 '없음'): "임베딩 검색이나 저장소 전체 압축 중 하나를 고르기보다, \"취약점 분석은 코드 전체를 이해하는 일이 아니라 위험한 경로(source → sink)를 추적하는 일\" 이라는 관점에서 출발하는 것을 제안합니다."
- 실제 문제와 일치: 2 — 근거: "유사도 검색은 입력 지점과 위험 함수가 서로 다른 파일에 있을 때 연결을 놓치기 쉽습니다." / 실패 1(코드 간 연관관계 파악 실패)에 대응하며, 발생 조건(입력 지점과 sink가 다른 파일에 있을 때)을 명시했다. "각 조건을 3회 반복해 변동 폭도 확인합니다(LLM 결과는 편차가 큽니다)"는 실패 4(실행마다 다른 결과)도 예상한 것이다.
- 실험의 판별력: 2 — 근거: "A: 도구 기반 에이전트 탐색 (제안안) / B: 임베딩 검색으로 상위 k개 조각을 넣어주는 방식" / "절대 재현율이 약 30% 미만이거나, 놓친 취약점의 로그를 보니 에이전트가 관련 파일에 도달조차 못 한 경우(탐색 실패)가 놓친 것의 절반 이상이거나". 샘플(정답 5~10개를 아는 서비스 1개, 같은 모델·도구 예산), 비교 대상(A/B/C, 각 3회 반복), 기각 조건이 모두 구체적이다.
- 실패 후 행동: 2 — 근거: "전자면 이 가정이 틀린 것이고, 후자면 설계가 아니라 프롬프트·모델 문제입니다." / "진입점 목록·호출 그래프 요약을 미리 만들어 컨텍스트에 제공", "임베딩 검색을 에이전트 도구 중 하나로 추가해 A+B 조합 시험". 실패 원인별로 바꿀 설계 요소가 구체적이고, 같은 정답 세트와 같은 비교 실험으로 개선을 재확인할 수 있다.
- 사용자 개입 판단: 2 — 근거: "제가 직접 시도할 수 있는 조치 (사용자 승인 없이 실험 범위 안에서)" / "사용자 결정이 필요한 조건 … 예산 상한: 실험이 비용 한도를 넘기거나, 대규모 사전 인덱싱 인프라(코드 그래프 구축 등)에 인력·비용을 투입해야 할 때". 권한 안에서 시도할 조치와, 비용·권한·서비스 요구가 바뀌어 사용자 결정이 필요한 조건을 명시적으로 나누었다.

두 응답의 구현 첫날 첫 행동은 실질적으로 같다. 둘 다 알려진 취약점이 있는 중간 규모 서비스 1개를 골라 정답 목록을 확보하는 일이며, R-70E7은 같은 단계에서 데이터 반출 정책 확인을 함께 한다는 차이만 있다.
