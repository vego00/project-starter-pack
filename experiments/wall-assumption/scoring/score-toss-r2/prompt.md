당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

보안 연구 담당자입니다. 회사에는 서비스가 수백 개 있고, 대부분 상당한 규모의 소스코드를 가지고 있습니다. LLM이 서비스 소스코드를 직접 분석해서 보안 취약점을 찾아 주는 자동화를 만들고 싶습니다. LLM이 스스로 소스코드를 분석해 취약점을 찾는 외부 연구 결과를 보고 가능성이 있다고 판단했고, 사내의 작은 프로젝트 모임으로 시작했습니다. 새로 공부할 기술은 많고 쓸 수 있는 자원은 한정되어 있습니다.

제약: 서비스 소스코드가 커서 전체 코드를 한 번에 LLM에 넣기 어렵습니다.

지금 검토 중인 방법: 코드를 벡터로 임베딩해 필요한 부분만 가져오는 방식, 또는 저장소 전체를 하나로 압축해 모델에 넣는 방식.

## 평가자용 기록

# 초기 설계안: LLM 기반 소스코드 취약점 탐지 자동화

## 1. 방향: 임베딩도 전체 압축도 아닌 "에이전트가 코드를 탐색하는 방식"

두 후보 모두 단독으로는 이 문제에 맞지 않습니다.

| 방식 | 한계 |
|---|---|
| 임베딩 + 검색(RAG) | 취약점은 대개 입력 지점에서 위험한 함수까지 이어지는 여러 파일에 걸친 데이터 흐름입니다. 임베딩은 비슷해 보이는 코드를 가져올 뿐, 실제 호출자·피호출자를 가져오지 못합니다. 청킹이 흐름을 끊고, 인덱스 구축·갱신 비용도 수백 개 서비스에 곱해집니다. |
| 저장소 전체 압축 | 큰 서비스는 여전히 컨텍스트에 들어가지 않습니다. 들어가더라도 긴 컨텍스트에서 정확도가 떨어지고, 서비스마다 비용이 큽니다. |

대안은 LLM 에이전트에 `grep`, 파일 읽기, 디렉터리 탐색, 정의·참조 찾기 같은 도구를 주고, 사람 리뷰어처럼 필요한 코드만 따라가며 읽게 하는 것입니다. 인덱스를 따로 만들 필요가 없고 새로 배울 기술도 적습니다. 공개된 LLM 취약점 탐지 연구 사례도 대체로 이 구조를 씁니다. 임베딩은 나중에 보조 검색 도구로 추가할 수 있습니다.

작은 서비스(대략 10만 토큰 이하)는 전체를 한 번에 넣는 방식이 가장 간단한 기준선입니다. 이 방식은 기준선과 소형 서비스용으로만 씁니다.

## 2. 파이프라인

```
[서비스 선별] → [공격 표면 식별] → [진입점별 분석 에이전트] → [검증/반박 패스] → [사람 트리아ージュ]
                                         ↑ 도구: grep, read, (Semgrep/CodeQL 결과)
```

1. **서비스 우선순위**: 외부 노출, 인증·결제·개인정보 처리 여부로 점수를 매깁니다. 수백 개를 한꺼번에 돌리지 않습니다.
2. **공격 표면 식별**: HTTP 라우트, RPC 핸들러, 큐 컨슈머 같은 진입점을 목록화합니다. 프레임워크별 Semgrep 규칙이나 tree-sitter, 또는 LLM으로 추출합니다.
3. **진입점 단위 분석**: "저장소 전체"가 아니라 "이 핸들러에서 시작되는 흐름"을 분석 단위로 삼으면 문제 크기가 줄어듭니다. 에이전트는 취약점 유형별 체크리스트(인가 누락/IDOR, 인젝션, SSRF, 역직렬화, 하드코딩 비밀 등)를 따라 입력부터 싱크까지 추적합니다. 토큰과 턴 예산을 제한합니다.
4. **정적 분석 결합**: Semgrep이나 CodeQL 결과를 후보 생성기 또는 에이전트의 도구로 씁니다. LLM은 후보의 도달 가능성 판단과 오탐 제거, 그리고 규칙으로 못 잡는 논리 결함(인가 등)을 맡습니다.
5. **검증 패스**: 별도 프롬프트나 에이전트가 "이 발견을 반박하라"는 관점으로 재검토합니다. 가능하면 샌드박스에서 테스트나 PoC로 재현합니다. 오탐이 가장 큰 운영 비용이므로 이 단계가 핵심입니다.
6. **출력 스키마 고정**: 서비스, 파일:라인, 유형, source→sink 경로, 근거, 신뢰도, 재현 방법을 JSON으로 받아 중복 제거와 추적에 씁니다.

## 3. 보안·운영 제약 (초기에 못 박을 것)

- **코드 반출 승인**: 사내 소스를 외부 LLM API로 보내도 되는지 정책, 법무, 보안 승인과 데이터 보존 없음(zero retention) 계약을 확인합니다. 가장 먼저 확인할 항목입니다.
- **샌드박스**: 분석 대상 코드는 신뢰하지 않습니다. 코드 주석에 심은 프롬프트 인젝션이 가능하므로, 에이전트는 읽기 전용 체크아웃, 네트워크 차단, 비밀 정보 없는 환경에서 돌립니다. 도구는 읽기와 검색만 허용합니다.
- **비용 계측**: 서비스당 토큰, 시간, 발견 건수 대비 유효 건수를 처음부터 기록합니다.

## 4. 성공 기준

- 정답 데이터: 과거 모의해킹, 버그바운티, 보안 사고에서 확인된 취약점이 있는 서비스를 정답셋으로 삼습니다.
- 지표: 재현율(과거 취약점을 찾는가), 정밀도(리뷰어가 유효로 판정한 비율), 서비스당 비용, 리뷰어 소요 시간.
- 목표 예시: 파일럿에서 "리뷰어가 유효로 인정한 발견 비율 X% 이상, 서비스당 비용 Y 이하"를 사전에 합의합니다.

## 5. 구현 첫날 제안

**오전: 전제 정리**
1. 코드 외부 전송 정책을 확인합니다. 승인 전이면 사내 호스팅 모델이나 승인된 엔터프라이즈 계약 경로로 한정합니다.
2. 파일럿 서비스 3개를 고릅니다. 소형 1개, 중형 1개, 과거 취약점 이력이 있는 서비스 1개로 하고, 이력 서비스에서 알려진 취약점 목록(정답셋)을 모읍니다.

**오후: 가장 단순한 엔드투엔드 1회**
3. 읽기 전용, 네트워크 차단 환경에 3개 서비스를 체크아웃합니다.
4. 기성 에이전트 프레임워크(Claude Agent SDK 등)로, 도구는 `grep`/`read`/`ls`만 주고 단순한 프롬프트를 만듭니다. "진입점을 찾고, 각 진입점에서 입력이 위험한 싱크에 도달하는지 추적하고, 고정 JSON 스키마로 보고하라"는 내용입니다. 직접 에이전트를 만들지 않습니다.
5. 소형 서비스에서 전체 투입 방식(기준선)과 에이전트 방식을 둘 다 돌려 비교합니다.
6. 같은 서비스에 Semgrep 기본 규칙셋을 돌려 비교 기준으로 둡니다.

**마감 전: 기록**
7. 결과를 직접 검토해 유효/오탐/놓침을 표로 만들고, 토큰, 시간, 비용을 기록합니다. 정답셋 취약점을 찾았는지 확인합니다.
8. 둘째 날 결정 사항을 정리합니다. 어떤 방식이 나았는지, 오탐 패턴이 무엇인지, 검증 패스를 먼저 넣을지 진입점 추출을 먼저 개선할지를 정합니다.

첫날의 목표는 좋은 시스템이 아니라 숫자가 있는 기준선 하나입니다. 이 숫자가 있어야 임베딩 추가나 정적 분석 결합 같은 이후 투자를 근거 있게 결정할 수 있습니다.

원하시면 에이전트 프롬프트 초안, 출력 JSON 스키마, 정답셋 양식 중 하나를 바로 작성해 드리겠습니다.

# 초기 설계안과 구현 첫날 계획

## 1. 설계 방향: 임베딩 vs 전체 압축 — 둘 다 기본안으로 삼지 않는다

두 방법 모두 취약점 탐지에 약점이 있다.

- **임베딩 검색(RAG)**: 의미가 비슷한 코드를 찾아 주지만, 취약점은 "입력이 들어오는 곳(source) → 중간 처리 → 위험한 호출(sink)"처럼 **호출·데이터 흐름을 따라** 나타난다. 의미 유사도로는 이 흐름이 끊긴다. 인덱싱·갱신 인프라 비용도 크다.
- **저장소 전체 압축**: 압축해도 토큰이 크게 줄지 않거나, 줄이면 정작 필요한 세부가 사라진다. 컨텍스트가 길어질수록 중간 내용을 놓치고 비용이 급증한다. 수백 개 서비스에 반복하면 비용이 감당되지 않는다.

**제안: 에이전트형 탐색 + 정적 분석으로 좁히기.** LLM이 코드를 통째로 읽는 대신, 사람 보안 리뷰어처럼 grep·파일 열기·정의 찾기 도구로 필요한 부분만 따라가게 한다.

```
[서비스 저장소]
   │
   ├─ 1. 공격면 식별 (코드 기반, 저렴)
   │     라우트/핸들러/RPC/큐 소비자 등 외부 입력 진입점 목록화
   │     (정규식/tree-sitter, 또는 Semgrep/CodeQL 규칙)
   │
   ├─ 2. 후보 좁히기
   │     진입점별로 sink(SQL, exec, 파일, 역직렬화, SSRF, 인증 체크 누락 등) 도달 경로를 정적 도구로 추출
   │
   ├─ 3. LLM 에이전트 분석 (진입점/후보 단위로 작은 작업)
   │     도구: 파일 읽기, grep, 심볼 정의/참조 조회
   │     출력: 구조화된 findings (위치, 근거 경로, 공격 시나리오, 신뢰도)
   │
   ├─ 4. 검증
   │     두 번째 LLM 패스(반증 시도) + 가능하면 PoC/테스트 실행
   │
   └─ 5. 사람 리뷰 큐 + 피드백 저장 (오탐/미탐 라벨 → 평가셋으로 축적)
```

핵심 원칙:
1. **분석 단위를 "저장소"가 아니라 "진입점 하나 + 그 호출 체인"으로 쪼갠다.** 컨텍스트 한계 문제가 구조적으로 사라진다.
2. **LLM은 판단에, 결정적 도구는 탐색에.** 코드 검색·호출 그래프는 도구가 하고, LLM은 "이 경로가 실제로 악용 가능한가"를 판단한다.
3. **평가셋을 먼저 만든다.** 방식 비교는 감이 아니라 측정으로 한다. 자원이 한정된 팀에게 가장 중요한 투자다.
4. **서비스 하나로 시작**하고, 수백 개로의 확장(비용, 병렬화, 언어별 차이)은 효과가 확인된 뒤에 한다.

## 2. 구현 첫날 할 일

목표: 오늘 안에 "정답을 아는 문제"와 "가장 단순한 기준선"을 확보한다.

1. **대상 서비스 1~2개 선정** (언어 하나, 중간 규모, 과거 취약점 이력이 있는 것). 보안 티켓·버그바운티·모의해킹 보고서에서 **확인된 취약점 10~20건**을 모아 위치(파일/함수)와 함께 기록한다. 이것이 정답지다. 취약점이 수정되기 *전* 커밋을 체크아웃해 사용한다.
2. **데이터 취급 확인**: 소스코드를 어떤 모델/엔드포인트로 보낼 수 있는지(사내 승인된 API, 데이터 보관 정책)를 확인한다. 막히면 나머지가 전부 막힌다.
3. **기준선 구축(반나절)**: 진입점 하나를 골라, 그 핸들러와 호출하는 함수 몇 개를 직접 붙여 넣어 LLM에 분석시킨다. 에이전트 구조 없이 수동으로 돌려 보며 결과 품질과 토큰 규모를 감 잡는다.
4. **비교 대상 기준선**: 같은 서비스에 Semgrep 등 기존 SAST를 돌려 결과를 저장한다. LLM이 이걸 못 넘으면 가치가 없다.
5. 기록 형식(findings 스키마, 실행 로그)을 정한다.

## 3. 설계를 뒤집을 수 있는 핵심 가정

**가정: "취약점 탐지에 필요한 코드는 진입점에서 출발한 호출 체인을 따라 모으면 대부분 확보된다(즉, 국소적 컨텍스트로 충분하다)."**

이 가정이 틀리면 — 예컨대 실제 취약점이 서비스 간 호출, 전역 설정·미들웨어의 인증 처리, 여러 모듈에 흩어진 비즈니스 로직 상태에 의존한다면 — 진입점 단위 분할이 핵심 문맥을 잘라 버린다. 그러면 설계를 전역 인덱스(코드 그래프)·서비스 간 모델링 중심으로 크게 바꿔야 한다.

## 4. 가장 작은 실험

- **입력**: 첫날 모은 알려진 취약점 중 10~20건. 각 취약점마다 (a) 취약점이 있는 핸들러에서 시작해 (b) 에이전트가 도구로 코드를 따라가도록 한다. 취약점 위치는 알려 주지 않고, 진입점만 준다. 수정 전 커밋 기준.
- **추가 조사(근거 분류)**: 각 취약점에 대해 사람이 "이 취약점을 판단하는 데 필요한 코드가 호출 체인 안에 있는가, 밖(미들웨어, 설정, 다른 서비스)에 있는가"를 먼저 표시해 둔다.
- **비교 대상**:
  - A: 진입점+호출 체인 방식 (제안안)
  - B: 사람이 필요한 파일을 모두 골라 준 "오라클 컨텍스트" (상한선)
  - C: Semgrep 기준선
  - 임베딩 검색은 여력이 있을 때만 D로 추가해, 정말 필요한지 검증한다.
- **실패로 판단할 관찰 결과**:
  - A가 찾은 비율이 B보다 크게 낮고(예: 절반 이하), 놓친 건의 다수가 "체인 밖에 필요한 코드가 있었던" 경우로 분류될 때 → 국소 컨텍스트 가정 실패.
  - 또는 A와 B 모두 Semgrep(C)보다 재현율이 나쁘거나, 같은 수준이면서 오탐이 감당할 수 없이 많을 때 → 접근 자체의 가치 재검토.
  - 기준 숫자는 표본이 작으므로 실험 전에 먼저 합의해 두고, 결과를 본 뒤 바꾸지 않는다.

## 5. 실패했을 때: 직접 시도할 조치 vs 사용자 결정이 필요한 조건

**제가(또는 팀이) 바로 시도할 수 있는 조치**
- 체인 밖 코드가 원인이면: 미들웨어·인증 설정·공통 라이브러리를 항상 컨텍스트에 포함하는 "서비스 공통 요약"을 추가하고 재실험.
- 호출 체인 추출이 부정확하면: 심볼 조회 도구를 개선(tree-sitter, LSP, CodeQL DB)하고 재실험.
- 프롬프트·출력 스키마 조정, 반증 패스 추가, 모델 교체 후 재측정.
- 임베딩 검색을 보조 도구(에이전트가 부를 수 있는 검색 도구)로 추가해 개선되는지 확인.

**사용자(보안 연구 담당자) 결정이 필요한 조건**
- 소스코드를 외부 API로 보낼 수 없어 사내 호스팅 모델로 바꿔야 할 때(성능·비용·인력 영향).
- 서비스 간 취약점이 많아 **전역 코드 그래프 구축**처럼 투자가 큰 방향 전환이 필요할 때.
- 정답지가 부족해 새로 모의해킹·수동 리뷰 비용을 써야 할 때.
- 오탐률이 높아 사람 리뷰 부담이 감당 안 될 때, 허용 오탐 수준·탐지 대상 취약점 유형을 어디까지로 좁힐지.
- 실험 결과 기준선(Semgrep) 대비 이점이 작을 때, 프로젝트를 계속할지·범위를 줄일지(예: 인증/인가 로직 결함처럼 SAST가 약한 유형만).
- 실제 서비스 대상으로 PoC를 실행해야 할 때의 안전·승인 범위.
