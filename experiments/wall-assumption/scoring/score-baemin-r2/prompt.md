당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

사내 구성원의 데이터 질문에 답하는 AI 서비스를 운영하는 데이터팀입니다. 지금 서비스는 질문을 SQL로 바꿔 데이터를 조회하고, 테이블 정의·메타데이터·SQL 예시를 검색해 답하는 검색 기반 서비스입니다.

최근 질문이 데이터 조회를 넘어 사내 전반의 지식으로 넓어졌습니다. 예를 들어 업무 용어의 뜻, 회사 주소, 특정 업무의 담당자, 사내 프로젝트 설명, 서비스 성과 분석을 묻습니다. 이런 정보는 사내 포털, 위키, 이슈 관리 도구, 메신저 대화, 문서 저장소에 흩어져 있고, 각 도구의 기본 검색은 키워드 매칭이라 문서 목록만 보여 줍니다. 메신저에는 업무 지원 채널이 수백 개 있고, 담당자가 같은 질문에 여러 번 답합니다.

목표: 사내 지식 전반에 대한 질문에 한 곳에서 답한다. 이전 대화를 이어서 답한다. 불만족스러운 답이 나오면 바로 개선할 수 있게 한다. 반복되는 지원 채널 문의도 자동으로 응대한다.

초기 설계: 지금처럼 개발자가 처리 순서를 정한 워크플로(예: 검색 → 요약 → 검색 → 답변)에 새 지식 소스를 붙여 넓힌다. 지원 채널은 미리 등록한 질문–답변 쌍을 키워드로 찾아 답하는 FAQ 자동응답으로 시작한다.

# 초기 설계안과 구현 첫날 계획

## 1. 설계 요약

**기본 구조.** 도구(검색, SQL)를 공통 인터페이스로 분리하고, 그 위에서 질문을 처리하는 방식(고정 워크플로 또는 에이전트 루프)을 교체할 수 있게 둔다. 제안하신 초기 설계(고정 워크플로에 소스 추가)를 출발점으로 삼되, 처리 방식을 바꿔도 나머지가 영향받지 않도록 경계를 둔다.

| 구성 | 내용 |
|---|---|
| 도구 계층 | 기존 SQL 조회, 테이블/메타데이터 검색에 더해 포털, 위키, 이슈 도구, 문서 저장소, 메신저 검색을 같은 형태(입력: 질의와 사용자 ID, 출력: 출처 포함 스니펫)로 래핑 |
| 접근 권한 | 검색 시점에 질문자 권한으로 필터링. 메신저와 문서는 권한이 제각각이라 인덱스 단계에서 ACL 메타데이터를 보존 |
| 대화 맥락 | 세션 단위 히스토리를 저장하고, 후속 질문은 독립 질의로 재작성한 뒤 검색 |
| 답변 형식 | 항상 출처 링크를 붙이고, 근거가 부족하면 모른다고 답하며 담당자 후보를 안내 |
| 개선 루프 | 모든 질문에 트레이스(질의, 호출한 도구, 검색 결과, 최종 답)를 남기고 👍/👎와 사유를 수집. 👎 건은 평가셋 후보로 적재해 회귀 테스트에 사용 |
| 지원 채널 | 처음부터 자동 응대하지 않고 **초안 제안 모드**(담당자에게만 보임, 승인 후 게시)로 시작. FAQ 키워드 매칭은 폴백으로만 쓰고, 채널 이력에서 반복 질문을 군집화해 후보 FAQ를 만들며, 신뢰도가 검증된 군집만 자동 응대로 승격 |

**초기 설계에서 우려되는 점**
- 키워드 기반 FAQ는 기존 도구 검색과 같은 한계(표현이 다르면 못 찾음)를 가진다.
- "서비스 성과 분석"처럼 SQL과 문서를 오가는 질문은 고정 순서로 처리하기 어려울 수 있다.

## 2. 뒤집힐 수 있는 핵심 가정

> **"질문이 어떤 소스를 어떤 순서로 볼지 개발자가 미리 정해둔 소수의 워크플로로 충분히 커버된다."**

- 맞으면: 라우터와 파이프라인 몇 개로 예측 가능하고 저렴하며 디버깅이 쉬운 서비스가 된다.
- 틀리면: 소스를 붙일 때마다 분기가 폭증한다. 도구 선택과 반복 검색을 모델이 하는 에이전트 루프 중심으로 설계를 바꿔야 하고, 비용, 지연, 평가 방식, 안전장치(단계 상한, 권한)도 모두 달라진다.

용어, 주소, 담당자 같은 단일 소스 질문은 고정 워크플로로 충분할 가능성이 높다. 불확실한 쪽은 성과 분석처럼 여러 소스를 조합하는 질문의 비중과 난이도다.

## 3. 가장 작은 실험

- **입력**
  - 최근 실제 질문 로그에서 유형별(용어, 회사 정보, 담당자, 프로젝트 설명, 성과 분석)로 층화 추출한 약 60건. 이전 대화 의존 질문 일부 포함.
  - 각 질문에 대해 해당 분야 담당자가 정답 요지와 정답 근거 소스를 라벨링.
  - 소스는 전부 붙이지 않고, 라벨링된 정답이 있는 상위 3~4개 소스만 연결.
- **비교 대상** (같은 도구, 같은 모델, 같은 프롬프트 예산)
  - A: 라우터 + 고정 워크플로(검색 → 요약 → 필요 시 재검색 → 답변)
  - B: 같은 도구를 주고 모델이 선택하는 에이전트 루프(최대 8단계)
- **사전에 정해두는 실패 기준** (실행 전에 확정)
  - A의 정답률이 B보다 10%p 이상 낮음(전체 또는 다중 소스 층 기준), **또는**
  - 라벨링 단계에서 20% 이상의 질문이 기존 워크플로 어디에도 배정되지 않음.
  - 보조 관찰: B의 평균 비용과 지연이 A의 3배를 넘는지 함께 기록.
- **해석 주의점.** 실패가 오케스트레이션 때문인지 검색 품질 때문인지 구분하려고, 실패 건에는 정답 문서를 직접 넣어 한 번 더 돌린다. 정답 문서를 줘도 A만 실패하면 오케스트레이션 문제로 본다.

60건은 작은 표본이라 방향을 보는 용도이고, 차이가 기준 근처이면 확정하지 않는다.

## 4. 구현 첫날

1. **질문 로그 확보와 분류** (오전). 최근 질문을 뽑아 유형별로 나누고, 현재 서비스가 답하지 못한 비율을 확인한다.
2. **평가셋 라벨링 의뢰** (오전). 유형별 담당자에게 정답 요지와 근거를 요청한다. 가장 오래 걸리므로 먼저 시작한다.
3. **도구 인터페이스 확정** (오후). 기존 SQL/메타데이터 검색과 위키, 포털 중 접근이 가장 쉬운 두 소스를 같은 형태로 래핑한다. 사용자 ID 전달과 트레이스 기록을 처음부터 넣는다.
4. **A/B 실행 하네스 골격** (오후). 같은 질문 파일을 두 방식에 흘려보내고 결과를 한 표로 모으는 스크립트. 채점은 라벨 기준 수동 또는 루브릭 기반으로 한다.
5. **병행 확인.** 메신저 소스의 접근 방식(API 범위, 채널 권한)을 조사해 둔다. 실험 결과와 무관하게 설계에 영향이 크다.

## 5. 실패했을 때의 조치

**직접 시도할 수 있는 것**
- 정답 문서 주입 실험으로 원인 분리(검색 vs 오케스트레이션)
- 라우터 분류 기준과 프롬프트 조정, 워크플로 분기 1~2개 추가 후 재측정
- 표본 확대와 라벨 재검토(라벨 오류 가능성)
- 하이브리드 구성: 단일 소스 질문은 고정 워크플로, 다중 소스 질문만 에이전트 루프로 처리
- B의 비용과 지연 절감(단계 상한, 캐시, 작은 모델로 도구 선택)

**사용자 결정이 필요한 조건**
- 에이전트 방식을 채택하면 비용과 지연이 허용 예산을 넘는 경우(허용 수준 결정)
- 정답률 기준(예: 10%p)이나 "충분히 좋은 답"의 기준 자체를 바꿔야 하는 경우
- 메신저, 비공개 문서를 검색 대상에 넣을 때 권한 모델상 노출 위험이 남는 경우(범위 제한 또는 제외 결정)
- 지원 채널을 초안 모드에서 자동 응대로 승격할 신뢰도 기준과 오답 시 책임 범위
- 라벨링에 담당자 시간을 추가로 써야 하는 경우

실험은 아직 실행하지 않았고, 위 수치(60건, 10%p, 20%, 3배)는 시작용 제안값이라 팀 상황에 맞게 조정하셔도 됩니다. 다만 실행 전에 확정해야 결과를 사후 합리화하지 않게 됩니다.

## 응답 R-362B

# 사내 지식 통합 AI 서비스: 초기 설계안과 첫날 계획

## 1. 주어진 초기 설계의 문제

| 초기 설계 | 문제 |
|---|---|
| 고정 워크플로(검색→요약→검색→답변)에 소스를 추가 | 질문 유형이 용어 정의, 담당자, 프로젝트 설명, 성과 분석 등으로 다양합니다. 질문마다 필요한 소스와 단계 수가 달라 고정 순서로는 분기가 폭발합니다. 소스 하나를 붙일 때마다 워크플로를 고쳐야 합니다. |
| 키워드 기반 FAQ 자동응답 | 메신저 질문은 표현이 제각각이라 키워드 매칭이 자주 빗나갑니다. 등록한 Q&A는 금방 낡고, 사람이 계속 관리해야 합니다. 이미 수백 개 채널에 해답이 쌓여 있는데 활용하지 못합니다. |
| (빠져 있는 것) | 권한, 평가·피드백 루프, 대화 맥락, "모르겠다"고 답하는 기준이 없습니다. |

## 2. 제안 아키텍처

```
사용자 질문 (+ 세션 히스토리)
        │
   [질문 재작성: 대화 맥락 반영]
        │
   ┌────▼─────────────── 에이전트 루프 ───────────────┐
   │ LLM이 질문을 보고 도구를 고르고, 결과가 부족하면 │
   │ 질의를 바꿔 재검색 (최대 N회, 비용·시간 상한)    │
   └─┬────────┬─────────┬──────────┬─────────┬────────┘
     │        │         │          │         │
 데이터조회  위키/문서  이슈도구  메신저    담당자/조직
 (기존       검색      검색      스레드    조회
 text-to-SQL)                    검색
     └────────┴─────────┴──────────┴─────────┘
        │  모든 도구는 요청자 권한(ACL)으로 필터링
        ▼
   답변 + 출처 링크 + 근거 부족 시 "모름/담당자 안내"
        │
   로그·트레이스 저장 → 피드백 → 평가셋 → 개선
```

### 핵심 결정

1. **고정 워크플로 대신 도구 호출형 에이전트로 전환합니다.**
   - 소스는 "도구 + 설명" 단위로 추가합니다. 새 소스를 붙여도 흐름 코드를 건드리지 않습니다.
   - 기존 text-to-SQL 파이프라인은 버리지 않고 `query_data` 도구로 감쌉니다. 정확성이 중요한 구간은 결정적 워크플로로 두고, 상위에서만 에이전트가 선택합니다.
   - 비용과 지연을 막기 위해 최대 반복 횟수, 도구별 타임아웃, 단순 질문용 빠른 경로를 둡니다.

2. **검색은 소스별 인덱싱 후 하이브리드(키워드+임베딩)로 합니다.**
   - 각 도구의 기본 키워드 검색을 그대로 호출하는 방식(라이브 호출)과 자체 인덱스 방식을 소스별로 고릅니다.
   - 문서는 구조(제목, 섹션)를 살려 청킹하고, 메타데이터(작성자, 수정일, 접근 범위)를 함께 저장합니다.
   - 오래된 문서는 최신성 가중치와 수정일 표시로 다룹니다.

3. **권한은 설계 단계에서 확정합니다.**
   - 검색 시점에 질문자 권한으로 필터링합니다(문서 ACL, 비공개 채널 제외).
   - 이 부분이 어긋나면 서비스가 정보 유출 경로가 됩니다. 소스별 ACL을 API로 가져올 수 있는지가 선행 확인 사항입니다.

4. **대화 맥락은 세션 히스토리와 질문 재작성으로 처리합니다.** "그 담당자 연락처는?" 같은 후속 질문을 독립 질의로 바꿔 검색합니다. 장기 기억(개인화)은 2단계로 미룹니다.

5. **지원 채널 자동응대는 FAQ 대신 "해결된 스레드 + 문서" 기반 RAG로 갑니다.**
   - 과거 스레드에서 (질문, 해결 답변, 답한 사람, 날짜)를 추출해 검색 대상으로 삼습니다.
   - 신뢰도 기준을 둡니다. 높으면 근거 링크와 함께 답하고, 중간이면 담당자에게 초안을 제안하고, 낮으면 답하지 않고 담당자를 호출합니다.
   - 초기에는 **섀도 모드**(채널에 게시하지 않고 내부 기록)로 시작하고, 이후 초안 제안, 일부 채널 자동응답 순으로 확대합니다.
   - 담당자의 수정과 승인이 곧 학습 데이터가 됩니다.

6. **"바로 개선할 수 있는" 구조를 처음부터 넣습니다.**
   - 모든 요청의 트레이스(질문, 선택된 도구, 검색 결과, 최종 답변)를 저장합니다.
   - 👍/👎에 사유(틀림, 오래됨, 못 찾음, 권한)를 붙입니다.
   - 👎 건은 평가셋에 추가하고, 변경 때마다 평가셋으로 회귀 테스트를 돌립니다.
   - 원인이 검색(못 찾음)인지 생성(잘못 요약)인지 트레이스에서 구분되게 합니다.

## 3. 단계별 로드맵 (개략)

- **1단계 (2~3주)**: 평가셋, 트레이싱, 에이전트 골격에 기존 SQL 도구와 위키 1~2개 소스를 연결하고, 지원 채널 1~2개를 섀도 모드로 운영합니다.
- **2단계**: 나머지 소스(이슈, 메신저, 문서 저장소)와 ACL을 확대하고, 피드백 UI와 지원 채널 초안 제안을 붙입니다.
- **3단계**: 자동응답 채널을 확대하고, 장기 기억과 오래된 지식 탐지(문서 갱신 요청)를 추가합니다.

## 4. 구현 첫날 할 일

목표는 **코드를 많이 쓰는 것이 아니라 무엇을 측정할지와 무엇이 막힐지를 확정하는 것**입니다.

**오전: 현실 데이터 파악**
1. 현재 서비스 로그에서 최근 질문 200개 정도를 뽑아 유형(데이터 조회, 용어, 담당자, 프로젝트, 성과 분석, 기타)과 필요한 소스로 분류합니다.
2. 지원 채널 상위 10~20개(질문량 기준)에서 최근 스레드를 샘플링합니다. 반복 질문 비율, "해결된 스레드"를 식별할 신호(이모지, 답변자, 종료 표현)를 확인합니다.
3. 소스별 API 접근 가능 여부를 점검합니다: 수집 API, 권한(ACL) 조회, 호출 한도, 보안 승인이 필요한지입니다. 메신저와 비공개 채널의 정책 이슈는 오늘 보안팀에 문의를 올려야 합니다.

**오후: 기준선과 얇은 프로토타입**
4. 분류된 질문 중 50개 정도에 정답과 근거 문서를 붙여 **초기 평가셋**을 만듭니다(담당자 2~3명에게 검수 요청).
5. 트레이싱을 먼저 켭니다(질문, 도구 호출, 검색 결과, 답변, 지연, 비용 저장).
6. 기존 SQL 파이프라인을 도구 하나로 감싸고, 위키 검색 도구 1개를 붙인 최소 에이전트 루프를 만듭니다.
7. 평가셋으로 현재 시스템과 새 골격의 기준선 점수를 냅니다.

**하루 끝 산출물**
- 질문 유형 분포표와 소스 우선순위
- 소스별 접근·권한 체크리스트와 막힌 항목 목록
- 평가셋 v0(50문항)와 기준선 점수
- 트레이스가 남는 최소 프로토타입
- 다음 날 결정 사항: 첫 소스 확대 순서, 섀도 모드로 시작할 지원 채널 선정

## 5. 초기에 합의해 둘 위험 요소

- **권한 누수**: ACL 확인 전에는 비공개 소스를 인덱싱하지 않습니다.
- **그럴듯한 오답**: 근거 링크 필수, 근거가 약하면 "찾지 못했다"고 답하고 담당자를 안내합니다.
- **지원 채널 오응답**: 섀도 모드와 신뢰도 임계값 없이 자동 게시하지 않습니다.
- **비용·지연**: 에이전트 반복 상한과 질문 유형별 빠른 경로를 둡니다.

원하시면 다음으로 평가셋 스키마, 트레이스 필드 정의, 지원 채널 신뢰도 기준 설계 중 하나를 구체화해 드리겠습니다.
