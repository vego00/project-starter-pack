## 사례 입력 (응답자가 받은 내용)

사내 구성원의 데이터 질문에 답하는 AI 서비스를 운영하는 데이터팀입니다. 지금 서비스는 질문을 SQL로 바꿔 데이터를 조회하고, 테이블 정의·메타데이터·SQL 예시를 검색해 답하는 검색 기반 서비스입니다.

최근 질문이 데이터 조회를 넘어 사내 전반의 지식으로 넓어졌습니다. 예를 들어 업무 용어의 뜻, 회사 주소, 특정 업무의 담당자, 사내 프로젝트 설명, 서비스 성과 분석을 묻습니다. 이런 정보는 사내 포털, 위키, 이슈 관리 도구, 메신저 대화, 문서 저장소에 흩어져 있고, 각 도구의 기본 검색은 키워드 매칭이라 문서 목록만 보여 줍니다. 메신저에는 업무 지원 채널이 수백 개 있고, 담당자가 같은 질문에 여러 번 답합니다.

목표: 사내 지식 전반에 대한 질문에 한 곳에서 답한다. 이전 대화를 이어서 답한다. 불만족스러운 답이 나오면 바로 개선할 수 있게 한다. 반복되는 지원 채널 문의도 자동으로 응대한다.

초기 설계: 지금처럼 개발자가 처리 순서를 정한 워크플로(예: 검색 → 요약 → 검색 → 답변)에 새 지식 소스를 붙여 넓힌다. 지원 채널은 미리 등록한 질문–답변 쌍을 키워드로 찾아 답하는 FAQ 자동응답으로 시작한다.

# 초기 설계안 및 첫날 계획

## 1. 설계 방향 요약

주어진 초기 설계(고정 워크플로 + 키워드 FAQ)는 그대로 확장하면 두 가지 문제가 생길 가능성이 큽니다.

- 질문 유형이 열려 있어서(용어, 주소, 담당자, 프로젝트, 성과 분석) 고정 순서로는 분기가 폭증합니다.
- 키워드 FAQ는 각 도구 기본 검색의 한계(표현이 다르면 못 찾음)를 그대로 재현합니다.

그래서 아래 구조를 제안합니다.

**A. 라우터 + 소스별 도구를 가진 에이전트형 구조 (단, 범위를 제한)**
- 1단계: 질문 분류기 (데이터 조회 / 사내 지식 / 담당자·조직 / 분석 / 범위 밖). 기존 text-to-SQL 경로는 **그대로 유지**하고 하나의 도구로 취급합니다.
- 2단계: 사내 지식 질문은 LLM이 도구(소스별 검색, SQL 조회, 담당자 조회)를 골라 호출하는 반복 루프. 호출 횟수·시간 상한을 둡니다.
- 고정 워크플로는 "성과 분석"처럼 순서가 정해진 반복 업무에만 남깁니다.

**B. 지식 계층**
- 소스별 커넥터(포털, 위키, 이슈, 문서 저장소, 메신저)로 수집 → 공통 스키마(본문, 출처 URL, 수정일, 권한, 소스 유형)로 정규화 → 하이브리드 검색(키워드 + 임베딩) + 재순위.
- **권한 상속**: 원본 접근 권한을 검색 시점에 적용합니다. 메신저·비공개 문서 때문에 가장 위험한 부분입니다.
- 모든 답변에 출처 링크와 문서 수정일을 표시하고, 근거가 부족하면 "모르겠다"고 답합니다.

**C. 대화 맥락**
- 세션 단위 대화 기록 + 후속 질문을 독립 질문으로 다시 쓰는 단계. 장기 메모리는 1차에서 제외합니다.

**D. 개선 루프**
- 답변마다 👍/👎 + 사유(틀림/오래됨/출처 없음)를 수집하고, 질문·검색 결과·도구 호출 기록·답변을 함께 저장합니다.
- 👎 건을 평가셋으로 쌓아 변경 때마다 회귀 테스트합니다. 즉시 수정이 필요하면 "정정 답변" 등록(우선 검색되는 큐레이션 항목)을 지원합니다.

**E. 지원 채널 자동응대**
- 키워드 FAQ 대신, 과거 채널 스레드(질문 → 담당자 답변)를 검색해 답을 초안으로 만드는 방식.
- 1차는 **자동 게시가 아니라 제안 모드**(담당자에게만 보이는 초안 또는 "비슷한 과거 답변" 링크)로 시작하고, 채널별 정확도가 기준을 넘으면 자동 응대로 전환합니다.
- 담당자가 승인·수정한 답변은 다시 지식으로 환류합니다.

## 2. 구현 첫날 계획

목표: 설계 전체를 만들지 않고, 아래 가정을 가장 싸게 검증할 수 있는 상태까지 가기.

1. (1~2시간) 실제 질문 로그에서 최근 질문 약 100~200건을 뽑아 유형별로 분류하고, 소스별로 답이 어디 있는지 사람이 표시합니다. 이것이 평가셋 v0입니다.
2. (1시간) 각 소스의 API 접근, 권한 모델, 내보내기 가능 여부를 확인합니다. 메신저 수집 허용 여부는 이 시점에 보안/법무 확인 요청을 보냅니다(대기 시간이 길기 때문).
3. (2~3시간) 가장 쉬운 소스 1~2개(위키 + 문서 저장소)만 수집해 임베딩 + 키워드 하이브리드 검색을 붙이는 스크립트를 만듭니다.
4. (남은 시간) 아래 실험을 실행합니다.

## 3. 뒤집히면 설계가 크게 바뀌는 가정

**가정: "질문의 대다수는 한두 번의 검색(단일 소스 또는 하이브리드 검색 한 번)으로 근거를 찾을 수 있다."**

- 맞다면: 에이전트 루프 없이 "검색 한 번 → 답변"의 단순 RAG + 라우터로 충분하고, 고정 워크플로 확장도 가능합니다.
- 틀리다면(여러 소스를 조합하거나, 검색 결과를 보고 다음 검색을 정해야 하는 질문이 많다면): 반복 호출형 에이전트 구조, 도구 설계, 비용·지연 관리, 평가 방식이 모두 달라집니다. 이 가정이 틀렸을 때 비용이 가장 크기 때문에 이것을 고릅니다.

(참고: "메신저 데이터를 지식원으로 쓸 수 있다"는 가정도 설계를 크게 바꾸지만, 이것은 실험이 아니라 보안/법무 확인 사안이라 2번 항목에서 별도로 처리합니다.)

## 4. 가장 작은 실험

- **입력**: 평가셋 v0에서 뽑은 질문 50건(유형별 균형: 용어, 주소/조직, 담당자, 프로젝트, 성과 분석), 각 질문의 정답 근거 문서를 사람이 미리 표시. 수집된 소스(위키 + 문서 저장소)만 사용하고, 정답 근거가 그 소스에 있는 질문만 포함(없는 질문은 별도 "소스 부재" 표시).
- **비교 대상**:
  - (a) 검색 1회(하이브리드 top-k) → 답변
  - (b) 최대 4회까지 LLM이 검색을 반복·재작성하는 루프 → 답변
  - 기준선: 기존 도구 기본 키워드 검색의 top-5에 정답 문서가 있는 비율
- **측정**: 정답 근거 문서 포함률(retrieval hit@5), 사람이 채점한 답변 정확도, 호출 횟수·지연·비용.
- **실패 판단(= 가정이 틀림)**: (a)가 (b)보다 정확도가 10%p 이상 낮거나, 질문의 30% 이상에서 (a)의 top-5에 정답 근거가 없고 (b)에서는 찾아지는 경우. 즉, 단순 RAG로는 부족하고 반복 검색이 실질적으로 필요하다는 관찰입니다. (임계값은 임시이며 평가셋을 보고 조정합니다.)
- 반대로 (a)와 (b)가 비슷하면 가정이 유지되어 단순 구조로 갑니다. 둘 다 낮으면 가정이 아니라 수집·청킹·소스 커버리지 문제로 봅니다.

## 5. 실패 시 조치

**직접 시도할 조치 (사용자 결정 불필요)**
- 청킹 크기, 메타데이터(제목·경로·수정일) 포함 방식, 임베딩 모델, 재순위 추가, 질의 재작성 프롬프트 조정 후 재측정
- 루프 상한(호출 횟수), 도구 설명 개선, 소스 선택 힌트 추가 등 (b) 쪽 튜닝
- 평가셋 라벨 오류 점검, 채점 기준 보정
- 위키·문서 외 소스를 읽기 전용으로 추가 수집(이미 접근 권한이 확인된 범위 내)

**사용자 결정이 필요한 조건**
- (b)가 필요한 것으로 확인되어 지연·비용이 늘어나는 구조(응답 시간 목표 완화, 질문당 비용 상한)로 가야 할 때
- 정확도 개선에 메신저 등 민감 소스 수집이 필요하고, 보안/법무 승인이나 권한 정책(누구에게 무엇을 보여줄지)이 걸릴 때
- 외부 LLM/임베딩 API로 사내 문서를 보내야 하는 경우
- 평가 기준(허용 오답률, "모르겠다" 허용 비율)을 정해야 할 때
- 기존 워크플로 서비스를 병행 유지할지, 교체할지 일정과 인력을 정해야 할 때
- 지원 채널 자동 게시로 전환하는 정확도 기준과 채널 범위 확정

# 사내 지식 질의응답 서비스: 초기 설계안과 구현 첫날 계획

## 0. 초기 설계에 대한 판단

제시된 초기 설계(고정 워크플로 + 키워드 FAQ)는 두 지점에서 목표와 어긋날 가능성이 큽니다.

| 초기 설계 | 문제 | 제안 |
|---|---|---|
| 개발자가 정한 순서(검색→요약→검색→답변)에 소스를 추가 | 질문 유형이 "용어 뜻", "담당자", "성과 분석(SQL + 문서)"처럼 달라서, 소스가 늘수록 분기와 순서 조합이 폭증합니다. 새 질문 유형마다 개발자가 개입해야 해 "바로 개선"이 어렵습니다. | **에이전트 루프 + 도구**. 모델이 어떤 소스를 몇 번 검색할지 정하고, 결정적이어야 하는 부분(SQL 생성·실행)만 워크플로로 도구화합니다. |
| 등록된 Q&A를 키워드로 매칭 | 이미 각 도구의 키워드 검색이 불만인데 같은 방식을 반복합니다. 수백 개 채널의 Q&A를 수동 등록하면 금방 낡습니다. | **과거 스레드에서 Q&A를 자동 추출하고 의미 기반 검색**. 신뢰도에 따라 응대 수준을 단계적으로 높입니다. |

현재 서비스의 SQL 파이프라인은 버리지 않고 `query_data` 도구로 감쌉니다.

## 1. 전체 구조

```
사용자 (포털/메신저)
   │
   ▼
[Gateway] 인증 · 사용자 ID · 세션 · 권한 토큰
   │
   ▼
[Agent 루프]  ← 대화 이력/요약 (Memory)
   │  도구 호출 (병렬 가능)
   ├─ search_wiki / search_portal / search_issues / search_docs / search_chat
   ├─ fetch_document(id)         # 검색 결과 원문 확인
   ├─ query_data(question)       # 기존 text-to-SQL 파이프라인
   ├─ lookup_glossary / find_owner
   └─ search_support_history     # 지원 채널 과거 해결 사례
   │
   ▼
답변 + 출처 링크 + 신뢰도 → 피드백 수집
   │
   ▼
[Trace 저장소] 질문·재작성 쿼리·도구 호출·검색 결과·답변·피드백
   │
   ▼
[개선 루프] 실패 분류 → 평가셋 편입 → 수정 → 회귀 테스트
```

### 1.1 지식 계층
- **커넥터**: 소스별로 `수집 → 정규화 → 청크 → 색인`을 하는 동일한 인터페이스를 둡니다. 소스를 추가해도 에이전트 코드는 바꾸지 않고 도구만 등록합니다.
- **색인**: 하이브리드 검색(BM25 + 임베딩)과 메타데이터(소스, 작성자, 수정일, 접근권한)를 사용합니다. 사내 용어, 약어, 고유명사는 키워드가 강하고 의미 질문은 임베딩이 강해서 둘 다 필요합니다.
- **권한(최우선 제약)**: 문서의 ACL을 색인에 같이 저장하고, 검색 시 **질문자 권한으로 필터링**합니다. 비공개 채널 내용이 다른 사람 답변에 섞이면 안 됩니다. 이 방식이 어렵다면 해당 소스는 후순위로 둡니다.
- **신선도**: 수정일과 출처를 답변에 노출하고, 오래된 문서는 가중치를 낮춥니다.
- **메신저**: 잡담이 많으므로 스레드 단위로 묶고 "질문 + 채택/확인된 답" 형태만 지식으로 승격합니다.

### 1.2 에이전트
- 시스템 프롬프트에 소스별 특성(무엇이 어디에 있는지), 답변 규칙(출처 필수, 근거 없으면 모른다고 답변, 담당자 안내)을 둡니다.
- 최대 도구 호출 횟수와 비용 상한을 둡니다.
- "회사 주소"처럼 단순한 질문은 1회 검색으로 끝나고, "서비스 성과 분석"은 `query_data`와 문서 검색을 조합하게 합니다.

### 1.3 대화 연속성
- 세션 이력을 유지하고, 길어지면 요약합니다.
- 후속 질문("그럼 담당자는?")은 이력을 바탕으로 독립 질의로 재작성한 뒤 검색합니다.
- 사용자 장기 기억은 1차 범위에서 제외합니다. 개인정보와 오답 고착 위험이 있고, 세션 단위로도 목표를 충족합니다.

### 1.4 불만족 답변의 즉시 개선 경로
1. 답변마다 👍/👎와 사유(틀림, 오래됨, 못 찾음, 권한)를 받습니다.
2. 모든 실행을 trace로 남깁니다. 어떤 문서를 가져와 왜 그렇게 답했는지 재현할 수 있어야 합니다.
3. 👎 건을 원인별로 분류합니다.
   - **소스 문서 오류/누락** → 문서 수정 요청 또는 용어집에 항목 추가
   - **검색 실패** → 색인, 동의어, 청크 조정
   - **추론/지침 문제** → 프롬프트나 도구 설명 수정
   - **소스 미연결** → 커넥터 백로그
4. 수정한 건은 평가셋에 편입하고 배포 전 회귀 테스트를 돌립니다.
5. 데이터팀이 검수하는 **용어집/정답 보정 저장소**를 두어, 코드 배포 없이 즉시 반영되게 합니다.

### 1.5 지원 채널 자동 응대
FAQ 자동응답이 아니라 **과거 해결 사례 기반 응대**로 설계하고, 단계적으로 자동화 수준을 올립니다.

| 단계 | 동작 | 진입 조건 |
|---|---|---|
| 0. 섀도 모드 | 새 질문에 대한 답을 내부에만 기록하고, 이후 담당자 실제 답과 비교 | 채널 선정 직후 |
| 1. 담당자 초안 | 담당자에게만 초안과 근거를 보여 줌 (1클릭 게시) | 섀도 정확도 기준 충족 |
| 2. 자동 답변 | 신뢰도 높음 + 승인된 유형만 직접 답변, 담당자 호출 버튼과 "해결됨" 확인 포함 | 채널·유형별 승인 |
| 3. 에스컬레이션 | 신뢰도 낮음, 장애·인사·권한 등 민감 유형은 자동 답변 금지, 담당자 멘션 | 상시 |

과거 스레드에서 질문과 해결 답변을 자동 추출해 후보로 만들고, 담당자가 검수한 것만 "승인 지식"으로 올립니다. 답변이 틀리면 담당자의 이모지 반응이나 수정이 곧 피드백이 됩니다.

## 2. 단계 계획

| 단계 | 기간(가안) | 내용 |
|---|---|---|
| P0 | 1주 | 평가셋, trace 로깅, 현행 서비스 베이스라인 측정 |
| P1 | 2~3주 | 에이전트 루프 + 2개 소스(위키, 포털) + `query_data` 도구화 + 권한 필터 + 세션 대화 |
| P2 | 2~3주 | 이슈 도구·문서 저장소·메신저 추가, 피드백 UI, 분류 대시보드 |
| P3 | 병행 | 지원 채널 섀도 모드 → 초안 → 자동 답변 |

## 3. 구현 첫날 할 일

기능 구현보다 **무엇을 맞다고 볼지 정하고 현재 위치를 측정하는 일**부터 시작합니다. 이게 없으면 에이전트 방식이 실제로 나은지 알 수 없습니다.

1. **실제 질문 수집 (오전)**
   - 현재 서비스 로그에서 최근 질문 100~200건을 추출합니다. 개인정보는 마스킹합니다.
   - 유형별로 분류합니다: 데이터 조회 / 용어 / 사람·담당 / 프로젝트 / 성과 분석 / 기타(범위 밖).
2. **평가셋 초안 (오전~점심)**
   - 유형별로 균형 있게 50건을 골라 기대 답변과 정답 출처를 팀이 직접 표기합니다. 이 세트가 이후 모든 변경의 기준입니다.
3. **베이스라인 측정 (오후)**
   - 현행 서비스에 평가셋을 돌려 유형별 정답률을 측정합니다. 가장 약한 유형이 우선순위를 알려 줍니다.
4. **trace 스키마 확정과 로깅 (오후)**
   - 필드: 세션 ID, 사용자, 원 질문, 재작성 쿼리, 도구 호출과 결과, 최종 답변, 출처, 피드백. 지금 서비스에도 우선 붙입니다.
5. **지원 채널 샘플 분석 (오후, 병렬 담당자)**
   - 채널 2~3개의 최근 3개월 스레드를 내려받아 **실제로 반복되는 비율**과 유형을 봅니다. 반복이 낮거나 답변이 사람 판단에 의존한다면 자동 응대 범위를 좁혀야 합니다.
6. **권한 모델 확인 (일과 종료 전)**
   - 위키, 이슈, 메신저, 문서 저장소 각각에서 API로 ACL을 가져올 수 있는지 확인하고, 안 되는 소스를 표로 정리합니다. 이 결과가 연결 순서를 결정합니다.

첫날 산출물은 **평가셋 50건, 베이스라인 점수표, trace 스키마, 소스별 권한 가능 여부 표, 지원 채널 반복률 초기 수치**입니다.

## 4. 열린 질문과 위험

- 메신저 비공개 채널의 내용을 답변에 쓸 수 있는지에 대한 정책 결정(보안·법무 확인)이 필요합니다.
- 에이전트 방식은 지연과 비용이 늘 수 있습니다. 단순 질문의 빠른 경로(검색 1회)와 호출 상한이 필요합니다.
- 성과 분석처럼 해석이 필요한 답은 수치 출처(SQL, 기준일)를 반드시 같이 보여 주고, 확정이 아닌 참고임을 표기합니다.
- 자동 답변의 오답 비용이 큽니다. 승인 유형과 신뢰도 임계값을 보수적으로 시작합니다.
