# 초기 설계안: 리뷰 자동 라벨링 도구

## 1. 핵심 판단
말씀하신 "키워드 → 서비스/유형 매핑"은 제약(문장이 정돈되지 않고 맥락 판단 필요)과 충돌합니다. 그래서 키워드 매핑을 **주 분류기가 아니라 비교 기준선(baseline)** 으로 두고, 주 설계는 **LLM 분류 + 사람 검수** 로 제안합니다.

## 2. 설계안

**흐름**
1. 리뷰 입력 (CSV/엑셀)
2. LLM이 리뷰별로 `관련 서비스 / 유형 / 세부 유형 / 확신도` 출력
3. 허용 라벨 목록(택소노미) 밖의 값은 거부 (고정 목록에서만 선택)
4. 확신도가 낮거나 라벨이 애매한 건만 사람 검수 목록으로 분리
5. 결과를 엑셀로 저장 → 월간 리포트 시각화에 사용

**구성 요소**
- 라벨 정의표: 서비스·유형·세부 유형 목록과 각 항목의 설명, 경계 사례 예시 (이미 손으로 붙인 라벨이 기반)
- 분류 프롬프트: 정의표 + 소수의 예시(few-shot)를 포함
- 검수 시트: 낮은 확신도 건만 모아 사람이 수정
- 정답 데이터(골든 셋): 기존 수작업 라벨 200~300건. 평가 전용이고 학습·예시와 분리

**도구 선택**: 코드를 거의 안 쓰는 길을 우선합니다. 파이썬 스크립트 하나(입력 파일 → 출력 파일)로 시작하고, 웹 화면·DB·자동 스케줄링은 만들지 않습니다.

## 3. 구현 첫날 할 일
코드보다 **데이터 준비**가 먼저입니다.
1. 지금까지 붙인 수작업 라벨이 있는 리뷰를 내보내 파일 하나로 모읍니다.
2. 라벨 값 목록을 뽑아 표기가 흔들리는 곳(띄어쓰기, 비슷한 이름)을 정리합니다. 이것이 택소노미 초안입니다.
3. 최근 리뷰 중 250건 정도를 무작위로 골라 골든 셋으로 따로 보관합니다.
4. 그 셋의 라벨 분포를 봅니다. 특정 라벨이 거의 없거나 "기타"가 많은지 확인합니다.
5. 시간이 남으면 키워드 기준선을 만들어 골든 셋 정확도를 측정합니다.

## 4. 틀리면 설계가 크게 바뀔 가정 하나
**"내 수작업 라벨이 일관적이어서, 라벨 정의표만으로 기준을 설명할 수 있다."**

라벨이 담당자 머릿속 판단이나 시기별 기준 변화에 의존한다면, 정의표와 예시로 LLM에 기준을 전달할 수 없습니다. 이 경우 설계는 "정의표 + 프롬프트"에서 "기준 재정립 먼저, 그다음 자동화"로 바뀝니다. 정답 자체가 흔들리기 때문에 어떤 방식도 정확도를 평가할 수 없습니다.

## 5. 가장 작은 실험

- **입력**: 골든 셋에서 무작위 100건. 같은 100건을 시간을 두고(예: 며칠 뒤) 라벨을 가리고 다시 직접 라벨링합니다.
- **비교 대상**: 과거 라벨 vs 이번 재라벨 (본인 vs 본인). 보조로 LLM 라벨 vs 과거 라벨도 같이 봅니다.
- **실패 판단**: 
  - 본인 일치율이 약 80% 미만이거나, 특정 유형·세부 유형에서 불일치가 몰리면 실패(기준이 일관적이지 않음). 
  - 80%는 임의의 시작 기준이므로 첫 결과를 보고 조정해도 됩니다.
  - LLM 일치율이 본인 재라벨 일치율보다 크게 낮은 것도 신호입니다. 이 경우 문제는 프롬프트나 정의표에 있습니다.
  - 불일치가 "어느 한쪽이 틀림"이 아니라 "둘 다 말이 되는" 형태라면, 택소노미 중복이 원인입니다.

## 6. 실패 시 조치

**직접 시도할 수 있는 조치 (사용자 결정 불필요)**
- 불일치 건을 모아 유형별로 분석하고, 정의표 문구와 경계 사례 예시를 보강
- 겹치는 세부 유형 후보를 정리안으로 작성해 제안
- 프롬프트의 예시를 불일치가 많은 라벨 중심으로 교체하고 골든 셋으로 재측정
- 확신도 기준을 낮춰 검수 대상 비율을 조정해 보기

**사용자 결정이 필요한 조건**
- 택소노미를 실제로 합치거나 삭제하거나 새로 만들어야 할 때 (리포트의 과거 데이터와 비교 가능성이 바뀜)
- 본인 일치율이 계속 낮아 "어느 기준이 맞는지" 정해야 할 때 (조직의 판단 기준)
- 자동화 비율과 오류 허용 수준: 예를 들어 검수 없이 자동 확정할 확신도 선, 월 리뷰 수 대비 검수 시간
- 리뷰 원문을 외부 LLM API로 보내도 되는지 (개인정보·사내 보안 정책 확인 필요)
- 비용이 월 예산을 넘을 때

## 7. 키워드 매핑 방식에 대해
완전히 버리지 않습니다. 기준선으로 먼저 정확도를 재면, LLM 방식이 실제로 얼마나 나은지 숫자로 확인되어 판단 근거가 됩니다. 단, 키워드 도구를 먼저 완성도 있게 만드는 데 시간을 쓰는 것은 권하지 않습니다.

원하시면 첫날 1~3단계를 위한 데이터 정리 스크립트부터 같이 만들어 드리겠습니다. 라벨 데이터가 어떤 형식(엑셀, 시트, 관리 툴)에 있는지 알려주세요.

# 앱 리뷰 자동 라벨링 도구: 초기 설계안과 구현 첫날 계획

## 1. 핵심 제안: 키워드 매핑 대신 LLM 분류로 시작하기

말씀하신 "키워드 매핑으로 첫 도구를 만든다"는 방향은 바꾸시길 권합니다. 제약에 이미 답이 있습니다. 리뷰 문장이 정돈되어 있지 않고 맥락 판단이 필요하다면, 키워드 매칭은 바로 한계에 부딪힙니다. 예를 들어 "배송 빠른데 앱이 자꾸 꺼져요"는 배송 키워드가 있어도 실제 유형은 앱 오류일 수 있습니다. 부정문, 비꼬는 표현, 오타, 한 리뷰에 여러 이슈가 섞인 경우도 키워드로는 규칙이 끝없이 늘어납니다.

대신 **LLM API(예: Claude)에 리뷰와 라벨 정의를 주고 분류시키는 방식**을 권합니다. 개발 경험이 적어도 오히려 더 쉽습니다. 규칙 코드를 짜는 대신 라벨 정의를 글로 쓰면 되기 때문입니다. 키워드 사전은 버리는 것이 아니라 보조 수단(명백한 케이스 사전 필터, 검증용)으로 남겨둘 수 있습니다.

## 2. 설계안

**전체 흐름**

```
리뷰 파일(CSV/엑셀) → 읽기 → LLM 분류 → 결과 파일(라벨 3개 + 신뢰도) → 사람 검수 → 월간 집계/차트
```

**구성 요소**

| 구성 | 내용 |
|---|---|
| 입력 | 현재 쓰는 리뷰 파일(CSV 또는 엑셀 내보내기) |
| 라벨 체계 | `labels.yaml` 한 파일에 서비스·유형·세부 유형 목록과 각각의 정의, 예시 2~3개를 기록 |
| 분류기 | 리뷰 1건(또는 10~20건 묶음)당 LLM을 호출하고, 정해진 JSON 형식으로 라벨을 반환 |
| 출력 | 원본 컬럼 + 관련 서비스, 유형, 세부 유형, 신뢰도(상/중/하), 판단 근거 한 줄 |
| 검수 | 신뢰도 '하' 또는 라벨 체계에 없는 값은 "검수 필요" 표시, 사람이 확인 |
| 집계 | 라벨 결과로 월별 건수·비율 표와 차트 생성 (이후 단계) |

**핵심 설계 결정**

- **라벨은 고정 목록에서만 선택**하게 합니다. 목록에 없는 값이 나오면 "기타/판단불가"로 보내 검수 대상이 됩니다. 월별 비교가 가능하려면 라벨 일관성이 필수입니다.
- **지금까지 손으로 붙인 라벨을 정답지로 활용**합니다. 과거 라벨링 데이터 100~200건이 있으면 도구의 정확도를 숫자로 측정할 수 있습니다.
- **사람 검수는 처음엔 전수, 정확도가 확인되면 표본·저신뢰 건만**으로 줄입니다. 리포트가 구성원에게 공유되므로 처음부터 완전 자동화하지 않습니다.
- **라벨 정의가 곧 성능**입니다. 세부 유형 간 경계가 모호한 곳이 오분류의 주원인이므로, 정의와 예시를 다듬는 것이 코드보다 중요합니다.
- 비용은 리뷰 수천 건 규모라면 보통 월 수천~수만 원 수준으로 예상되지만, 실제 건수와 모델에 따라 달라지므로 첫날 소량으로 측정해 보세요.
- 리뷰에 개인정보(이름, 연락처 등)가 섞여 있을 수 있으니, 외부 API로 보내도 되는지 사내 정책을 확인하세요.

**기술 선택(개발 경험이 적은 점 고려)**

- Python 스크립트 1개 + 설정 파일 1개로 시작합니다. 웹 화면, DB, 서버는 만들지 않습니다.
- 실행은 터미널에서 `python label.py reviews.csv` 한 줄로 합니다.
- AI 코딩 도구(Claude Code 등)에게 이 설계안을 그대로 주고 만들게 할 수 있는 크기입니다.

## 3. 구현 첫날 계획

목표: **오늘 안에 리뷰 50건이 라벨링되어 정답과 비교된 표를 보는 것.**

1. **(30분) 정답 데이터 준비**: 이미 손으로 라벨링한 리뷰 중 최근 100건 정도를 CSV로 저장합니다. 컬럼은 `리뷰내용, 관련서비스, 유형, 세부유형`. 이후 모든 개선의 기준이 됩니다. 라벨이 달린 과거 데이터가 없다면 오늘 30~50건을 새로 라벨링하세요.
2. **(40분) 라벨 체계 문서화**: 지금 머릿속에 있는 분류 기준을 `labels.yaml`로 옮깁니다. 서비스 목록, 유형 목록, 유형별 세부 유형, 각각 한 줄 정의와 대표 리뷰 예시 2개. 헷갈리는 경계 사례("이건 A가 아니라 B로 분류")도 적어둡니다.
3. **(20분) 환경 준비**: Python 설치 확인, API 키 발급(키는 코드에 직접 쓰지 않고 환경변수로 관리), 프로젝트 폴더 생성. 막히면 AI 코딩 도구에게 단계별로 안내받으세요.
4. **(60분) 최소 분류기 제작**: AI 코딩 도구에게 요청합니다. 예시 프롬프트:
   > "reviews.csv의 각 리뷰를 labels.yaml 기준으로 분류해 관련서비스·유형·세부유형·신뢰도·근거를 CSV로 저장하는 Python 스크립트를 만들어줘. 라벨은 yaml에 있는 값만 허용하고, 아니면 '판단불가'로 처리해. 처음엔 10건만 돌리는 옵션도 넣어줘."
5. **(30분) 10건 시험 실행 후 50건 확대**: 결과를 눈으로 확인합니다.
6. **(30분) 정답과 비교**: 일치율을 라벨 3개 각각 계산하고, 틀린 건을 모아 원인을 분류합니다(정의 모호, 예시 부족, 정답 자체가 애매 등).

**첫날 종료 시 산출물**: `labels.yaml`, `label.py`, 정답 대비 일치율 숫자, 틀린 사례 목록.

## 4. 이후 단계 (참고)

- **2~3일차**: 틀린 사례를 반영해 라벨 정의·예시 보강, 전체 정답 데이터로 재측정. 목표 일치율(예: 서비스 95%, 유형 90% 등)을 정해 두세요.
- **1주차 말**: 실제 월간 데이터로 시험 가동, 검수 시간을 측정해 기존 6시간과 비교.
