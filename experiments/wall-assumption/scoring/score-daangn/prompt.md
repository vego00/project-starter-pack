# 초기 설계안: 앱 리뷰 자동 라벨링 도구

## 0. 먼저 짚을 점
말씀하신 "키워드 매핑으로 첫 도구를 만든다"는 방식은 제약과 충돌합니다. 리뷰가 정돈되지 않았고 맥락 판단이 필요하다면 키워드 매칭은 정확도가 낮을 가능성이 큽니다. 예를 들어 "배달 빨라서 좋은데 앱이 자꾸 꺼져요"는 서비스와 유형이 둘 이상이고, "결제가 안 돼서 환불했다"는 키워드만으로 유형이 갈립니다. 그래서 **LLM 기반 분류를 주력**으로 하고, 키워드는 보조 역할(사전 필터, 검증)로만 쓰는 것을 제안합니다. 개발 난이도도 오히려 낮습니다. 규칙을 일일이 만드는 대신 라벨 정의와 예시를 프롬프트에 쓰면 됩니다.

## 1. 목표와 성공 기준
- 목표: 월 6시간+ 수작업을 1시간 이내의 검수 작업으로 축소
- 성공 기준(초기안): 사람이 붙인 라벨과 비교해 일치율 80~85% 이상 (라벨 축별로 측정), 확신 낮은 건은 자동으로 "검수 필요"로 분리

## 2. 전체 구조 (단순하게)
```
[리뷰 파일(CSV/엑셀)] → [전처리] → [LLM 분류] → [검증/신뢰도 체크] → [결과 CSV] → [사람 검수] → [월간 리포트 시각화]
```
1. **입력**: 지금 쓰는 엑셀/CSV 그대로. 컬럼은 리뷰 ID, 날짜, 본문 정도
2. **전처리**: 빈 값, 중복 제거 정도만 (문장을 정제하지 않음)
3. **LLM 분류**: 리뷰 한 건당 `관련 서비스`, `유형`, `세부 유형`, `근거 한 줄`, `확신도`를 JSON으로 받음
4. **검증**: 라벨이 허용된 목록에 있는지 확인하고, 아니면 재시도 또는 "검수 필요" 처리
5. **출력**: 원본 + 라벨 컬럼이 붙은 CSV. 검수 필요 건은 따로 표시
6. **피드백**: 사람이 고친 라벨은 예시 모음에 추가해 다음 달 정확도 개선

## 3. 핵심 설계 결정
- **라벨 체계를 문서로 고정**: 서비스, 유형, 세부 유형 목록과 각 정의, 경계 사례를 하나의 파일(예: `labels.yaml`)에 둠. 코드 수정 없이 이 파일만 고치면 됨
- **few-shot 예시**: 기존에 손으로 붙인 라벨 중 대표 사례 20~40개를 프롬프트에 포함
- **출력 형식 강제**: 자유 텍스트 대신 정해진 JSON 스키마, 허용값 외 라벨 불가
- **복수 라벨 여부 결정 필요**: 한 리뷰에 서비스/유형이 둘 이상일 때 주된 하나만 붙일지, 여러 개 허용할지 지금 수작업 기준을 확인
- **비용/속도**: 월 리뷰 수가 수천 건이면 비용은 크지 않을 가능성이 높지만, 실제 건수를 확인해 추산
- **개인정보**: 리뷰에 이름, 전화번호 등이 섞여 있다면 외부 API 전송 전 마스킹 필요. 사내 정책 확인

## 4. 기술 선택 (비개발자 기준)
- Python 단일 스크립트 + CSV 입출력 (DB, 서버 없음)
- 실행은 명령어 한 줄 또는 간단한 웹 화면(나중에)
- AI 코딩 도구가 만들고 수정하기 쉬운 구조: 파일 3~4개
  - `labels.yaml` (라벨 정의)
  - `examples.csv` (정답 예시)
  - `label_reviews.py` (실행 스크립트)
  - `evaluate.py` (정확도 측정)

## 5. 리스크
| 리스크 | 대응 |
|---|---|
| 라벨 기준이 사람 머릿속에만 있어 모호함 | 1일차에 문서화, 애매한 경계 사례 기록 |
| LLM이 그럴듯하게 틀림 | 정답셋 대비 측정, 저확신 건 검수 |
| 월별 라벨 기준 변화 | `labels.yaml` 버전 관리 |
| 비용·개인정보 | 건수 추산, 마스킹 |

## 6. 구현 첫날 계획

**목표: 오늘 안에 "리뷰 50건을 돌려서 사람 라벨과 비교한 숫자"를 얻는다.** 완성도가 아니라 가능성 확인이 목적입니다.

1. **(30분) 정답 데이터 모으기**: 이미 라벨링한 과거 리뷰 중 100~200건을 엑셀에서 CSV로 내보냅니다. 서비스·유형이 골고루 섞이게 하고, 이 중 50건은 "시험용"으로 따로 두어 예시에는 쓰지 않습니다.
2. **(45분) 라벨 체계 문서화**: 지금 쓰는 서비스/유형/세부 유형 목록을 `labels.yaml`에 적고 각각 한 줄 정의를 붙입니다. 헷갈리는 경계(예: 결제 오류 vs 환불 요청)를 메모합니다.
3. **(30분) 환경 준비**: Python 설치, AI 코딩 도구에 위 구조를 설명하고 API 키 설정. 개인정보 정책도 이때 확인합니다.
4. **(90분) 최소 스크립트**: AI 코딩 도구에 "CSV를 읽어 리뷰마다 LLM으로 3개 라벨을 JSON으로 받아 CSV로 저장하는 스크립트"를 요청합니다. 처음엔 10건으로 테스트하고, 결과를 눈으로 확인합니다.
5. **(45분) 첫 측정**: 시험용 50건을 돌려 사람 라벨과 일치율을 축별(서비스/유형/세부 유형)로 계산합니다. 틀린 건을 훑어 원인을 분류합니다(정의 모호, 예시 부족, 정말 애매한 리뷰).

**첫날 종료 시 판단 기준**
- 서비스/유형이 80% 안팎이면 → 프롬프트와 예시 보강으로 진행
- 세부 유형만 낮으면 → 세부 유형 정의 정리, 또는 세부 유형만 검수 대상으로 설정
- 전반적으로 60% 미만이면 → 라벨 정의 자체가 모호한지부터 점검

# 앱 리뷰 자동 라벨링: 초기 설계안

## 먼저 짚을 점
"키워드 매핑으로 첫 도구를 만든다"는 방법은 말씀하신 제약, 즉 키워드 매칭으로는 안 되고 맥락 판단이 필요하다는 점과 충돌합니다. 그래서 키워드 매핑은 **본 도구가 아니라 비교 기준(baseline)** 으로 쓰고, 본 도구는 LLM 분류를 기본으로 설계하겠습니다.

## 초기 설계

**흐름**
1. **입력**: 리뷰를 CSV나 스프레드시트로 내보냅니다. 컬럼은 ID, 날짜, 별점, 본문입니다.
2. **분류**: 스크립트가 리뷰를 LLM에 보냅니다. 프롬프트에는 라벨 정의서(서비스, 유형, 세부유형의 허용 값과 한 줄 설명)와 과거에 직접 붙인 예시 20~30개를 넣습니다. 출력은 허용 값만 고르게 한 JSON입니다. 라벨 3개, 확신도, 한 줄 근거를 받습니다.
3. **검수 분기**: 확신도가 낮거나 "해당 없음/애매"인 건만 사람이 봅니다. 나머지는 자동 확정합니다.
4. **교정 환류**: 사람이 고친 건을 예시 풀에 추가해 다음 달 정확도를 높입니다.
5. **집계**: 확정 라벨로 월간 차트용 표를 만듭니다.

**원칙**
- 코드를 최소화하고 파일 입출력 중심의 로컬 스크립트로 시작합니다.
- 라벨 목록은 코드가 아니라 별도 파일(정의서)로 두어, 직접 고칠 수 있게 합니다.
- 처음부터 자동 확정은 하지 않습니다. 정확도가 검증된 뒤에 켭니다.

## 구현 첫날 할 일 (코딩보다 데이터 준비가 먼저)
1. **정답 세트 만들기**: 이미 라벨을 붙인 과거 리뷰에서 약 200건을 뽑습니다. 드문 라벨도 포함되도록 라벨별로 골고루 뽑습니다.
2. **라벨 정의서 초안**: 서비스/유형/세부유형 목록과 각 라벨의 판단 기준을 한 줄씩 적습니다. 헷갈리는 쌍에는 "이 경우는 A, 저 경우는 B"를 적어둡니다.
3. **보안 확인**: 리뷰 데이터를 외부 AI API로 보내도 되는지 확인합니다. 리뷰에 개인정보가 섞여 있는지도 봅니다.
4. **키워드 baseline 만들기**: 약 1시간이면 됩니다. 이후 비교 기준이 됩니다.
5. 여기까지 끝나면 아래 실험을 돌립니다. 이 시점에는 본 도구를 만들지 않습니다.

## 틀리면 설계가 크게 바뀌는 가정
> **"라벨 정의서와 소수의 예시만으로 LLM이 내가 붙이는 라벨을 충분히 재현한다."**

틀리면 구조 자체가 달라집니다. 예시를 더 모아 별도 분류 모델을 학습시키거나, 라벨 체계를 개편하거나, 사람 검수 중심 도구로 바꿔야 합니다.

## 가장 작은 실험

- **입력**: 정답 세트 200건 중 25건은 프롬프트 예시로 쓰고, 나머지 175건은 라벨을 숨긴 채 분류시킵니다.
- **비교 대상**
  1. 키워드 매핑 baseline
  2. LLM 결과
  3. (상한선) 본인이 일주일 뒤 같은 50건을 다시 라벨링했을 때의 일치율. 본인조차 일관되지 않으면 어떤 도구도 그 이상은 나오지 않습니다.
- **실패 기준** (아래 숫자는 제안이며, 실험 전에 확정해 주세요)
  - 유형·세부유형 일치율이 80% 미만이거나, 키워드 baseline보다 10%p 이상 높지 않음
  - 확신도 높은 건만 자동 확정했을 때 정확도가 95% 미만이거나, 자동 확정 비율이 전체의 50% 미만이라 검수 시간이 크게 줄지 않음
  - 오답이 특정 라벨 쌍의 혼동에 몰려 있지 않고 무작위로 흩어져 있음. 이 경우 프롬프트 수정으로 고치기 어렵습니다.
  - 본인의 재라벨 일치율 자체가 낮음. 이 경우 문제는 도구가 아니라 라벨 기준입니다.

## 실패했을 때

**제가 직접 시도할 수 있는 조치**
- 혼동 행렬로 오답 패턴을 찾아 프롬프트의 정의와 경계 사례 설명을 수정
- 오답 사례를 예시에 추가하고 예시 수를 늘려 재측정
- 한 번에 3개 라벨을 붙이는 대신 서비스, 유형, 세부유형 순서의 단계 분류로 변경
- 더 큰 모델이나 다른 모델로 교체해 비교
- 확신도 기준값 조정으로 자동 확정/검수 경계를 재설정
- 입력에 별점이나 앱 버전 같은 메타데이터를 추가

**사용자 결정이 필요한 조건**
- **라벨 체계 변경**: 혼동이 심한 라벨의 통합, 분할, 삭제. 라벨의 의미는 운영 목적에 달려 있어서 제가 정할 수 없습니다.
- **본인 재라벨 일치율이 낮은 경우**: 어느 쪽 판단이 맞는지 기준을 정해야 합니다.
- **허용 정확도 수준**: 리포트에 몇 %의 오분류를 감수할지, 검수를 얼마나 남길지
- **외부 API 사용 가능 여부와 비용 한도**: 보안상 불가하면 로컬 모델이나 다른 구조로 가야 합니다.
- **프롬프트 개선으로도 기준에 못 미칠 때**: 추가 라벨링 데이터(수백~수천 건) 확보에 시간을 쓸지, "사람 검수 보조 도구"로 목표를 낮출지 선택해야 합니다.

## 정리
첫날의 목표는 도구를 만드는 것이 아니라 정답 세트와 라벨 정의서를 확보하고 실험을 한 번 돌리는 것입니다. 실험이 통과하면 도구를 만들고, 실패하면 위 구분에 따라 제가 고칠 부분과 결정하실 부분으로 나누어 진행하겠습니다.
