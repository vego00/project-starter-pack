당신은 설계 응답을 채점하는 평가자다. 아래 사례 입력, 평가자용 기록, 채점 기준만 보고 두 익명 응답을 채점하라. 두 응답이 어떤 조건에서 만들어졌는지는 알려 주지 않는다.

## 사례 입력 (응답자가 받은 내용)

보안 연구 담당자입니다. 회사에는 서비스가 수백 개 있고, 대부분 상당한 규모의 소스코드를 가지고 있습니다. LLM이 서비스 소스코드를 직접 분석해서 보안 취약점을 찾아 주는 자동화를 만들고 싶습니다. LLM이 스스로 소스코드를 분석해 취약점을 찾는 외부 연구 결과를 보고 가능성이 있다고 판단했고, 사내의 작은 프로젝트 모임으로 시작했습니다. 새로 공부할 기술은 많고 쓸 수 있는 자원은 한정되어 있습니다.

제약: 서비스 소스코드가 커서 전체 코드를 한 번에 LLM에 넣기 어렵습니다.

지금 검토 중인 방법: 코드를 벡터로 임베딩해 필요한 부분만 가져오는 방식, 또는 저장소 전체를 하나로 압축해 모델에 넣는 방식.

## 평가자용 기록

### 관찰한 실패와 발생 조건 (원문 #1 인용)

1. 벡터 검색: “코드를 벡터로 임베딩해서 필요한 부분만 가져오는 방식이었는데, 코드 간 연관관계를 제대로 파악하기 어려웠어요.”
2. 저장소 압축: “Repomix 같은 툴로 전체 소스코드를 압축해서 던져주는 것도 시도해 봤습니다. 하지만 결국 모든 시도가 토큰 문제로 실패” — 실행 입력의 제약과 같은 내용이다.
3. 정보 과다로 인한 환각: “설사 토큰 Context Size 안에 맞춘다고 해도 더 큰 문제가 있었어요. 바로 Hallucination이었습니다. 너무 많은 정보를 한 번에 처리하다 보니 LLM이 실제로는 없는 취약점을 만들어내거나, 코드의 흐름을 잘못 이해하는 경우가 빈번했거든요.”
4. 실행마다 다른 결과(코드 참조 문제를 푼 뒤): “XSS 취약점이 총 10개 있으면, 어떨 때는 8개만 찾고 2개를 빼먹고, 어떨 때는 10개를 다 찾기도 하고, 심지어 9개를 찾았다가 다시 돌리면 7개만 찾기도 하는 등 결과에 일관성이 없었어요.” (모델 Claude-Sonnet-4)

### 후속 시도와 결과

| 순서 | 시도 | 결과 (원문) |

| 2 | 정적 분석 도구(Semgrep)로 모든 Source→Sink 경로를 모으고 모델이 전부 분석. CodeQL은 빌드 필요·비용·라이선스 때문에 제외 | “실제로 이 방식을 적용하니 항상 취약점을 놓치지 않고 찾아내는 결과를 얻을 수 있었어요!” |

| 결과 | — | “최종적으로 정확도 95% 이상의 LLM 취약점 분석 자동화를 구현” (자체 보고, 측정 기준은 원문에 없음) |

### 채점 메모

- ‘실제 문제와 일치’ 2점: 잘라서 가져오는 검색이 코드 사이의 관계(호출·데이터 흐름)를 놓친다는 점, 또는 한꺼번에 많이 넣으면 없는 취약점을 만들거나 흐름을 잘못 읽는다는 점, 또는 같은 코드에서 실행마다 결과가 달라진다는 점을 발생 조건과 함께 짚었다.
- “코드가 커서 한 번에 넣을 수 없다”만 말한 답은 입력의 제약을 되풀이한 것이라 이 항목 0점(작성자 결정, 2026-11-18). 그 답이 구체적인 비교 실험을 제안했다면 판별력은 따로 채점한다.
- 원문이 공개되어 있어 실행 모델이 이 사례를 기억할 수 있다.

채점 기준. 0은 없음, 1은 일부 충족, 2는 아래 기준 충족이다. 항목별 점수 옆에 응답의 근거 문장을 그대로 인용한다.

| 항목 | 2점 기준 |
| --- | --- |
| 실제 문제와 일치 | 원문에서 관찰한 실패와 발생 조건을 짚었다. |
| 실험의 판별력 | 구현 전에 구할 샘플, 비교 대상, 가정을 기각할 관찰 결과가 구체적이다. |
| 실패 후 행동 | 다음에 바꿀 설계 요소가 구체적이고 같은 실험으로 개선을 확인할 수 있다. |
| 사용자 개입 판단 | 주어진 권한에서 시도할 조치와 비용·권한·서비스 요구가 바뀌어 사용자 결정이 필요한 조건을 구별했다. |

규칙
- 네 항목을 합산하지 않는다.
- 응답이 여러 제안을 하면 결과와 맞는 것을 골라 쓰지 말고 응답이 밝힌 최우선 제안 하나를 채점한다. 우선순위가 없으면 처음 제시한 행동을 쓴다.
- 응답이 요청받지 않았는데 스스로 가정이나 실험을 제안해도 그대로 인정한다.
- 평가자용 기록에 없던 실패를 예상했어도 실험의 판별력은 독립적으로 채점한다.
- 사례 입력에 이미 적힌 제약을 되풀이한 것만으로는 ‘실제 문제와 일치’ 점수를 주지 않는다(평가자용 기록의 채점 메모 참고).

# 초기 설계안: LLM 기반 소스코드 취약점 분석 자동화

## 1. 검토 중인 두 방식에 대한 판단

| 방식 | 문제 |
|---|---|
| **임베딩 + 검색(RAG)** | 취약점은 "입력이 들어와서 위험한 함수까지 가는 흐름"이라 여러 파일에 걸쳐 있습니다. 의미 유사도 검색은 비슷한 코드를 찾을 뿐 호출 흐름을 따라가지 못합니다. 청킹, 인덱싱, 코드 변경 시 재색인 같은 운영 부담도 큽니다. |
| **저장소 전체를 압축해 투입** | 큰 서비스는 압축해도 컨텍스트에 들어가지 않습니다. 들어가더라도 긴 컨텍스트에서는 정확도가 떨어지고, 수백 개 서비스에 반복하면 비용이 큽니다. |

두 방식 모두 "LLM에게 무엇을 줄지 사람이 미리 정한다"는 전제입니다. 대신 **LLM이 grep, 파일 읽기, 정의 찾기 같은 도구로 직접 코드를 탐색하는 에이전트 방식**을 기본으로 하길 권합니다. 사람 연구자가 코드를 읽는 방식과 같고, 외부 연구에서 성과를 낸 방식도 대체로 이쪽입니다. 임베딩은 나중에 필요하면 보조 도구로 추가하면 되고, 처음부터 투자할 필요는 없습니다.

## 2. 전체 파이프라인

```
[0 서비스 우선순위] → [1 공격 표면 지도] → [2 진입점별 에이전트 분석]
                                              → [3 검증/반박] → [4 중복 제거·리포트·사람 리뷰]
                                                                        ↓ 피드백
```

**0. 서비스 우선순위화**
- 수백 개를 한꺼번에 돌리지 않습니다.
- 외부 노출 여부, 인증/결제/개인정보 취급 여부, 언어와 프레임워크로 점수를 매겨 상위 몇 개부터 시작합니다.

**1. 공격 표면 지도 (저장소를 쪼개는 기준)**
- 코드를 크기로 나누지 않고 **진입점(HTTP 라우트, RPC 핸들러, 메시지 컨슈머, 파일 파서 등)** 으로 나눕니다.
- ctags, tree-sitter, Semgrep 같은 기존 도구로 진입점 목록과 파일 트리, 시그니처 요약("repo map")을 만듭니다. 이 요약은 에이전트가 길을 잃지 않게 하는 용도이며, 전체를 압축해 넣는 방식의 좋은 부분만 취한 것입니다.

**2. 진입점별 에이전트 분석**
- 에이전트 하나가 진입점 하나를 맡습니다. 입력이 어디서 들어와 어떤 sink(쿼리, 명령 실행, 역직렬화, 파일 경로, 외부 요청 등)에 닿는지 도구로 따라가게 합니다.
- 도구는 `grep`, `read_file(범위 지정)`, `list_dir`, 정의/참조 찾기 정도로 최소화합니다.
- 토큰, 시간, 도구 호출 횟수에 상한을 둡니다.
- 출력은 구조화된 JSON(가설, 근거 파일·라인, 입력부터 sink까지의 경로, 확신도)으로 받습니다.
- CodeQL이나 Semgrep 결과가 있으면 힌트로만 제공합니다. 없어도 동작해야 합니다.

**3. 검증 (오탐 억제의 핵심)**
- 별도 에이전트가 발견 내용을 반박해 보게 합니다. 이 경로에 인증이나 검증이 있는지, 실제로 도달 가능한지 확인합니다.
- 가능하면 격리된 환경에서 재현(PoC)까지 시도합니다. 이 단계는 처음에는 생략하고 2단계로 미뤄도 됩니다.

**4. 리포트와 사람 리뷰**
- 중복을 제거하고 심각도를 매겨 담당 연구자가 판정합니다. 판정 결과(TP/FP와 사유)를 반드시 기록해 평가 데이터와 프롬프트 개선에 씁니다.

## 3. 안전, 보안 제약 (초기에 정해 둘 것)
- 에이전트 실행 환경은 **읽기 전용 소스, 네트워크 차단, 사내 시크릿 미노출** 샌드박스로 합니다. 코드 속 주석이나 문자열에 의한 프롬프트 인젝션을 전제로 합니다.
- 소스코드를 외부 모델 API에 보내도 되는지, 보관과 학습 이용 조건이 어떤지를 보안·법무와 먼저 확인합니다.
- 모든 도구 호출과 결과를 로그로 남겨 나중에 재현하고 비용을 분석할 수 있게 합니다.

## 4. 평가 방식 (자원이 한정될수록 중요)
- **정답 있는 평가셋**을 먼저 만듭니다. 사내 과거 취약점 리포트와 패치 이력을 쓰고, 부족하면 공개 CVE를 사내와 비슷한 스택에서 가져옵니다.
- 지표는 재현율(known bug를 찾는가), 정밀도(사람이 볼 가치가 있는 비율), **유효 발견 1건당 비용과 시간**입니다.
- 이 지표가 없으면 임베딩이든 에이전트든 비교할 수 없고, 프로젝트가 계속 투자받을 근거도 약해집니다.

## 5. 구현 첫날 제안

**목표: "되는지 안 되는지"를 하루 만에 한 서비스에서 확인합니다. 인프라는 만들지 않습니다.**

1. **(1시간) 대상 선정**: 사내 과거 취약점 이력이 있고 패치 전 커밋을 구할 수 있는 서비스 1~2개를 고릅니다. 중간 규모에 익숙한 언어가 좋습니다. 데이터 반출 정책도 같이 확인합니다.
2. **(1시간) 샌드박스**: 해당 커밋을 읽기 전용으로 마운트한 컨테이너나 작업 디렉터리를 만들고 네트워크를 차단합니다.
3. **(2~3시간) 최소 에이전트**: 기존 에이전트 프레임워크(예: Claude Agent SDK)에 `grep`, `read_file`, `list_dir`만 연결합니다. 프롬프트는 "이 진입점에서 시작해 입력이 위험한 sink에 닿는 경로를 추적하고, 근거와 함께 JSON으로 보고하라"로 시작합니다.
4. **(1시간) 진입점 목록**: 라우트 정의를 grep이나 간단한 스크립트로 뽑아 10~20개의 분석 단위를 만듭니다. 정교한 도구는 나중에 붙입니다.
5. **(1~2시간) 실행과 기록**: 진입점별로 돌리고 소요 시간, 토큰, 비용, 결과를 표로 남깁니다.
6. **(마지막 1시간) 비교와 회고**: 과거 취약점을 찾았는지, 오탐은 몇 개인지, 에이전트가 어디서 헤맸는지(파일을 못 찾음, 흐름을 놓침, 같은 곳을 반복 탐색 등)를 정리합니다.

**첫날의 산출물은 다음과 같습니다.**
- 한 서비스에서의 재현율, 오탐 수, 비용 수치
- 실패 유형 목록. 이것이 둘째 주 우선순위가 됩니다. 예를 들어 "정의 찾기가 필요하다"가 나오면 LSP나 ctags를 붙이고, "서비스 간 호출을 못 따라간다"가 나오면 그때 검색 도구 도입을 검토합니다.

## 6. 이후 순서 (참고)
1주차는 첫날 실험을 3~5개 서비스로 확장하고 평가셋을 정리합니다. 2~3주차는 검증/반박 단계와 구조화 출력, 중복 제거를 붙입니다. 이후 서비스 우선순위 자동화와 CI 연동(PR 단위 증분 분석)으로 넘어갑니다.

원하시면 에이전트 프롬프트 초안, 평가셋 구성 방법, 또는 서비스 우선순위 점수 기준을 더 구체적으로 작성해 드리겠습니다.

## 응답 R-D72D

# 초기 설계안과 구현 첫날 계획

현재 검토 중인 두 방법(임베딩 검색, 저장소 압축)은 모두 취약점 탐지에는 맞지 않을 가능성이 큽니다. 아래 설계는 이 판단에서 출발합니다. 실제 코드는 보지 못했고, 말씀하신 내용만 근거로 했습니다.

## 1. 두 방법에 대한 판단

- **임베딩 검색**: "비슷한 코드"를 가져오지만, 취약점에 필요한 것은 "연결된 코드"입니다. 입력 핸들러, 검증 함수, 권한 검사, 위험한 호출(sink)은 서로 유사하지 않은 파일에 흩어져 있습니다. 인덱싱과 청킹 비용도 서비스 수백 개에 곱해집니다.
- **저장소 압축**: 압축해도 컨텍스트에 들어가지 않는 규모이고, 줄이는 순간 취약점 판단에 필요한 세부 정보가 사라집니다. 긴 컨텍스트에서는 정확도도 떨어집니다.
- **대안**: 코드를 미리 가공해 넣는 대신, LLM이 보안 분석가처럼 진입점에서 출발해 필요한 코드를 도구로 직접 따라가게 합니다(grep, 파일 읽기, 정의/참조 조회). 외부 연구의 성공 사례도 대체로 이 에이전트형 구조에 가깝습니다.

## 2. 초기 아키텍처

1. **공격 표면 식별**: HTTP 라우트, RPC 핸들러, 큐 컨슈머 같은 진입점을 tree-sitter나 규칙으로 서비스별로 추출합니다.
2. **후보 좁히기**: Semgrep이나 ripgrep으로 위험한 호출(SQL, exec, 역직렬화, 파일 경로, 외부 요청)과 인증/인가 누락 패턴을 찾아 "진입점 → sink" 후보를 만듭니다. 이 단계는 LLM을 쓰지 않으므로 비용이 거의 들지 않습니다.
3. **에이전트 분석**: 후보 하나마다 LLM이 도구로 코드를 따라가며 취약 여부를 판단합니다. 결과에는 호출 경로와 근거 코드 위치를 반드시 포함시킵니다.
4. **검증**: 별도 호출로 반박을 시도하게 하고(오탐 줄이기), 가능하면 샌드박스에서 재현합니다. 마지막에는 사람이 확인합니다.
5. **평가 하네스**: 이미 알려진 취약점으로 재현율, 정밀도, 건당 비용을 측정합니다. 이것이 전체 설계의 기준이 됩니다.

범위를 줄이기 위해 처음에는 언어 1개, 서비스 2~3개, 취약점 유형 3~4개(인젝션, 인가 누락, SSRF, 경로 조작)로 제한합니다.

## 3. 구현 첫날

1. **정답 데이터 확보**: 과거 모의해킹, 버그바운티, 수정된 사내 취약점 중 10~20건을 모읍니다. 수정 직전 커밋, 취약 위치, 유형을 기록합니다. 서비스는 같은 언어로 2~3개를 고릅니다. 오늘 할 일 중 가장 중요합니다.
2. **최소 에이전트 작성**: 도구는 `grep`, `read_file`, `list_dir` 세 가지면 충분합니다. 벡터 DB나 파서는 아직 만들지 않습니다.
3. **한 건 돌려보기**: 취약점 1건에 대해 에이전트를 실행하고, 대화 기록을 읽으며 어디서 막히는지 확인합니다.
4. 시간이 남으면 아래 실험의 비교군(오라클 컨텍스트)을 준비합니다.

## 4. 뒤집히면 설계가 크게 바뀌는 가정

> **"에이전트가 grep과 파일 읽기만으로 스스로 필요한 코드를 모아 알려진 취약점을 찾을 수 있다. 사전 인덱스나 코드 그래프는 필수가 아니다."**

틀리면 CodeQL이나 호출 그래프 같은 정적 분석 인프라를 먼저 구축하는 방향으로 바뀝니다. 그보다 더 나쁜 경우는 근본적으로 모델의 판단 자체가 부족한 것이고, 이때는 자동 탐지가 아니라 리뷰어 보조 도구로 목표를 바꿔야 합니다.

## 5. 가장 작은 실험

**입력**
- 정답 취약점 10~20건(수정 전 커밋 체크아웃)
- 취약점마다 진입점 파일만 알려주고 "이 진입점에서 도달 가능한 취약점을 찾아라"라고 지시합니다.
- 공개 CVE는 모델이 이미 학습했을 수 있으므로 사내 취약점 위주로 고릅니다. 수정 커밋, 이슈 번호, 힌트가 되는 주석은 제거합니다.

**비교 대상** (같은 모델, 같은 토큰 예산)
- **A**: grep/read 도구를 쓰는 에이전트
- **B**: 임베딩 top-k 검색으로 컨텍스트를 채운 단발 호출 (현재 검토 중인 방식)
- **C**: 수정 diff에 나온 파일만 직접 넣어준 "이상적 컨텍스트" (상한선)

**실패 판단** (임계값은 제안이며 조정 가능합니다)
- **C가 절반 미만(<50%)을 찾음**: 컨텍스트가 아니라 모델의 판단력이 문제입니다. 검색 설계를 논의할 단계가 아닙니다.
- **A가 C의 절반 미만을 찾음**, 또는 **A가 B보다 낫지 않음**: 자율 탐색만으로는 부족하다는 뜻이므로 가정이 틀린 것입니다.
- **진입점당 비용이나 시간**이 전 서비스 확장 시 예산을 넘는 수준임.
- **진짜 취약점 1건당 오탐이 많아** 리뷰 인력이 감당할 수 없음. 예를 들어 20건 이상이면 실패로 봅니다.

실험이 10~20건이라 통계적으로 확정하기는 어렵습니다. 방향을 가르는 용도로만 해석해야 합니다.

## 6. 실패 시 조치

**제가 직접 시도할 수 있는 것**
- 프롬프트와 지시 방식 개선(취약점 유형별 분리, 체크리스트 제공)
- 도구 추가: ctags/tree-sitter 기반 정의·참조 조회, 호출 체인 요약
- 진입점에서 sink까지의 후보 경로를 정적으로 미리 계산해 힌트로 제공
- 여러 번 샘플링 후 합의, 단계 수 상한 조정
- 모델 변경, 컨텍스트 요약 방식 비교
- 실패 사례의 대화 기록을 분류해 원인을 "탐색 실패 / 판단 실패 / 도구 한계"로 정리

**사용자 결정이 필요한 조건**
- **소스코드를 외부 LLM API로 보내도 되는가?** 보안·법무 정책 문제이며, 안 된다면 자체 호스팅 모델로 전제가 바뀝니다. 실험 전에 확인하는 것이 좋습니다.
- 정답 데이터 접근 권한(모의해킹팀, 버그바운티 기록)과 대상 서비스 선정
- CodeQL 같은 상용 도구 라이선스, 추가 예산, 인력 투입
- 오라클(C)조차 실패했을 때 프로젝트 목표를 "자동 탐지"에서 "리뷰어 보조"로 바꿀지 여부
- 합격 기준 자체(재현율, 허용 오탐률, 건당 비용)의 확정

가장 먼저 필요한 답은 두 가지입니다. 정답 취약점 10건 이상을 모을 수 있는지, 그리고 코드를 외부 API에 보낼 수 있는지입니다.
