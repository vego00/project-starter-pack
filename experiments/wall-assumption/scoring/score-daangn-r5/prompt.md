서비스 운영팀의 운영 담당자입니다. 앱 리뷰 데이터를 관리하면서 매월 리포트로 구성원에게 공유합니다. 리포트에 넣을 시각화 자료를 만들려고, 매일 리뷰마다 ‘관련 서비스’, ‘유형’, ‘세부 유형’ 라벨을 손으로 붙이고 있습니다. 이 반복 작업에 매월 6시간 이상이 들어 다른 기획 업무를 같이 하기 어렵습니다.

## 응답 R-9406

# 초기 설계안: 앱 리뷰 자동 라벨링

## 0. 먼저 짚을 점
말씀하신 "키워드 매핑으로 첫 도구를 만든다"는 방법은 제약(문장이 정돈되지 않아 맥락 판단 필요)과 충돌합니다. 그래서 키워드 매핑은 **주 방식이 아니라 비교 기준선(baseline)** 으로 쓰고, 주 방식은 **LLM 분류 + 사람 검수**로 제안합니다. 키워드 매핑은 만드는 데 하루도 안 걸리니, 기준선으로 두면 LLM이 실제로 얼마나 나은지 숫자로 확인할 수 있습니다.

## 1. 초기 설계

**흐름**
1. 리뷰 파일(CSV/엑셀) 입력
2. 라벨 체계(서비스·유형·세부 유형 목록과 각각의 정의, 경계 사례 예시)를 한 문서로 고정
3. LLM이 리뷰마다 3개 라벨 + 확신도 + 한 줄 근거를 출력 (정해진 목록 안에서만 선택하도록 제한)
4. 확신도 낮음 또는 "해당 없음/모호" 건만 사람이 검수
5. 검수 결과는 예시 모음에 누적 → 다음 달 프롬프트의 예시로 재사용 (정확도가 점점 개선)
6. 최종 라벨 표 → 월간 리포트용 집계/차트

**설계 원칙**
- 라벨 목록은 닫힌 집합. 목록에 없으면 "기타"로 보내고 사람이 확인
- 서비스 → 유형 → 세부 유형의 계층 규칙을 코드로 검증 (불가능한 조합은 자동 재검수 대상)
- 처음엔 **사람이 최종 확인하는 보조 도구**로 시작. 완전 자동화는 정확도가 확인된 뒤 결정
- 개인정보(이름, 연락처 등)가 리뷰에 섞여 있으면 외부 API로 보내기 전 정책 확인 필요

## 2. 구현 첫날 할 일

코드보다 **정답 데이터와 라벨 정의**가 먼저입니다.

1. 이미 손으로 붙인 과거 리뷰 중 최근 1~2개월분을 모은다 (이것이 정답지)
2. 라벨 목록과 정의를 한 장 문서로 정리한다 (애매한 경계 사례 포함)
3. 정답지를 **평가용 200~300건**과 **예시용**으로 분리한다 (평가용은 프롬프트 작성 시 보지 않는다)
4. 키워드 매핑 기준선을 AI 코딩 도구로 만들어 평가용에 돌리고 정확도를 기록한다
5. 라벨별 건수 분포를 확인한다 (희귀 라벨이 있는지)

여기까지가 하루의 목표이며, 결과물은 "기준선 정확도 수치"와 "라벨 정의 문서"입니다.

## 3. 뒤집히면 설계가 크게 바뀌는 가정 하나

**가정: "기존 수작업 라벨이 일관되어 정답지로 쓸 수 있다."**

라벨 기준이 사람·시기마다 흔들렸거나 경계가 모호하면, LLM이든 키워드든 무엇을 만들어도 "정확도"를 신뢰할 수 없고, 설계의 중심이 도구에서 **라벨 체계 재정의**로 옮겨갑니다. (세부 유형이 너무 많거나 겹치는 경우가 전형적입니다.)

## 4. 가장 작은 실험

- **입력**: 과거에 이미 라벨링한 리뷰 중 무작위 50건. 같은 50건을 **본인이 라벨 정의 문서만 보고 다시** 라벨링 (최소 며칠 간격을 두고, 이전 라벨은 가린 채)
- **비교 대상**: 과거 라벨 vs 이번 재라벨 (같은 사람의 일관성). 가능하면 동료 1명이 같은 50건을 라벨링한 결과도 비교
- **실패로 판단할 관찰 결과**: 라벨 3개 모두 일치하는 비율이 약 80% 미만이거나, 불일치가 특정 유형 쌍(예: A와 B 사이)에 몰려 있는 경우. 사람끼리도 이 정도면 자동화 정확도의 상한이 거기에 묶입니다. (80%는 임시 기준이며, 리포트의 용도에 따라 조정)

## 5. 실패 시 조치 구분

**제가 직접 시도할 수 있는 것**
- 불일치 건을 쌍별로 집계하고, 혼동되는 라벨 쌍을 표로 정리
- 정의 문서에 경계 규칙과 예시를 보강한 수정안 작성
- 세부 유형 병합/분리 안을 2~3개 만들어 제시
- 수정안으로 같은 실험을 재실행해 일치율 변화를 측정

**사용자 결정이 필요한 것**
- 라벨 체계를 실제로 바꿀지 (과거 리포트와 시계열 비교가 끊길 수 있음)
- 어떤 세부 유형을 병합하거나 폐기할지 (리포트 독자의 용도에 대한 판단)
- 허용 가능한 정확도 수준과 사람 검수 범위 (오분류 비용에 대한 판단)
- 리뷰 데이터를 외부 LLM API로 보내도 되는지 (회사 보안·개인정보 정책)
- 동료에게 라벨링 협조를 요청하는 일

원하시면 다음 단계로 라벨 정의 문서 템플릿과 평가용 데이터 분리 방법을 만들어 드리겠습니다.

## 응답 R-CD3C

# 초기 설계안: 앱 리뷰 자동 라벨링 도구

## 1. 핵심 판단: 키워드 매핑 방식은 첫 도구로 부적합

말씀하신 제약(문장이 정돈되지 않았고 맥락 판단이 필요함)과 키워드 매핑은 서로 맞지 않습니다.

- "배송 빠른데 앱이 자꾸 꺼져요"처럼 한 리뷰에 여러 서비스/유형이 섞이면 키워드는 오분류합니다.
- "좋아요 진짜 ㅋㅋ 망했네요" 같은 반어, 오탈자, 줄임말은 키워드 목록이 계속 늘어나 유지보수 부담이 됩니다.
- 결과적으로 매월 규칙을 손보는 일이 새 반복 업무가 됩니다.

**대안: LLM 분류를 기본 엔진으로 쓰고, 키워드는 보조(전처리/검증)로만 사용합니다.** 사람이 맥락을 읽고 판단하는 작업이므로, 맥락을 읽는 LLM이 같은 역할을 대신하는 게 자연스럽습니다. 코딩 경험이 없어도 "프롬프트 + 라벨 정의 + 예시"가 핵심이라 오히려 운영 담당자가 가장 잘 기여할 수 있는 영역입니다.

## 2. 전체 구조

```
[리뷰 파일 CSV/엑셀] → [읽기·정리] → [LLM 분류] → [검증/신뢰도 체크] → [라벨 결과 CSV] → [사람 검수(예외만)] → [리포트용 시각화]
```

| 구성요소 | 역할 | 비고 |
|---|---|---|
| 입력 | 리뷰 파일(CSV/엑셀) 읽기 | 현재 쓰는 시트 형식 그대로 |
| 라벨 정의서 | 서비스/유형/세부 유형 목록과 각 정의, 경계 사례 | 설정 파일(YAML/CSV), 코드와 분리 |
| 분류기 | 리뷰 1건 → 세 라벨 + 신뢰도 + 한 줄 근거 | LLM 호출, 정해진 JSON 형식으로 출력 |
| 검증 | 라벨이 정의서 목록에 없으면 거부, 신뢰도 낮으면 표시 | 오분류·환각 방지 |
| 출력 | 원본 + 라벨 + 신뢰도 + 검수 필요 여부 | 기존 시각화 작업에 바로 사용 |
| 검수 | "검수 필요"로 표시된 건만 사람이 확인 | 전수 검토 → 예외 검토 |

## 3. 설계 원칙

1. **라벨 정의서가 제품의 핵심입니다.** 코드가 아니라 정의서의 품질이 정확도를 좌우합니다. 지금까지 손으로 붙인 라벨이 가장 큰 자산입니다.
2. **닫힌 목록으로 분류.** LLM이 라벨을 만들어내지 못하게 허용 목록 중에서만 선택시킵니다.
3. **불확실하면 표시.** 억지로 분류하지 않고 "검수 필요"로 넘깁니다.
4. **정답 세트로 측정.** 이미 손으로 붙인 과거 리뷰 200~300건을 정답 세트로 삼아 정확도를 숫자로 확인합니다.
5. **작게 시작.** 처음엔 화면 UI 없이 "파일 넣으면 파일 나오는" 명령줄 도구 하나면 충분합니다.

## 4. 성공 기준(제안)

- 정답 세트 기준 일치율: 서비스 90%+, 유형 85%+, 세부 유형 75%+ (현 수준을 보고 조정)
- 사람 검수 대상이 전체의 20% 이하
- 월 6시간 → 1시간 내외

## 5. 주의할 점

- **개인정보**: 리뷰에 이름, 전화번호 등이 섞여 있을 수 있으니, 외부 LLM API로 보내기 전에 회사 정책과 마스킹 필요 여부를 확인하세요.
- **비용**: 월 리뷰 건수를 알려주시면 대략 추정할 수 있습니다. 보통 건당 매우 저렴하며, 여러 건을 묶어 호출하면 더 줄어듭니다.
- **일관성**: 같은 리뷰는 같은 라벨이 나오도록 설정을 고정하고, 정의서 버전을 기록합니다.

## 6. 구현 첫날 계획

목표: **"오늘 안에 리뷰 20건이 자동으로 라벨링되어 내가 붙인 라벨과 비교되는 것"을 눈으로 확인.**

**1단계 (준비, 사람이 할 일, 약 1시간)**
1. 지금까지 손으로 라벨링한 데이터 중 최근 리뷰 200건 정도를 CSV로 내보내기 (열: 리뷰 원문, 관련 서비스, 유형, 세부 유형)
2. 라벨 목록을 정리: 서비스 몇 개, 유형 몇 개, 세부 유형 몇 개인지, 유형별 세부 유형 구조
3. 헷갈리는 경계 사례 5~10개를 메모 (예: "결제 오류 vs 환불 문의는 어디?")

**2단계 (AI 코딩 도구와 함께, 약 2~3시간)**
4. 작업 폴더를 만들고, AI 코딩 도구에 이 설계안과 위 CSV 샘플을 주고 "리뷰 20건을 읽어 LLM으로 세 라벨을 붙여 결과 CSV로 저장하는 최소 스크립트"를 요청
5. 라벨 정의서를 별도 파일로 두도록 요청 (코드 안에 하드코딩하지 않기)
6. LLM 출력은 JSON 형식, 허용 목록 외 값은 오류로 처리하도록 요청

**3단계 (확인, 약 1시간)**
7. 20건 결과를 내 라벨과 나란히 비교해 틀린 것을 확인
8. 틀린 이유를 분류: 정의서가 모호했나, 예시가 부족했나, 원래 내 라벨이 애매했나
9. 정의서를 고치고 같은 20건을 다시 돌려 개선 확인

**첫날 끝났을 때의 산출물**: 작동하는 스크립트 1개, 라벨 정의서 1개, 20건 비교 결과 1개, 그리고 "어떤 유형에서 틀리는지"에 대한 메모.

**첫날 하지 말 것**: 화면(UI), 자동 스케줄링, 대시보드 연동, 전체 데이터 처리. 정확도가 숫자로 확인된 뒤 2~3주차에 붙여도 늦지 않습니다.

## 7. 이후 로드맵(요약)

- **2일차**: 정답 세트 200건 전체로 정확도 측정, 오답 패턴별 정의서/예시 보강
- **1주차 말**: 신뢰도 기준 설정, "검수 필요" 출력 추가
- **2주차**: 실제 월간 데이터로 병행 운영(자동 + 수동 비교)
- **3~4주차**: 시각화용 집계 출력 정리, 필요하면 키워드 기반 사전 필터(예: 스팸/빈 리뷰 제거) 추가

## 확인하고 싶은 것

1. 월 리뷰 건수와 현재 데이터 형식(엑셀/구글시트/내부 도구 내보내기)
2. 서비스·유형·세부 유형 각각의 개수
3. 사용 가능한 LLM API와 회사의 외부 전송 정책
4. 지금까지 쌓인 라벨 데이터의 양

이 네 가지를 알려주시면 정의서 템플릿과 첫날 스크립트 요청문까지 바로 구체화해 드리겠습니다.
