## 채택 판단

기준(작성자, 2026-11-18): 세 사례 중 두 건 이상에서 ① B의 판별력 점수가 A보다 높고 ② 구현 첫날 행동도 달라야 후속 검증을 제안한다.

- ① 충족: 세 사례 모두 B가 높다(1 → 2).
- ② 미충족: 세 사례 모두 채점자가 첫날 행동을 “실질적으로 같다”고 판정했다. A도 스스로 정답 데이터(과거 취약점, 질문 로그, 과거 라벨)부터 모으자고 했다.
- 판단: **기준 미충족. 후속 검증을 제안하지 않는다.** B 문장은 첫날 하는 일을 바꾸지 않고, 그 데이터로 무엇을 비교하고 언제 가정을 버릴지를 구체적으로 만들었다.

## 한계

- 사례당 한 번 실행했다. 판별력 차이 1점이 반복해도 유지되는지 모른다.
- 원문이 공개되어 있어 실행 모델이 사례를 기억할 수 있다. 토스 A·B 모두 처음부터 “모델이 도구로 코드를 직접 따라가는 방식”을 권했는데, 이는 원문의 해결책과 같다. 기억 때문인지 일반 지식 때문인지 구분할 수 없다.
- 채점은 블라인드였지만 B 응답에는 “가장 작은 실험” 같은 절이 있어 채점자가 B를 짐작할 수 있었다.
- 실험을 제안한 것과 실제로 문제를 해결한 것은 다르다. 이 실험은 제안의 질만 본다.
- 당근 원문은 글머리에 생성형 AI로 제작했다고 밝히고, 정확도 수치가 없다. 사례도 에이전트 설계보다 분류 문제에 가깝다.
- 당근의 “키워드 제약 되풀이는 0점” 규칙은 토스 원칙을 Claude가 적용한 것이다(작성자 확인 전). 이 규칙 때문에 당근 A·B 모두 ‘실제 문제와 일치’가 1점이다.
- 실행 세션은 자신의 작업 폴더 경로(프로젝트 이름 포함)와 계정 이메일을 볼 수 있었다. 사례 내용은 볼 수 없었다(`runs/_leak-check`).
- 모델은 Claude Code CLI 기본 샘플링 설정이다. 온도 등은 지정할 수 없다.

## 반복 실행 (2026-11-18, 사례당 5회)

1회차 뒤 같은 프롬프트, 격리 설정, 모델로 2~5회차를 더 돌렸다(응답 24개, 채점 12개, 실패 0). 회차마다 새 무작위 ID로 블라인드 채점했다. 실행은 사례별 하위 에이전트 3개가 `repeat.py`를 돌렸고, 하위 에이전트는 응답과 채점 내용을 읽지 않았다. 원자료: `repeat-summary-*.json`, `runs/*-r[1-5]`, `scoring/score-*-r[2-5]`.

“같음/다름”은 스크립트가 채점문의 마지막 문장에서 뽑았고, 15개 문장을 모두 직접 읽어 일치를 확인했다.

### 첫날 행동이 달랐던 3번

| 회차 | A의 첫 행동 | B의 첫 행동 |
| --- | --- | --- |
| 토스 r2 | 코드를 외부로 보내도 되는지 정책 확인 | 대상 서비스 선정, 정답 취약점 10~20건 수집 |
| 토스 r4 | 모델로 코드를 보내는 경로의 승인 확인 | 파일럿 서비스 선정, 정답·증거 묶음과 측정 도구 준비 |
| 배민 r4 | 실제 질문으로 평가셋 만들기 | 실험할 채널과 메신저 데이터 접근 권한·사용 승인 확인 |

세 번 모두 차이는 “권한·정책 확인을 먼저 하느냐, 정답 데이터를 먼저 모으느냐”의 순서였다. 그리고 어느 쪽이 권한을 먼저 확인했는지는 일정하지 않다(토스는 A, 배민은 B). B 문장 때문에 첫날 행동이 한 방향으로 바뀐 것으로 보기 어렵다.

### 채택 판단 (반복 반영, 외부 검토 후 고침)

처음 쓴 판단에는 수치 오류 하나와 판정 누락 하나가 있었다(외부 검토, 2026-11-18). `repeat-summary-*.json`으로 다시 세어 둘 다 확인하고 아래로 고쳤다.

항목별 비교(15쌍 = 세 사례 × 5회):

| 항목 | B가 높음 | 동점 | A가 높음 |
| --- | ---: | ---: | ---: |
| 실제 문제와 일치 | 1 | 13 | 1 |
| 실험의 판별력 | 15 | 0 | 0 |
| 실패 후 행동 | 11 | 4 | 0 |
| 사용자 개입 판단 | 15 | 0 | 0 |

- 고친 것 1: 처음에 “실패 후 행동을 15회 모두 높였다”고 썼는데 틀렸다. B가 높은 것은 11회이고 4회는 동점(A도 2점)이다.
- 고친 것 2: 지시서 기준(세 사례 중 두 곳 이상에서 ① B 판별력 우위 ② 첫날 행동 다름)을 회차마다 적용하면, 충족한 사례 수는 1~5회차에 0, 1, 0, 2, 0곳이다. **4회차는 기준을 통과한다**(토스, 배민). 처음 판단은 여기에 “사례마다 5회 중 과반”이라는 지시서에 없는 기준을 따로 적용했다.
- **정확한 결론: 사전에 정한 1회차는 기준 미충족이다. 탐색적으로 반복한 결과, 같은 기준을 충족한 회차는 5회 중 1회다.** 후속 검증을 제안하지 않는다는 판단은 유지한다.
- 프로젝트 질문(실제로 부딪힐 문제를 더 잘 짚는가)에 직접 답하는 수치는 ‘실제 문제와 일치’ 13회 동점이다. B 지시는 검증 계획을 구체적으로 쓰게 했지만, 실제 문제를 더 잘 짚는 효과는 세 사례에서 확인되지 않았다.

### 해석의 한계 (외부 검토)

- ‘첫날 행동’을 ‘첫 번째 행동’으로 좁혀 채점했다. 두 응답이 오전에 같은 자료를 모아도, A는 현행 정답률만 재고 B는 같은 자료로 두 방식을 비교해 설계 유지 여부까지 정할 수 있다. 그날 끝에 알게 되는 것은 다를 수 있다. 반대로 배민 r4의 ‘다름’은 권한 확인과 표본 수집 중 무엇을 먼저 적었는지의 차이다. 이 결과가 지지하는 표현은 “첫 작업의 순서는 일관되게 달라지지 않았다”까지다. 실제 사용자의 첫날 행동은 관측하지 않았다.
- 판별력 15전 15승은 B가 샘플·비교 대상·기각 기준을 쓰라고 명시했고, 판별력 2점 조건이 바로 그 세 가지라서 나온 결과다. 요청한 항목을 일관되게 쓴다는 근거일 뿐, 그 기각 기준이 사용자 업무에서 타당한지, 그 실험을 돌렸다면 잘못된 설계를 더 일찍 버렸을지는 별도 질문이다.
- 당근 결과는 앱 리뷰 자동 라벨링 사례에 대한 것이다. 희소 신고 항목을 찾아내는 능력으로 해석하면 안 된다.

### 남겨 둘 발견

- 검증할 가정이 주어졌을 때 비교 방법과 포기 조건을 쓰게 하는 지시는 검증 계획 초안을 만드는 데 쓸 만하다.
- 어떤 가정이 가장 위험한지 고르는 능력은 A와 B 사이에 뚜렷한 차이가 없었다.
- 이 실험의 배경인 ‘벽 정의’(토스 글처럼 벽을 정의하고 하나씩 넘는 방식)를 스타터팩에 단계로 넣는 것은 작성자가 이미 도입하지 않기로 했다. 이번 결과도 도입할 근거가 되지 않는다.
